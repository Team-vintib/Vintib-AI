## 1. 연결

| 항목 | 값 |
| --- | --- |
| 엔드포인트 | `/ws` (예: `ws://localhost:8080/ws`) |
| 프로토콜 | **plain WebSocket + STOMP.** SockJS는 쓰지 않는다 |
| 앱 prefix | `/app` (클라이언트 → 서버) |
| 브로커 prefix | `/topic`(브로드캐스트), `/queue`(개인) |
| user prefix | `/user` |

### 인증은 CONNECT 프레임 헤더로 보낸다

**핸드셰이크 URL 쿼리나 HTTP 헤더가 아니다.** 브라우저 `WebSocket` API는 핸드셰이크 요청에
`Authorization` 헤더를 붙일 수 없어서, 토큰을 STOMP CONNECT 프레임의 native header로 받는다.

```ts
const client = new Client({
  brokerURL: `${WS_BASE}/ws`,
  connectHeaders: accessToken ? { Authorization: `Bearer ${accessToken}` } : {},
});
```

동작 규칙:

| 보낸 것 | 결과 |
| --- | --- |
| 토큰 없음 | **연결 성공 (비회원).** 구독·읽기 가능, 발언 불가 |
| 유효한 토큰 | 연결 성공 (회원) |
| 잘못된/만료된 토큰 | **연결 거부** — ERROR 프레임 후 끊김 |

만료 토큰을 조용히 비회원으로 강등시키지 않는다. **연결이 거부되면 토큰을 갱신하고 재연결**해
달라 — 그대로 두면 사용자는 "왜 채팅이 안 써지는지" 알 수 없다.

> 허용 오리진은 `cors.allowed-origins`(로컬 기본값 `http://localhost:5173`)를 따른다. 다른
> 오리진에서 붙으면 핸드셰이크가 **403**이다. HTTP CORS와 별개 설정이므로 배포 시 함께 확인이 필요하다.

## 2. 목적지 표

경매까지 미리 잡아둔 네임스페이스다. 남은 것은 해당 Phase 완료 시 다시 알린다.

| 방향 | destination | 인증 | 상태 |
| --- | --- | --- | --- |
| 발행 | `/app/lives/{liveId}/chat` | **회원만** | ✅ 사용 가능 |
| 구독 | `/topic/lives/{liveId}/chat` | 비회원 허용 | ✅ 사용 가능 |
| 구독 | `/user/queue/errors` | — | ✅ 사용 가능 |
| 발행 | `/app/lives/{liveId}/reactions` | **회원만** | ✅ 사용 가능 |
| 구독 | `/topic/lives/{liveId}/reactions` | 비회원 허용 | ✅ 사용 가능 |
| 구독 | `/topic/lives/{liveId}/viewers` | 비회원 허용 | ✅ 사용 가능 |
| 구독 | `/topic/lives/{liveId}/product` | 비회원 허용 | ⏳ Phase 5 (현재 소개 상품 전환) |
| 구독 | `/topic/lives/{liveId}/auction` | 비회원 허용 | ⏳ Phase 6~8 |

### ⚠️ `/topic/lives/{liveId}/**` 구독은 그 자체로 "시청 중"으로 집계된다

어느 토픽이든 이 접두어 아래를 구독하면 **그 방송의 시청자 한 명으로 센다.** 채팅만 구독해도,
경매만 구독해도 마찬가지다. 같은 연결에서 네 토픽을 구독해도 **한 명**이다(세션 단위 집계).

그래서 **보고 있지 않은 방송의 토픽을 미리 구독해 두면 시청자 수가 부풀려진다.** 목록 화면에서
카드마다 미리 구독하는 식은 피해 달라 — 화면을 벗어날 때는 `unsubscribe()`를 호출해 주면 된다.

**입찰은 STOMP가 아니라 REST(`POST`)로 받는다.** 성공 여부를 즉시 알아야 하는 동작이라
동기 응답이 필요하다. 결과 전파만 STOMP다. 자세한 계약은 Phase 7에서 별도 문서로 낸다.

## 3. 채팅 발행

`/app/lives/{liveId}/chat`

```json
{ "content": "이 자켓 사이즈 M 맞나요?", "clientMessageId": "tmp-3f9c1e" }
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `content` | 예 | 1~500자. 앞뒤 공백은 서버가 제거한 뒤 길이를 판정하고, 저장도 제거된 값으로 한다 |
| `clientMessageId` | 아니요 | 클라이언트가 만든 임시 ID. 브로드캐스트에 그대로 실려 돌아온다 |

### ack 채널을 따로 두지 않았다

발행자도 `/topic/lives/{liveId}/chat`으로 자기 메시지를 받는다. 그 payload에
`clientMessageId`가 그대로 담겨 오므로, **낙관적으로 그려둔 말풍선을 그 값으로 찾아 치환**하면
된다. 다른 구독자는 이 필드를 무시하면 된다.

목적지를 하나로 유지하는 편이 ack 채널을 따로 만들어 순서를 맞추는 것보다 단순하고, 클라이언트가
만든 임시 문자열이라 노출돼도 문제가 없다.

## 4. 채팅 구독 payload

`/topic/lives/{liveId}/chat` — **REST 이력 조회와 같은 형태다.** 어댑터를 두 개 만들 필요가 없다.

```json
{
  "messageId": 1044,
  "senderId": 31,
  "senderNickname": "빈티지장인",
  "senderProfileImageUrl": null,
  "senderType": "USER",
  "content": "이 자켓 사이즈 M 맞나요?",
  "createdAt": "2026-07-30T14:02:11",
  "clientMessageId": "tmp-3f9c1e"
}
```

| 필드 | 타입 | nullable | 비고 |
| --- | --- | --- | --- |
| `messageId` | `Long` | 아니요 | **재접속 후 누락분 보충 시 커서로 쓴다** |
| `senderId` | `Long` | 가능 | `SYSTEM`·`AI` 메시지는 null |
| `senderNickname` | `String` | 가능 | 닉네임이 없으면 이름으로 대체됨. `SYSTEM`은 null |
| `senderProfileImageUrl` | `String` | **항상 null (현재)** | 아래 5번 참고 |
| `senderType` | enum | 아니요 | `USER` / `SYSTEM` / `AI` |
| `content` | `String` | 아니요 | |
| `createdAt` | datetime | 아니요 | 서버 수신 시각 |
| `clientMessageId` | `String` | 가능 | 발행자가 보낸 값. 이력 조회에서는 항상 null |

`senderType` 처리:

- `USER` — 일반 말풍선
- `SYSTEM` — 입장·퇴장·경매 안내. 작성자가 없으니 안내 스타일로 표시해 달라
- `AI` — **값만 열어둔 상태.** AI 채팅 매니저(CHAT-002/003/004)가 보류라 현재 발생하지 않는다

## 5. `senderProfileImageUrl`은 아직 항상 null이다

**회원 엔티티에 프로필 이미지 필드가 없다.** `member` 테이블 스키마에는 `profile_image_url`이
있는데 `Member` 엔티티에는 매핑이 빠져 있어서, 지금은 채울 값 자체가 없다. 회원 도메인은 서윤
담당이라 별도 요청 문서를 전달했다.

필드는 **미리 넣어 뒀으니 DTO·어댑터는 지금 확정해도 된다.** 값이 생기면 그대로 채워진다.
`null`이면 기본 아바타를 쓰는 방식으로 처리해 달라 — `viewerCount`와 같은 패턴이다.

## 6. 에러 규약

`/user/queue/errors` — **발행자에게만** 간다. 브로드캐스트 토픽에 실으면 남의 실패 메시지가
모든 시청자 화면에 뜬다.

본문은 **REST와 동일한 `ApiResponse` 규격**이다. 에러 처리를 한 갈래로 유지할 수 있다.

```json
{
  "success": false,
  "data": null,
  "error": { "code": "L008", "message": "채팅은 로그인 후 이용할 수 있습니다.", "errors": null }
}
```

| 코드 | 상황 | FE 처리 제안 |
| --- | --- | --- |
| `L008` | 비회원이 **발언** 시도 | 로그인 유도 |
| `L009` | 빈 메시지 또는 500자 초과 | 입력창에서 미리 막고, 그래도 오면 토스트 |
| `L010` | 비회원이 **반응** 시도 | 로그인 유도 (문구를 채팅과 다르게 쓸 수 있다) |
| `L011` | 반응 rate limit 초과 | **토스트를 띄우지 않기를 권한다** — 아래 반응 섹션 참고 |
| `L007` | 종료·취소된 방송에 발언·반응 | 입력창·반응 버튼 비활성화 |
| `L001` | 존재하지 않는 라이브 | 목록으로 이동 |
| `C001` | payload 형식 오류 (예: 없는 `ReactionType`) | 버그 신호 — 콘솔에 남기고 조용히 무시 |
| `U001` | 토큰의 회원이 없음 | 재로그인 |

> `L009`는 서버가 최종 판정한다. FE에서 500자를 막아도 서버 기준(앞뒤 공백 제거 후 길이)과
> 어긋날 수 있으니 에러 처리는 남겨 두는 편이 안전하다.

> `C001`은 **역직렬화 단계에서 터진 경우**도 포함한다. 이때는 서버 핸들러가 실행되기 전이라
> 어떤 필드가 문제였는지는 알려주지 못한다.

## 7. 과거 메시지 조회 (REST)

```http
GET /api/lives/{liveId}/chat-messages?cursor={messageId}&size=30
```

- **비회원도 조회 가능** (인증 헤더 불필요)
- WebSocket은 접속 이후 메시지만 주므로, **중간 입장 시 이력**과 **재접속 후 누락분 보충**을 이걸로 채운다

| query | 기본값 | 설명 |
| --- | --- | --- |
| `cursor` | 없음 | 이 `messageId`보다 **오래된** 메시지. 최신순. 위로 스크롤용 |
| `after` | 없음 | 이 `messageId`보다 **새로운** 메시지. **오래된 순.** 재접속 후 끊긴 구간 메우기용 |
| `size` | `30` | 1~100. 벗어나면 400 |

`cursor`와 `after`를 **동시에 주면 400**이다. 방향이 반대라 임의로 하나를 고르면 FE가 왜 예상과
다른 결과가 오는지 알 수 없다. 자세한 설명·예시는 `002-realtime-chat-handoff.md` 참고.

응답:

```json
{
  "success": true,
  "data": {
    "content": [ /* 위 4번과 같은 형태, 최신순 */ ],
    "nextCursor": 1043,
    "hasNext": true
  },
  "error": null
}
```

### 커서는 page 번호가 아니다

채팅은 조회하는 동안에도 계속 쌓인다. `page=1`을 요청하는 순간 경계가 밀려 **같은 메시지가 두 번
보이거나 빠진다.** 그래서 오프셋 대신 `messageId` 커서를 쓴다. 응답의 `nextCursor`를 다음 요청에
그대로 넣고, `hasNext`가 `false`면 더 없다는 뜻이다.

`totalElements`를 주지 않는 것도 의도다 — 매 요청마다 값이 바뀌는 전체 개수를 세느라 COUNT
쿼리를 한 번 더 쏠 이유가 없다. **무한 스크롤에는 `hasNext`만 있으면 충분하다.**

### 정렬은 최신순 고정

`content[0]`이 가장 최신 메시지다. 채팅창은 보통 아래가 최신이므로 **FE에서 뒤집어 쓰는 것을
전제로 했다.** 서버가 오래된 순으로 주면 커서 의미가 반대가 되어 헷갈린다.

### 차단 메시지는 응답에서 빠진다

`is_blocked` 처리된 메시지는 목록에도 브로드캐스트에도 나오지 않는다. **숨김 판단을 FE에 맡기지
않는다** — 클라이언트마다 다르게 보이면 안 되기 때문이다. (금칙어·도배 차단 자체는 CHAT-004로
보류 상태라 현재 차단되는 메시지는 없다.)

## 8. 시청자 수

### 초기값은 REST, 변화는 STOMP

```
라이브 상세 GET /api/lives/{liveId}  →  currentViewerCount (초기값)
        ↓
/topic/lives/{liveId}/viewers 구독   →  이후 변화
```

**구독만 하고 초기값을 토픽에서 기다리면 화면이 비어 있게 된다.** 구독 시점의 브로드캐스트가
자기 세션에 도달하는 것은 보장되지 않는다(구독 등록과 이벤트 발행이 경합한다). 변화가 없으면
다음 프레임은 다른 사람이 들어오거나 나갈 때까지 오지 않는다.

`/topic/lives/{liveId}/viewers` payload:

```json
{ "liveId": 101, "viewerCount": 128 }
```

| 필드 | 타입 | nullable | 비고 |
| --- | --- | --- | --- |
| `liveId` | `Long` | 아니요 | 여러 방송을 한 연결에서 구독할 때 구분용 |
| `viewerCount` | `int` | 아니요 | **0일 수 있다** |

### `peakViewerCount`와 다른 값이다

라이브 상세에 두 필드가 함께 온다. 섞어 쓰면 안 된다.

| 필드 | 뜻 | 방송 종료 후 |
| --- | --- | --- |
| `currentViewerCount` | **지금** 보고 있는 사람 수 | 0으로 비워진다 |
| `peakViewerCount` | 그 방송의 **최고 기록** | 남는다 |

### 프로세스 재기동 시 0으로 리셋된다

시청자 수는 Redis에만 있는 휘발성 값이라 **서버가 재시작되면 0부터 다시 센다.** 실제로 보고
있던 사용자는 재연결하면서 다시 집계되므로 몇 초 안에 복구된다. 배포 직후 잠깐 낮게 보이는
것은 정상이다.

## 9. 반응 이모지

### 발행 — `/app/lives/{liveId}/reactions` (회원만)

```json
{ "type": "HEART" }
```

`type` 허용값은 **`HEART` / `FIRE` / `CLAP` / `WOW` 네 가지뿐이다.** 자유 이모지 문자열은 받지
않는다 — 그러면 모든 시청자 화면에 임의 문자열을 띄우는 통로가 된다. FE 쪽 이모지·애니메이션에
이 네 값을 매핑해 달라. 표현을 바꿔도 서버 계약은 그대로다.

### 구독 — `/topic/lives/{liveId}/reactions`

```json
{
  "liveId": 101,
  "type": "HEART",
  "senderId": 42,
  "senderNickname": "빈티지러버",
  "sentAt": "2026-07-30T21:15:03"
}
```

| 필드 | 타입 | nullable | 비고 |
| --- | --- | --- | --- |
| `liveId` | `Long` | 아니요 | |
| `type` | enum | 아니요 | `HEART` / `FIRE` / `CLAP` / `WOW` |
| `senderId` | `Long` | 아니요 | 비회원은 보낼 수 없어 항상 값이 있다 |
| `senderNickname` | `String` | 가능 | 닉네임이 없으면 이름으로 대체됨 |
| `sentAt` | datetime | 아니요 | **서버 시각** |

### 저장하지 않는다 — 이력 조회 API가 없다

의도된 설계다. 초당 수십 건이 들어와도 DB 부하가 0이고, 지나간 반응을 되짚어 볼 화면도 없다.
**중간에 입장한 시청자는 그 전의 반응을 볼 수 없다.** 채팅과 달리 이력 보충이 없다.

### 자기 반응이 두 번 그려지지 않게 `senderId`로 걸러 달라

발행자도 자기 반응을 브로드캐스트로 받는다. 즉시 그려두고 브로드캐스트를 그대로 또 그리면
하나가 두 개로 보인다. `senderId === 내 회원 ID`인 프레임은 무시하면 된다.

### rate limit — 초당 5건

같은 방송·같은 회원 기준으로 **1초에 5건까지** 통과한다. 넘으면 `L011`이 오고 그 반응은 버려진다.

**이 에러에 토스트를 띄우지 않기를 권한다.** 하트 연타는 정상적인 사용 방식이고, 여섯 번째
탭에서 "너무 빠릅니다" 경고가 뜨면 사용자는 무엇을 잘못했는지 알 수 없다. 서버를 지키려는
제한이 아니라 **다른 시청자의 브라우저가 애니메이션 폭주로 멈추지 않게** 하는 제한이다.
FE에서도 버튼에 짧은 쿨다운을 두면 이 에러가 거의 오지 않는다.

## 11. FE에서 확인 부탁

1. STOMP 클라이언트의 `connectHeaders`에 `Authorization`을 넣는 구조인지 (URL 쿼리 아님)
2. 잘못된/만료 토큰이면 **연결 자체가 거부**되므로, 토큰 갱신 후 재연결 로직이 필요하다
3. `clientMessageId` 기반 낙관적 렌더 → 치환 흐름
4. 이력 조회는 `page`가 아니라 `cursor` 기반
5. `senderProfileImageUrl`은 당분간 `null` — 기본 아바타 처리
6. **시청자 수 초기값은 라이브 상세의 `currentViewerCount`** — 토픽에서 기다리면 안 된다
7. **보고 있지 않은 방송의 토픽은 구독하지 않기** — 시청자 수가 부풀려진다
8. 반응은 `senderId`로 자기 것을 걸러내고, `L011`에는 토스트를 띄우지 않기

궁금한 점이나 계약을 바꿔야 하는 부분이 있으면 이 문서에 이어서 적어 주시면 된다.
