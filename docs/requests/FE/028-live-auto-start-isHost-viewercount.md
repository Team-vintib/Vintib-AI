# 028 라이브 이슈 4건 — 자동 시작 / 내 라이브 표시 / 홈 목록 / 시청자 수 중복

- **작성자 파트**: BE (정윤) / **대상 파트**: FE
- **작성일**: 2026-08-04

정윤님이 리포트한 라이브 이슈 4건을 조사했습니다. 원인별로 BE에서 고친 것과 FE 확인이 필요한
것을 나눴습니다.

---

## 1. 예약 라이브 자동 시작 — **BE에서 반영 완료, FE 조치 불필요**

이전에는 예정 시각이 지나도 호스트가 `PATCH /api/lives/{liveId}/status`를 직접 호출해야만
`LIVE`로 바뀌었습니다. 이번에 서버 스케줄러(30초 주기)를 추가해 예정 시각이 지난 라이브를
자동으로 `LIVE`로 전이시킵니다.

- 전이 시 기존과 **완전히 같은 경로**를 탑니다 — room 배정, `LIVE_STARTED` 팔로워 알림,
  `/topic/lives/{liveId}/status` 브로드캐스트까지 전부 동일합니다.
- FE는 이미 이 토픽을 구독해 `applyStatusMessage`로 처리하고 있으므로(`LiveWatchPage.vue`),
  **별도 대응이 필요 없습니다.** 방송 시작 시점이 호스트 수동 클릭이 아니라 서버 타이머가 될
  수 있다는 점만 참고해 주세요(최대 30초 오차).

## 2. 목록 조회에서 "내 라이브" 표시 — **BE 필드 추가 완료, FE 코드 변경 필요**

`GET /api/lives`(전체보기) 응답의 `LiveListItemResponse`에 `isHost` 필드를 추가했습니다.
상세 조회(`GET /api/lives/{liveId}`)의 `isHost`와 완전히 같은 규칙입니다 — 인증 토큰으로 판별한
"요청자가 이 방송의 호스트인지"이며, 비회원·타인이면 `false`입니다.

```jsonc
{
  "liveId": 101,
  "title": "90s 데님 재킷 라이브 셀렉션",
  "hostId": 31,
  "hostNickname": "빈티지장인",
  "isHost": true,   // 신규
  "thumbnailUrl": "...",
  // ...
}
```

**`myApi.ts`의 `getMyHostLives()`를 이 필드를 쓰도록 바꿔주세요.** 지금 코드
(`FE/src/domains/my/api/myApi.ts:299`)는 두 가지 문제가 있습니다.

1. `skipAuth: true`로 호출하고 있어 인증 토큰이 안 실립니다. 그 결과 서버는 `selfView=false`로
   판단해 **공개 상태(SCHEDULED/LIVE)만** 돌려주고, 종료·취소된 내 라이브는 응답에 아예 없습니다.
2. `hostId === userId`로 클라이언트에서 직접 비교합니다 — 상세 조회에서 이미 겪었던 "회원 정보
   복원이 렌더보다 늦으면 판정이 뒤집힌다"는 문제가 목록에도 그대로 있습니다.

권장 수정:
- `GET /api/lives?hostId={내ID}`를 **인증 토큰을 실어서** 호출한다(`skipAuth` 제거).
- 서버가 이미 `hostId` 필터 + 종료·취소 포함 전체 상태로 응답을 좁혀 주므로, 클라이언트 쪽
  "최신 100건 중 필터링"은 필요 없다 — `page`/`size`만 페이지네이션 용도로 쓰면 된다.
- `isMine`/"내 라이브" 판정이 필요하면 `hostId` 비교 대신 응답의 `isHost`를 쓴다.

이게 사용자가 리포트한 "내 라이브인데 남 라이브처럼 뜬다"의 원인으로 보입니다 — `isHost`가
아예 없었고, `skipAuth` 때문에 서버가 애초에 비회원 취급으로 응답했습니다.

## 3. 홈 화면에 진행중/예약 라이브가 안 뜨는 문제 — **원인 확인, 대부분 1번으로 해소**

홈(`/home`)의 `liveNow`/`scheduledLives`와 전체보기(`/lives`)는 필터가 다릅니다.

- 홈의 `scheduledLives`는 **예정 시각이 아직 안 지난** 라이브만 보여줍니다(의도적 — 지나간
  예약이 "곧 시작"으로 홈에 영원히 남는 걸 막으려는 설계입니다).
- 전체보기(`/lives`)는 상태만 보고 시각은 안 봅니다 — `SCHEDULED`면 예정 시각이 지났어도
  나옵니다.

즉 예정 시각이 지났는데 아직 `LIVE`로 전이되지 않은 라이브는 전체보기에는 보이고 홈에서는
사라지는 상태가 됩니다. 이게 1번(자동 시작 없음)과 겹쳐서 생긴 증상이었습니다 — 이제 예정
시각이 지나면 30초 안에 자동으로 `LIVE`가 되므로, 그 라이브는 홈의 `liveNow`에 나타나고 이
공백이 사실상 사라집니다. `liveNow`가 계속 비어 있다면 실제로 `LIVE` 상태인 라이브가 없다는
뜻이니, 테스트 시 라이브를 하나 열어서(즉시 개설 또는 예약+자동 시작 대기) 확인해 주세요.

홈 API 자체(쿼리·필드 매핑)에서는 버그를 찾지 못했습니다.

## 4. 시청자 수가 1명 입장에 2명씩 늘어나는 문제 — **FE 원인, BE는 의도된 설계**

원인을 찾았습니다. **`LiveWatchPage.vue`가 라이브 하나당 WebSocket(STOMP) 연결을 2개 엽니다.**

- `LiveWatchPage.vue` 자신이 `connectRealtime()`으로 연결 하나를 열어 `/topic/lives/{id}/status`,
  `/topic/lives/{id}/product`를 구독합니다(주석에 "채팅/반응/시청자수는 LiveChatOverlay가
  별도 클라이언트로 관리하므로 여기서 건드리지 않는다"고 명시돼 있습니다).
- 자식 컴포넌트 `LiveChatOverlay.vue`가 **별도의** `LiveRealtimeClient`로 또 하나의 연결을 열어
  `/topic/lives/{id}/chat`, `/reactions`, `/viewers`, `/user/queue/errors`를 구독합니다.

BE의 시청자 집계(`LiveSessionEventListener`)는 **`/topic/lives/{id}` 아래 어떤 서브토픽이든
구독하면 그 세션을 시청자 한 명으로 셉니다** — 채팅만 구독해도 보고 있는 것으로 치는 의도된
설계입니다(테스트 `LiveViewerCountStompTest.구독하면_시청자로_집계된다`로 고정돼 있습니다).
그런데 STOMP 연결(세션)이 다르면 서버는 같은 브라우저인지 알 방법이 없습니다 — 세션 ID로만
구분하기 때문입니다. 그 결과 실제 시청자 한 명이 페이지를 열 때마다 **연결이 2개, 즉 세션도
2개**가 생겨 시청자 수가 2씩 올라갑니다.

**이건 BE가 아니라 FE에서 고쳐야 합니다.** BE가 세션 대신 다른 기준(예: 회원 ID)으로 묶는
방법도 있지만, 비회원 시청도 세야 하고 같은 회원이 여러 탭/기기로 보는 것은 실제로 별도
시청자로 세는 게 맞아서, 세션 = 연결 단위 집계 자체는 바꾸지 않는 편이 맞다고 판단했습니다.

권장 수정: **한 라이브 시청 화면에서 STOMP 연결을 하나만 쓰도록 합칩니다.** `LiveChatOverlay`가
이미 만드는 연결에 `status`/`product` 구독을 얹거나(예: `LiveChatOverlay`가 만든
`LiveRealtimeClient`를 부모가 넘겨받아 추가 구독), 반대로 `LiveWatchPage`가 만든 연결 하나를
자식에 넘겨 채팅/반응/시청자수 구독도 거기서 하게 하면 됩니다. `LiveBroadcastPage.vue`(호스트
방송 화면)는 이미 `LiveChatOverlay` 연결 하나만 쓰고 있어 이 문제가 없습니다 — 시청 화면만
고치면 됩니다.
