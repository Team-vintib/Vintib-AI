## 결론 먼저

**FE 코드 문제가 아니고, 서버 버전 문제도 아닙니다.** SSAFY EC2 의 **상위 방화벽이 미디어
포트를 막고 있던 것**이 유일한 원인입니다.

**FE 는 아무것도 바꾸지 않으셔도 됩니다.** livekit-client 버전도 그대로 두세요.

---

## 질문별 답변

### 1) 서버 버전 1.9.1 → 올려야 하나요? / FE 가 낮춰야 하나요?

**둘 다 아닙니다.** LiveKit 서버 로그에 접속이 이렇게 찍혀 있었습니다.

```
"starting RTC session"
"Client": {"sdk": "JS", "version": "2.21.0", "protocol": 17, "browser": "Chrome"}
```

**서버 1.9.1 이 protocol 17 을 정상 수락했습니다.** `/rtc/v1` 404 → `/rtc` 폴백은
livekit-client 2.x 가 구버전 서버를 만났을 때의 **설계된 동작**이고, 실제로 잘 넘어갔습니다.
콘솔의 `Consider upgrading` 은 권고 문구일 뿐 이번 증상과 무관합니다.

### 2) livekit 컨테이너 nodeIP 가 공인 IP 인가요?

**공인 IP 맞습니다.** `NODE_IP=43.201.54.59` 이고, 서버가 광고한 후보도 정확했습니다.

```
"subscriberCandidates": [
  "[local][trickle] udp4 host 43.201.54.59:7885",
  "[local][trickle] tcp4 host 43.201.54.59:7881"
]
```

사설 IP(172.x) 문제였다면 여기가 `172.x` 로 찍혔을 텐데 아니었습니다.

### 3) UDP 7885 / TCP 7881 방화벽 + setup 스크립트

**UFW 에는 이미 둘 다 열려 있었고 호스트도 LISTEN 중이었습니다.** 스크립트도 실행돼
있었습니다(다시 돌려도 `Skipping adding existing rule`).

**그런데도 외부에서 닿지 않았습니다.** 외부에서 포트를 직접 찔러 본 결과가 이렇습니다.

| 포트 | UFW | 외부 접근 |
| --- | --- | --- |
| 22 / 80 / 443 / 8989 | 허용 | ✅ 열림 |
| **7881** | **허용** | ❌ **막힘** |
| **7885/udp** | **허용** | ❌ 막힘 (tcpdump 인바운드 0) |
| 443/udp | — | ❌ 막힘 (프로브 12개 → 0개 도달) |

UFW 상태가 같은데 결과가 갈립니다. → **SSAFY 가 관리하는 상위 방화벽이 TCP 22·80·443·8989
만 통과시킵니다.** UDP 는 443 을 포함해 전 포트가 막혀 있습니다. 웹 콘솔이 제공되지 않아
우리가 열 수 없습니다.

### 4) `/rtc/validate` 는 되나요?

**시그널링은 애초에 정상이었습니다.** 그래서 확인이 불필요합니다 — 토큰 발급(200), 시그널
연결, room join 까지 전부 성공했고 `participant joined` 도 찍혔습니다. 끊긴 지점은 그 다음의
**미디어(ICE) 협상**입니다.

```
"connectionType": "unknown"
"removing participant without connection"
"reason": "SIGNAL_SOURCE_CLOSE"
```

`without connection` — 미디어가 한 번도 붙지 못한 채 15초 ICE 타임아웃으로 끝났습니다.
검은 화면에 에러가 없던 것도 이 때문입니다.

## 조치 — 미디어를 포트 80 으로 옮겼습니다

열려 있는 포트 중 미디어에 내줄 수 있는 것이 **80 하나뿐**입니다(22=SSH, 443=Caddy,
8989=SSAFY Gerrit). 그래서 LiveKit TCP 미디어를 80 으로 옮기고 Caddy 를 80 에서 내렸습니다.

**FE 영향: 없습니다.**

- 시그널링은 `wss://i15a108.p.ssafy.io` 그대로(443)
- 미디어 포트는 서버가 ICE 후보로 알려주므로 **FE 가 지정할 것이 없습니다**
- `serverUrl`·`token` 사용법 그대로

### 알아두실 것 두 가지

**① 미디어가 TCP 입니다.** UDP 가 전부 막혀 WebRTC 본래의 UDP 경로를 못 씁니다. TCP 는
재전송·헤드오브라인 블로킹이 있어 **UDP 대비 지연과 끊김에 불리합니다.** 회피가 아니라
감수하는 선택입니다 — 상위 방화벽을 우리가 못 여는 이상 대안이 없습니다.

**② 연결이 조금 늦을 수 있습니다.** 서버는 UDP 후보도 함께 광고하는데(나중에 SSAFY 가
열어 줄 여지를 남김) 그게 막혀 있어, 클라이언트가 UDP 를 먼저 시도하고 실패한 뒤 TCP 로
넘어갑니다. 접속까지 1~2초 더 걸릴 수 있습니다.

**③ `http://` 자동 리다이렉트가 사라집니다.** 80 을 미디어에 내주면서 Caddy 의
http→https 리다이렉트를 포기했습니다. 주소를 직접 치는 경우 `https://` 를 붙여야 합니다.
앱 내 링크는 전부 https 라 실사용에는 영향이 없습니다.

## 확인 부탁

배포 후 재접속해서 영상이 뜨는지 봐 주세요. 콘솔에서 이렇게 바뀌어야 정상입니다.

- 이전: `connection state changed: connecting -> disconnected`
- 이후: `connected` 유지, 영상 표시

여전히 안 되면 **콘솔 전체 로그와 접속 망(사내망/핫스팟)** 을 알려 주세요. 사내망이 TCP 80
아웃바운드를 막는 경우는 드물지만 확인은 필요합니다.
