# 032 라이브 `createdAt` · 최신순 정렬 · 시청자 수 회원 기준 집계

- **작성자 파트**: BE (정윤) / **대상 파트**: FE
- **작성일**: 2026-08-05
- **원 요청**: `docs/requests/BE/024`(라이브 생성 시각), `026`(최신순 정렬 기준),
  `028`(유령 시청자 세션 — 후속)

---

## 1. `createdAt` 추가 (024)

라이브 **상세**(`GET /api/lives/{liveId}`)와 **목록**(`GET /api/lives`) 응답 양쪽에 넣었습니다.

```jsonc
{
  "liveId": 101,
  // ...
  "scheduledAt": "2026-08-06T20:00:00",
  "startedAt": null,
  "createdAt": "2026-08-05T14:12:03"   // 신규
}
```

포맷은 기존 시각 필드와 동일합니다(오프셋 없는 KST 벽시계).

> 요청서에 "생성 시각 기준의 정확한 의미는 팀 내 확정 필요"라고 적어 주셨는데, BE는 값만
> 내려주고 **경과 시간을 무엇으로 잴지는 FE 판단**으로 두었습니다. 방송 중 경과 시간은
> `startedAt` 기준이 자연스럽고, "만든 지 얼마나 됐나"는 `createdAt` 기준입니다.

## 2. `sort=LATEST` 기준을 `createdAt`으로 변경 (026)

**FE 코드 변경 없이 정렬 결과만 바뀝니다.**

- 이전: `startedAt` → `scheduledAt` → `id` (두 상태가 시각 컬럼을 따로 써서 `NULLS LAST`까지 필요했음)
- 이후: `createdAt DESC` → `id DESC`

지적하신 대로 예약 방송은 만든 시점과 시작 예정 시각이 달라, 시작 시각으로 정렬하면 생성
순서와 어긋나게 섞였습니다. 이제 "최근에 만든 순"이 정확히 맞습니다.

`VIEWERS_DESC`·`TITLE_ASC`는 그대로입니다.

## 3. 시청자 수를 **회원 ID 기준**으로 집계 (028 후속)

`028`에서 하트비트를 요청해 주셔서 반영했고(이미 머지됨), 그 뒤에 **하트비트로도 안 없어지는
중복**이 남아 있어 집계 기준 자체를 바꿨습니다.

### 무엇이 문제였나

세션 ID로만 세다 보니 같은 사람이 여러 명으로 잡히는 경로가 둘 있었습니다.

1. **재연결** — FE가 다시 붙으면 세션 ID가 새로 발급됩니다. 옛 세션은 서버가 하트비트로 알아챌
   때까지(약 30초) 남아 있어 그 사이 한 명이 두 명으로 보입니다. **자동 재연결이 이 창을
   적극적으로 만듭니다.**
2. **탭·기기 여러 개** — 같은 사람이 폰과 PC로 보면 두 명이었습니다.

### 어떻게 바뀌나

- **로그인 회원은 회원 ID로 셉니다.** 재연결해도, 탭을 여러 개 열어도 **한 명**입니다.
- **비회원은 그대로 세션 기준**입니다. 신원이 없어 달리 구분할 방법이 없습니다.
- 회원이 탭 하나를 닫아도 다른 탭이 살아 있으면 시청자로 남습니다(마지막 연결이 끊길 때만 빠집니다).
- 호스트 제외는 그대로입니다.

### FE가 할 일

**없습니다.** 응답 형식·토픽 모두 그대로이고 집계 규칙만 바뀝니다.

다만 테스트하실 때 참고하세요:

- **같은 계정으로 창을 여러 개 열면 1명입니다.** 여러 명으로 보이게 하려면 서로 다른 계정이나
  시크릿 창(비회원)을 쓰셔야 합니다.
- 폰과 PC로 같은 계정을 보면 1명입니다. 이게 의도와 다르면 알려 주세요 — 기준을 되돌릴 수 있습니다.
