# 라이브 방송 WebRTC 기술 — BE 회신 및 확정 사항

- **요청자 파트**: BE
- **대상 파트**: AI
- **회신 대상**: AI 파트 `002-live-webrtc-candidates.md` (라이브 방송 WebRTC 기술 후보 정리)
- **상태**: 기술 선택 확정 통보 + 일정·요건 답변

## 결론 먼저

1. **OpenVidu v3로 확정합니다.** AI 파트 의견과 같습니다. 정리해 주신 후보 비교가 판단에 도움이 됐습니다.
2. **저장소는 이미 해결됐습니다.** MinIO가 운영에 배포 완료돼 있습니다. AI 문서에는 "자체 호스팅 가능해야 한다"가 미해결 요건으로 적혀 있는데, 이미 떠 있는 상태입니다.
3. **다만 STT 연동은 당분간 착수하지 않습니다.** 녹화 파이프라인은 방송 자체가 성립한 뒤 순번이고, 남은 일정상 이번 스프린트에는 들어가지 않습니다.

## 사실관계 정정 3가지

문서 작성 시점 이후 상황이 바뀐 부분과, 처음부터 조금 다르게 알고 계셨던 부분입니다.

### 1. 미디어 서버는 "미확정"이 아니라 "미설치"였습니다

문서 배경에 *"WebRTC 미디어 서버가 아직 확정 안 됐다고 들었습니다"* 라고 적혀 있는데, 기술 선택 자체는 로드맵 단계에서 OpenVidu v3로 정해져 있었습니다. AI 파트가 근거로 찾으신 것들(`live.openvidu_room` 컬럼, `setup-swap.sh`, `Caddyfile` 주석)이 바로 그 결정의 산물입니다.

미확정이었던 것은 **설치 시점**이지 기술이 아닙니다. 현재는 티켓까지 끊어둔 상태입니다.

- `S15P11A108-448` [INFRA | BE] OpenVidu v3 미디어 서버 구축 (EC2)
- `S15P11A108-449` [LIVE-005 | BE] OpenVidu 연동 및 송출·시청 토큰 발급

### 2. MinIO는 이미 운영에 배포돼 있습니다

AI 문서의 저장소 요건("AWS 계정/과금 없이 자체 호스팅, S3 호환 API")은 **이미 충족된 상태**입니다. 상품 이미지·시착 결과 이미지 저장용으로 먼저 들어갔고, 녹화 파일도 같은 스토리지를 쓰면 됩니다.

| 항목 | 값 |
| --- | --- |
| 이미지 | `minio/minio:RELEASE.2025-09-07T16-13-09Z` (버전 고정) |
| 컨테이너 네트워크 엔드포인트 | `http://minio:9000` |
| 버킷 | `vintib-public` / `vintib-private` |
| API | S3 호환 |

접근 자격증명은 GitLab CI/CD Variables로 관리하고 있어 여기 적지 않습니다. AI 워커가 접근해야 하면 별도로 전달드리겠습니다.

**워커가 HTTP(S) URL로 다운로드하는 기존 구조는 그대로 쓰실 수 있습니다.** 다만 공개 버킷에 녹화본을 두는 건 곤란하니(방송 원본이 URL만 알면 열림), `vintib-private` + presigned URL 방식을 전제로 봐 주시면 좋겠습니다.

### 3. LIVE-007(STT)은 현재 보류 상태입니다

AI 채팅 매니저 기능 전반이 보류로 정리됐습니다. 따라서 이번 스프린트의 라이브 작업에는 STT 연동이 들어가지 않습니다. 문서에서 요청하신 요건들은 폐기가 아니라 **뒤 순번으로 미뤄둔 것**입니다.

## AI 요건별 답변

| AI 요건 | BE 답변 |
| --- | --- |
| 오디오를 파일/스트림으로 추출 | OpenVidu 녹화로 가능할 것으로 보나 **아직 검증 안 했습니다.** 서버를 올린 뒤 확인합니다 |
| HTTP(S) 접근 가능한 URL | MinIO presigned URL로 제공 가능 |
| 자체 호스팅 저장소 | **해결됨** — MinIO 배포 완료 |
| 완료 통보(webhook/상태 조회) | 미정. 아래 "확정 못 한 것" 참고 |
| 청크 단위 중간 수신 | **1순위로 잡지 않겠습니다.** 방송 종료 후 일괄 처리를 기본으로 보고, 청크는 여력이 있을 때 검토합니다 |
| 보관 정책 | 지적 감사합니다. 반드시 필요한데 아직 안 정했습니다 |

### 오디오 전용 추출에 대해

AI 문서에서 *"OpenVidu 녹화가 오디오만 뽑는 옵션을 지원하는지 확인 못 했다"* 고 하신 부분은 **저희도 확인하지 못했습니다.** 다만 문서에 *"비디오가 섞여 있어도 무방하다"* 고 명시해 주셔서 블로커로 보지 않습니다. LiveKit Egress의 `audio_only` 옵션 정보는 유용했고, OpenVidu가 그 엔진을 쓰는 만큼 설치 후 실제로 열려 있는지 확인해 보겠습니다.

### 보관 정책이 특히 중요한 이유

단일 EC2(300GB)에 Spring·FastAPI·PostgreSQL·Redis·MinIO·GitLab Runner가 이미 동거하고 있고, 여기에 OpenVidu까지 올라갑니다. 녹화 파일이 쌓이면 디스크가 빠르게 찹니다. **"STT 처리 후 삭제"** 를 기본 방향으로 잡되, AI 파트가 재처리를 위해 원본을 얼마나 들고 있어야 하는지 알려주시면 그에 맞춰 정하겠습니다.

## 왜 LiveKit 직접이 아닌가

AI 파트 판단과 같습니다. 덧붙이자면 저희 쪽 사정이 하나 더 있습니다.

room 관리·토큰 발급을 직접 구현하는 비용도 문제지만, **ERD의 `live.openvidu_room` 컬럼과 인프라 문서·티켓이 전부 OpenVidu 전제로 짜여 있어** 되돌리면 스키마 변경까지 번집니다. 남은 일정에서 "오디오 전용 추출"이라는 이점 하나로 감당할 만한 변경이 아닙니다.

mediasoup·매니지드 클라우드를 비권장으로 정리해 주신 것도 동의합니다. 특히 AWS 과금이 필요한 선택지는 이 프로젝트에서 불가능합니다.

## 진행 순서

STT가 어느 시점에 붙을 수 있는지 가늠하시라고 공유합니다.

```
1. OpenVidu 서버 구축 (-448)        ← 여기가 가장 먼저, 리드타임 있음
2. OpenVidu 연동·토큰 발급 (-449)   ← 방송이 실제로 보이는 지점
3. WebSocket 기반 + 실시간 채팅
4. (여력 시) 녹화 파이프라인 + STT   ← AI 파트 요건이 실제로 걸리는 자리
```

4번은 아직 티켓도 없습니다. 1~3이 끝나고 일정이 남으면 착수하며, 그때 이 문서의 요건을 기준으로 스펙을 맞추겠습니다.

## BE가 아직 확정 못 한 것

착수 시점에 AI 파트와 함께 정해야 합니다.

- **녹화 완료 통보 방식** — webhook vs 상태 조회 API. AI 워커 구조에 어느 쪽이 편한지 의견 주시면 반영하겠습니다.
- **보관 기간** — 재처리를 위해 원본이 얼마나 필요한지에 달렸습니다.
- **버킷·경로 규칙** — `vintib-private` 아래 어떤 키 규칙을 쓸지.
- **청크 분할 단위** — 청크 방식으로 간다면. 지금은 후순위입니다.
