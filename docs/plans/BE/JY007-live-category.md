# 라이브 카테고리 도입 + 상품 카테고리 필수화

- Jira 에픽: [S15P11A108-217](https://ssafy.atlassian.net/browse/S15P11A108-217) `[LIVE]`, [S15P11A108-211](https://ssafy.atlassian.net/browse/S15P11A108-211) `[PROD]`
- 발단: FE 요청 `.codex/requests/be/009-live-list-api-contract.md` (공개 라이브 목록 API)
- 선행: 이 계획이 끝나야 라이브 목록 API를 만들 수 있다

## 배경/목표

FE 라이브 목록 화면이 카테고리 필터를 요구하는데 **`live` 테이블에 카테고리가 없다.** 별도 컬럼을
추가하는 안(A)과 편성 상품에서 유도하는 안(B)을 놓고 검토한 결과, **B로 확정**했다.

핵심 근거는 사용자가 제시한 운영 조건 세 가지다. 이 조건들이 B안의 약점을 없앤다.

| B안의 원래 약점 | 조건으로 해소 |
| --- | --- |
| 대표 카테고리를 하나 못 고름 | **대표를 안 고른다** — 복수로 전부 갖는다 |
| 방송 중 편성이 바뀌면 값이 흔들림 | **방송 시작 후 편성 변경 불가** |
| 예약 라이브는 상품이 없어 카테고리가 빔 | **개설 시점에 상품을 고른다**(즉시·예약 무관) |

덤으로 A안 대비 이점이 둘 있다. 호스트가 카테고리를 따로 입력하지 않아도 되고(개설 화면 변경 불필요),
"아우터로 걸고 신발만 파는" 불일치가 원천적으로 불가능하다.

## 확정된 정책 (사용자 결정 2026-07-29)

1. 상품은 **사전에 등록**한다.
2. **라이브 등록 시점에** 판매할 상품을 등록된 상품 중에서 고른다. 즉시·예약 라이브 모두 동일.
3. **라이브 시작 후에는 상품 추가·삭제 불가.**
4. **상품 등록 시 카테고리는 필수.**
5. 라이브의 카테고리 = 편성된 상품들의 카테고리 집합(복수). 구매자가 그중 아무 카테고리로
   검색해도 그 라이브가 나온다.

## 설계 결정

### 카테고리 계층 활용

시드(`db/seed.sql`)는 2단계다 — 대분류 6개(depth 1), 소분류 30개(depth 2).

```
아우터   ─ 자켓, 코트, 가디건, 베스트, 후드집업
상의     ─ 티셔츠, 셔츠, 니트, 후드티, 스웨트셔츠
하의     ─ 데님, 슬랙스, 카고팬츠, 스커트, 쇼츠
신발     ─ 스니커즈, 부츠, 로퍼, 샌들
가방     ─ 백팩, 숄더백, 토트백, 크로스백, 파우치
액세서리 ─ 모자, 벨트, 스카프, 주얼리, 시계, 선글라스
```

- **상품은 소분류(depth 2)에 단다.** 검색·필터 정밀도를 위해서다. 대분류에 다는 것도 막지는 않되
  권장하지 않는다.
- **라이브 카드에 표시하는 배지는 대분류(depth 1) 집합**으로 올려서(rollup) 중복을 제거한다.
  소분류를 그대로 노출하면 배지가 5~6개씩 붙어 지저분하다.
- **필터는 대분류·소분류 둘 다 받는다.** 대분류를 고르면 그 하위 소분류 상품까지 매칭한다.
  - `아우터` 선택 → 자켓·코트·가디건… 상품을 가진 라이브 전부
  - `스카프` 선택 → 스카프 상품을 가진 라이브만

  사용자가 예로 든 "목도리로 검색하면 그 라이브가 뜬다"가 이 규칙으로 성립한다(목도리 = 액세서리 > 스카프).

### 응답 형태 — 단수에서 복수로

FE 요청서는 라이브당 카테고리 하나를 전제했으나, 이 방식에서는 여러 개가 된다.

```
categoryId: 10, categoryName: "아우터"
  ↓
categories: [{ id: 10, name: "아우터" }, { id: 30, name: "하의" }, { id: 60, name: "액세서리" }]
```

필터 query도 `categoryId` 단일 → `categoryIds` 복수로 확장한다. FE 요청서에도 복수 허용 시
이렇게 바꿔 달라고 적혀 있어 합의된 방향이다.

### 왜 `live`에 컬럼을 두지 않나

편성 상품에서 매번 유도하면 조인 비용이 든다. 그럼에도 컬럼을 두지 않는 이유는 **같은 사실을 두
군데에 저장하면 반드시 어긋나기 때문**이다. 상품 편성이 진실이고 카테고리는 그 파생값이다.

성능이 문제가 되면 그때 `live_category` 반정규화 테이블을 두고 편성 확정 시점에 채운다.
지금 규모(단일 EC2, 발표용)에서는 조인으로 충분하다.

착수 전 서윤과 한 번 맞추는 것이 안전하다. 특히 아래 두 가지가 걸린다.

- 로컬은 `ddl-auto: update`라 **기존 행에 `category_id`가 NULL이면 NOT NULL 추가가 실패**한다.
  로컬 DB를 비우거나 기존 행을 채워야 한다(운영은 `ddl-auto: create`라 무관).
- 온보딩·시착 등 다른 흐름에서 카테고리 없이 상품을 만드는 경로가 있으면 함께 막힌다.

## 확인이 필요한 미결정 사항

1. **Phase A를 내가 직접 할지, 서윤에게 요청할지.** 사용자 지시는 "수정하라"였으나 담당 경계가 걸린다.
2. **`SCHEDULED` 상태에서 편성 변경 허용 여부** — 위에서는 허용으로 잡았다.
3. **기존 상품 중 카테고리가 비어 있는 행 처리** — 로컬 DB 초기화로 갈지, 백필 스크립트를 쓸지.
4. **Phase D의 `VIEWERS_DESC` 정렬** — -450 전까지는 정렬 옵션에서 빼고 내보낼지, 목록 API 자체를
   -450 이후로 미룰지.
