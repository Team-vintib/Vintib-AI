# 온보딩 완료 강제 (회원가입만으로는 서비스 이용 불가)

## 배경/목표

지금은 `ONBOARDING_REQUIRED`(U004, 403, "온보딩을 완료해야 이용할 수 있습니다.") 에러코드가
정의만 되어 있고 **코드 어디에서도 실제로 던져지지 않는다.** 회원가입(`AuthService`,
`POST /auth/signup`)은 이메일·비밀번호·이름만으로 끝나고, `nickname`이 `null`, `onboardingCompleted`가
`false`인 `Member`가 그대로 만들어진다. 이후 온보딩 API(`PATCH /users/{id}`, `S15P11A108-227`)를
호출하도록 강제하는 게이트가 백엔드에 없다 — FE가 가입 직후 온보딩 화면으로 보내주는 것에만 의존하는
상태라, 회원이 온보딩을 영영 안 하고 `nickname = null`인 채로 다른 기능을 계속 쓸 수 있다.

실제로 이 상태 때문에 라이브·채팅 쪽에서 "이름 없는 말풍선"(닉네임 없는 회원이 발언) 버그를
`nickname != null ? nickname : name`으로 임시 대체해 우회하고 있다. 원래
`docs/requests/BE/001-member-entity-schema-drift.md`(정윤→서윤, CHAT-001 응답 작성 중 발견)에서
추적하던 항목인데, 그 문서의 비밀번호 컬럼명 불일치 부분은 `S15P11A108-474`에서 해결되며 문서
전체가 삭제됐다 — 이 "표시명 대체 규칙" 항목만 아직 미해결이라 아래 미결정 사항으로 옮겨 둔다.

목표: **온보딩을 완료하지 않은 회원은 서비스의 다른 기능을 쓸 수 없게 만든다.** ("회원가입 자체가
불가능"이라는 표현은 아래 미결정 사항의 방식 중 어느 쪽이든, 결과적으로 "온보딩 없이는 실질적으로
아무것도 못 한다"는 뜻으로 이해했다.)

## 작업 내용 (초안 — 아래 미결정 사항에 따라 달라짐)

- `ONBOARDING_REQUIRED`를 실제로 던지는 게이트를 추가한다. 후보:
  - JWT 인증 필터/인터셉터 단에서 `onboardingCompleted == false`면 온보딩 관련 API(`PATCH /users/{id}`,
    `GET /users/me` 등 극소수 화이트리스트)를 제외한 모든 요청을 403으로 막는다.
  - 또는 각 컨트롤러/서비스 진입점마다 개별적으로 체크한다(현재 `requireSelf`류 패턴과 비슷하게) —
    다만 매 API마다 빠뜨리기 쉬워 인터셉터 방식보다 신뢰도가 낮다.
- 화이트리스트(로그인, 토큰 재발급, 온보딩 자체 API, 헬스체크, Swagger 등)를 명확히 정의해야 한다.
- FE에는 온보딩 미완료 상태에서 다른 API를 호출하면 403 + `ONBOARDING_REQUIRED`가 온다는 걸 알리는
  요청 문서가 필요하다(화면 전환 로직에 영향).

## 확인 필요한 미결정 사항

- **"회원가입 자체를 불가능하게"의 정확한 의미**:
  1. 회원가입 API(`POST /auth/signup`)와 온보딩 API를 **하나로 합쳐서**, 온보딩 정보 없이는 애초에
     회원 row 자체가 만들어지지 않게 할지
  2. 아니면 지금처럼 회원가입과 온보딩을 **두 단계로 유지하되**, 온보딩 완료 전에는 로그인 이후
     온보딩 API 외의 모든 기능을 막는 게이트만 추가할지
  - 2번이 구현 난이도·기존 흐름과의 정합성 면에서 더 현실적이라고 보지만, 실제 화면 흐름(FE가
    가입 직후 바로 온보딩 화면으로 보내는 SPA 흐름인지, 재방문 로그인 때도 온보딩 화면을 다시
    보여줄 수 있는지)에 따라 달라져 확인이 필요하다.
- **화이트리스트 범위**: 온보딩 완료 전에 정확히 어떤 API까지 허용할지(로그아웃은 당연히 허용,
  마이페이지 조회(`GET /users/me`)는 허용해야 자기 상태를 확인할 수 있음 등) 목록을 정해야 한다.
- **기존 회원 마이그레이션**: 이미 `nickname = null`인 기존 회원이 있다면(테스트 더미 데이터 등)
  게이트를 켜는 순간 전부 막히는데, 로컬/스테이징 데이터를 어떻게 정리할지도 같이 정해야 한다.
- **표시명 대체 규칙 공통화**: 닉네임이 없는 회원의 표시명을 라이브·채팅에서
  `nickname != null ? nickname : name`으로 임시 대체하고 있다. 이 게이트가 들어가 온보딩
  미완료 회원이 다른 기능(채팅 포함)을 아예 못 쓰게 되면 이 우회가 통째로 불필요해질 수도
  있다 — 게이트 방식(위 1번)이 정해지면 이 항목도 같이 정리한다.

## 관련 요청 문서

`onboardingCompleted`가 정확히 언제 `true`로 바뀌어야 하는지는 이 계획과 별개로
`.codex/requests/be/001-onboarding-basic-info-api.md`,
`002-onboarding-interests-api.md`, `004-onboarding-member-type-completion-api.md`에도
공통으로 걸려 있던 미결정 사항이다(2026-07-31 정리하며 이 문서로 모았다). 현재 동작은
ONBOARD-001(기본 정보 저장) 시점에 바로 완료 처리되는데, FE 화면 흐름은
001→002→003→004 네 단계를 거치므로 004(회원 유형 저장)까지 마친 시점으로 옮겨야
할 가능성이 크다 — 위 "확인 필요한 미결정 사항" 1번과 같은 질문이다.
