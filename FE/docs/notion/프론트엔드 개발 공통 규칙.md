## 1. 기본 개발 방식

### 1.1 기술 기준

| 구분 | 추천 규칙 |
| --- | --- |
| 프레임워크 | Vue 3 |
| 언어 | TypeScript |
| 빌드 도구 | Vite |
| Vue 작성 방식 | Composition API |
| SFC 문법 | `<script setup lang="ts">` |
| 라우팅 | Vue Router |
| 전역 상태 | Pinia |
| HTTP 통신 | Axios 공통 인스턴스 |
| 코드 검사 | ESLint |
| 코드 포맷 | Prettier |

### 1.2 Vue 파일 기본 형식

모든 Vue 파일은 다음 순서로 작성한다.

```
<script setup lang="ts">
</script>

<template>
</template>

<style scoped>
</style>
```

- Options API와 Composition API를 혼용하지 않는다.
- 컴포넌트 스타일은 기본적으로 `scoped`를 사용한다.
- 전역 스타일과 디자인 토큰만 별도 공통 스타일 파일에서 관리한다.

### 1.3 패키지 관리

- 저장소에 있는 Lock 파일을 기준으로 패키지 매니저를 한 종류만 사용한다.
    - `package-lock.json` → npm
    - `pnpm-lock.yaml` → pnpm
    - `yarn.lock` → yarn
- 새로운 라이브러리 설치 전 프론트 팀원에게 공유한다.
- 같은 기능을 수행하는 라이브러리를 중복 설치하지 않는다.
- 설치한 라이브러리의 사용 목적과 적용 위치를 공유한다.
- Node.js 버전은 한 버전으로 맞추고 README에 명시한다.

## 2. 네이밍 규칙

### 2.1 파일 및 코드 이름

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| Vue 컴포넌트 | PascalCase, 두 단어 이상 | `ProductCard.vue` |
| 페이지 컴포넌트 | `View`로 끝냄 | `ProductDetailView.vue` |
| 레이아웃 | `Layout`으로 끝냄 | `DefaultLayout.vue` |
| 기본 공통 UI | `Base`로 시작 | `BaseButton.vue` |
| Composable | `use`로 시작 | `useModal.ts` |
| API 파일 | `Api`로 끝냄 | `productApi.ts` |
| 변수·일반 함수 | camelCase | `productList` |
| Boolean | `is`, `has`, `can`, `should` | `isLoading` |
| 상수 | UPPER_SNAKE_CASE | `MAX_FILE_SIZE` |

### 2.2 함수 이름

```
// 사용자의 화면 동작
handleSubmit()
handleModalClose()
handleProductSelect()

// 화면에서 데이터를 불러오는 함수
fetchProducts()
fetchProductDetail()

// API 파일의 요청 함수
getProducts()
createProduct()
updateProduct()
deleteProduct()
```

- 클릭·제출·선택처럼 화면 이벤트를 처리하는 함수는 `handle`로 시작한다.
- 화면에서 서버 데이터를 불러와 상태에 저장하는 함수는 `fetch`로 시작한다.
- API 파일에서는 HTTP 목적이 드러나도록 `get`, `create`, `update`, `delete`를 사용한다.
- 의미가 불분명한 `data`, `value`, `item`, `temp` 같은 이름은 최소화한다.

## 3. TypeScript 규칙

- Props와 Emits에는 타입을 작성한다.
- API 요청·응답 데이터에는 타입을 작성한다.
- 여러 화면에서 사용하는 타입은 별도 타입 파일로 관리한다.
- 한 파일 안에서만 쓰는 간단한 타입은 해당 파일 내부에 선언할 수 있다.
- `any`는 원칙적으로 사용하지 않는다.
- 불가피하게 `any`를 사용하면 이유를 주석으로 남긴다.
- 타입만 가져올 때는 `import type`을 사용한다.

```
interface Props {
  productId: number
  disabled?: boolean
}

const props = withDefaults(defineProps<Props>(), {
  disabled: false,
})

const emit = defineEmits<{
  close: []
  select: [productId: number]
}>()
```

## 4. 컴포넌트 작성 규칙

### 4.1 컴포넌트 분리 기준

다음 중 하나에 해당하면 컴포넌트 분리를 고려한다.

- 동일한 UI가 두 번 이상 반복된다.
- 한 화면 안에서 독립적인 역할을 수행한다.
- 파일이 길어져 화면 구조를 파악하기 어렵다.
- Props와 Emits를 통해 독립적으로 사용할 수 있다.
- 여러 화면에서 공통으로 사용한다.

단순한 문장이나 작은 영역까지 무조건 분리하지 않는다.

### 4.2 공통 컴포넌트 규칙

- 동일한 공통 컴포넌트를 두 사람이 각각 만들지 않는다.
- 공통 컴포넌트 변경 전 상대 프론트 팀원에게 공유한다.
- 특정 화면에만 필요한 기능을 공통 컴포넌트에 억지로 추가하지 않는다.
- 새로운 Variant를 추가할 때 기존 사용 화면이 깨지지 않는지 확인한다.
- 공통 컴포넌트에는 API 호출이나 특정 화면의 비즈니스 로직을 직접 넣지 않는다.

### 4.3 데이터 전달 방식

```
부모 → 자식: Props
자식 → 부모: Emits
컴포넌트 내부 상태: ref, reactive
여러 화면에서 공유하는 상태: Pinia
반복되는 상태 로직: Composable
```

- 자식 컴포넌트가 Props를 직접 수정하지 않는다.
- 부모와 자식 사이에서 해결할 수 있는 상태를 무조건 Pinia에 저장하지 않는다.

## 5. 상태 관리 규칙

### 5.1 Pinia에 저장할 상태

여러 화면이나 서로 멀리 떨어진 컴포넌트가 함께 사용하는 상태만 저장한다.

예:

- 로그인 사용자와 인증 상태
- 사용자 포인트
- 읽지 않은 알림 수
- 장바구니 요약 정보
- 라이브·채팅 연결 상태
- 여러 화면에서 유지해야 하는 공통 상태

### 5.2 컴포넌트 내부에 둘 상태

예:

- 입력창 값
- 현재 선택한 탭
- 한 화면에서만 사용하는 필터
- 모달 열림 여부
- Hover 여부
- 임시 미리보기 데이터

## 6. API 통신 규칙

### 6.1 기본 구조

```
View 또는 Component
        ↓
도메인별 API 함수
        ↓
Axios 공통 인스턴스
        ↓
Backend
```

- Vue 파일에서 Axios 기본 주소와 Header를 직접 설정하지 않는다.
- API 요청은 도메인별 API 파일을 통해 호출한다.
- Axios 공통 인스턴스는 하나만 사용한다.
- 기본 URL, 공통 Header, 인증, Timeout, 공통 오류 처리는 공통 인스턴스에서 관리한다.
- API 응답 타입을 작성한다.
- 서버 주소를 코드에 하드코딩하지 않는다.

### 6.2 Mock 데이터

백엔드 API가 준비되지 않았을 때는 Mock 데이터로 화면을 먼저 구현할 수 있다.

- Mock 데이터는 Vue 파일 여러 곳에 흩어놓지 않는다.
- 실제 API 응답과 동일한 구조와 타입으로 작성한다.
- API 연결 완료 후 사용하지 않는 Mock 데이터는 제거한다.
- 임시 데이터를 실제 사용자 데이터처럼 오해할 수 없도록 구분한다.

## 7. 로딩·오류·빈 화면 규칙

API를 사용하는 화면에는 기본적으로 다음 상태를 구현한다.

```
Loading
Success
Empty
Error
```

| 상황 | 처리 방식 |
| --- | --- |
| 목록·상세 조회 중 | Skeleton 또는 Loading 표시 |
| 조회 결과 없음 | 공통 Empty State |
| 페이지 조회 실패 | 공통 Error State |
| 짧은 작업 성공·실패 | Toast |
| 입력값 오류 | 입력창 아래 오류 메시지 |
| 중요한 확인·경고 | Modal |
| 로그인이 필요한 기능 | 안내 후 로그인 화면 이동 |
| 버튼 요청 진행 중 | 버튼 Loading + 중복 클릭 방지 |
- 오류 내용을 Console에만 표시하고 끝내지 않는다.
- Loading 중 동일 요청이 중복 실행되지 않도록 한다.
- 사용자가 다시 시도할 수 있는 경우 재시도 버튼을 제공한다.

## 8. 입력 및 폼 규칙

- 필수 입력과 형식 오류는 입력창에서 벗어날 때 확인한다.
- 제출 시 전체 항목을 다시 검증한다.
- 오류 메시지는 해당 입력창 가까이에 표시한다.
- 서버 검증 오류와 프론트 검증 오류의 문구를 가능한 한 통일한다.
- 제출 중에는 버튼을 비활성화하고 Loading 상태를 표시한다.
- 동일한 제출 요청이 여러 번 전송되지 않도록 한다.
- Label 없이 Placeholder만으로 입력 의미를 전달하지 않는다.

## 9. 스타일 코드 규칙

- 컴포넌트별 스타일은 기본적으로 `scoped`를 사용한다.
- 공통 색상, 여백, Radius, 높이는 CSS 변수로 관리한다.
- 같은 디자인 값을 화면마다 직접 하드코딩하지 않는다.
- 인라인 스타일은 위치나 크기가 실시간 계산되는 경우에만 사용한다.
- `!important`는 원칙적으로 사용하지 않는다.
- 클래스 이름은 kebab-case로 작성한다.
- JavaScript로 처리할 필요가 없는 Hover와 Focus는 CSS로 구현한다.
- UI 프레임워크나 CSS 라이브러리를 새로 추가하기 전에 팀원과 합의한다.

```
/* 권장 */
.product-card {
  color: var(--color-text-primary);
  border-radius: var(--radius-card);
}

/* 지양 */
.product-card {
  color: #171815;
  border-radius: 13px !important;
}
```

## 10. Import 규칙

- `src` 내부 다른 영역을 가져올 때는 `@/` 별칭을 기본으로 사용한다.
- 같은 폴더의 가까운 파일은 상대 경로를 허용한다.
- 타입 Import는 `import type`으로 구분한다.

```
// 1. Vue
import { computed, ref } from 'vue'

// 2. 외부 라이브러리
import axios from 'axios'

// 3. 프로젝트 내부 파일
import BaseButton from '@/components/base/BaseButton.vue'

// 4. 타입
import type { Product } from '@/types/product'
```

## 11. 환경 변수 규칙

- API 주소와 실행 환경별 값은 환경 변수로 관리한다.
- Vite에서 사용하는 클라이언트 환경 변수는 `VITE_`로 시작한다.
- 비밀번호, DB 정보, 비밀 API 키는 프론트 환경 변수에 저장하지 않는다.
- 실제 환경 파일은 Git에 올리지 않는다.
- 팀에는 `.env.example`만 공유한다.

```
VITE_API_BASE_URL=http://localhost:8080
```
