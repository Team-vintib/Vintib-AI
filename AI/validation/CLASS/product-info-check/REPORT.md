## ⚠️ 가장 먼저 읽을 것 — 이 보고서의 증거 등급

이번 세션에서 **실제 사진 7장**(+ synthetic 1장 제외)에 **실제 모델**(CLIP ViT-B/32, Qwen3-VL-4B-Instruct 4bit, SAM3)을 로컬(RTX 4070 Laptop 8GB)에서 직접 돌려서 얻은 **진짜 숫자**다. Mock이 아니다.

**그러나 N=7은 강한 방향성 신호이지 최종 결론이 아니다.** 이 7장은:
- 대분류 2종(TOP/BOTTOM)뿐 — OUTER/SHOES/BAG/ACCESSORY **0건**
- 촬영유형 전부 `flat`(평면/제품샷) — 착용샷/걸이샷 **0건**
- BOTTOM 4건이 전부 DENIM(다른 소분류 없음)
- 라벨은 Claude(나)가 육안으로 1차 라벨링, **사람 검증 0/7** — 라벨러 간 일치율 계산 불가

아래 모든 수치는 **"방향은 이쪽이다"를 보여주는 파일럿**이지, 정확도를 인용할 수 있는 근거가 아니다. V0(정답셋 40~60건, 6개 대분류·3개 촬영유형·혼동쌍 포함)를 완료하고 이 스파이크를 그대로 재실행하기 전까지는 아래 결론을 "확정"으로 취급하지 말 것.

## 가정 5개 판정 요약

| # | 가정 | 판정 | 근거 |
|---|---|---|---|
| 1 | CLIP/SigLIP zero-shot이 중고 의류 사진에서 쓸 만한 정확도가 나오는가 | **조건부 PASS** | 영어 CLIP 템플릿 top1=71%(규칙 baseline 57% 이김). 단 한글 프롬프트는 완전 실패, SigLIP 미검증 |
| 2 | CPU 추론이 1.5초 안에 들어오는가(품질검수 동시 실행 상태) | **PASS(현실적 부하 기준) / FAIL(최악 부하 기준)** | 실제와 유사한 GPU-bound 동시 부하에서 p95=146ms. 순수 CPU 포화(비현실적 최악)에서는 p95=18.6초 |
| 3 | 이미지만으로 성별 판별 가능한가 | **검증 불요 — 이미 결정됨** | 사용자가 채팅에서 확정: AI가 채우지 않고 사용자가 폼에서 직접 선택 |
| 4 | 자동 채움 임계값이 몇이어야 하는가(초안 0.7 재검토) | **부분 PASS(카테고리) / FAIL(색상)** | 카테고리 score는 정답/오답이 실제로 분리됨(0.74 근방). 색상 confidence는 오답에서도 높게 나와 분리 안 됨 |
| 5 | 색상 k-means+팔레트 스냅이 VLM보다 나은가 | **FAIL** | 설계안 0/7, baseline(평균색)도 0/7 — 동률로 전멸. VLM은 5/7(71%) |

**결론 미리보기**: 이 표본에서는 검증하려던 가정 중 절반 이상이 원안 설계의 기본 결정(CPU zero-shot + 고전 CV 기본, GPU 없음)에 불리하게 나왔다. 특히 가정 5(색상)는 원안이 baseline과 동률로 완전히 밀렸다. 아래 §6 결론에서 대안을 제시한다.

## V1 — 지연 실측

후보: CLIP ViT-B/32(캐시됨, 실측). CLIP ViT-L/14·SigLIP so400m·ONNX 변환본은 **이번 세션 미실행**(로컬 캐시에 없어 각각 ~1.7GB/~3.5GB 신규 다운로드 필요 — 코드는 준비됨, `classify.py`의 `CATEGORY_BACKENDS` 키만 바꾸면 바로 실행 가능).

| 조건 | 설명 | p50 | p95 | load |
|---|---|---|---|---|
| idle | 유휴 상태 | 127~140ms | 143~160ms | 24~27s(1회성) |
| synthetic | CPU N-1코어 100% 인위 포화(순수 파이썬 busy-loop) | **14,939ms** | **18,568ms** | 27.6s |
| external | **실제 Qwen3-VL-4B(4bit) GPU 추론을 50초간 반복(30회) 돌리면서 측정** | **136ms** | **146ms** | 5.1s |

**숫자 → 결정**: `synthetic`(순수 CPU 포화)과 `external`(실제 GPU-bound 부하)의 차이가 100배 이상 난다 — **CH012 §6.3의 우려("SigLIP CPU 1.5초는 quality 동시 실행 상태에서 실측해야 한다")는 부하의 종류에 따라 결론이 완전히 갈린다.** 실제 품질검수(SAM3+Qwen-VL)는 GPU 바운드라 CPU 코어를 많이 점유하지 않는 것으로 보이며, 그 조건에서는 목표(≤1.5s)를 여유 있게 통과한다. **다만 `external` 테스트는 Qwen-VL 생성 루프만 재현했고 SAM3의 CPU측 전/후처리(마스크 렌더링, bbox 계산 등)는 포함하지 않았다** — 진짜 최종 수치는 실제 SAM3+Qwen-VL 워커를 함께 띄운 상태에서 재확인해야 한다(`latency.py`의 `stress_mode="external"` 그대로 사용 가능).

**→ 유지되는 결정**: CPU 기반 classify가 GPU 품질검수와 진짜로 공존 가능하다는 원안의 핵심 전제는, 적어도 이 1차 실측에서는 **살아남았다**.

## V2a — 카테고리(소분류) zero-shot 정확도

백엔드: `clip_vit_b32` (CPU). N=7(실제 사진).

| 템플릿 | 1단계 top1 | 1단계 top3 | 2단계 top1 | 2단계 top3 |
|---|---|---|---|---|
| `kr_plain`("니트") | 0.14 | 0.14 | 0.00 | 0.00 |
| `en_clip_style`("a photo of a knit sweater") | **0.71** | **1.00** | 0.29 | 0.29 |
| `kr_secondhand_flat`("바닥에 펼쳐놓고 찍은 중고 니트 사진") | 0.14 | 0.43 | 0.29 | 0.29 |
| 규칙 baseline(항상 DENIM) | 0.57 | — | — | — |

**숫자 → 결정**:
1. **프롬프트 언어·문구가 결과를 지배한다.** 영어 표준 CLIP 템플릿(0.71)과 한글 라벨(0.14)의 차이가 5배다 — `openai/clip-vit-base-patch32`는 사실상 영어 전용 텍스트 인코더라는 뜻으로 해석된다. **한글 프롬프트로는 규칙 baseline(0.57)도 못 이긴다.** 다국어 CLIP/SigLIP 변형이나 한국어 파인튜닝 버전을 후보에 추가 검토할 것.
2. **1단계가 2단계를 모든 템플릿에서 압도한다**(en_clip_style 기준 0.71 vs 0.29). 애초 가설("라벨 수가 적어지면 2단계가 유리할 것")은 **기각**됐다 — 대분류 1차 판정이 틀리면 정답 소분류가 후보 집합에서 아예 빠지는 오류 전파가, 라벨 수 감소로 얻는 이득보다 크다.
3. 유일하게 규칙 baseline을 이긴 조합(en_clip_style + 1단계, 0.71 > 0.57)만 실사용 후보다.

**→ 결정 변경**: "2단계 분류가 나을 수 있다"는 원안 가설은 **기각**. **1단계 30-way + 영어 프롬프트**로 확정 권고(§6 결론 참고).

## V3 — 색상 추출 정확도

N=7(실제 사진). 대분류가 TOP/BOTTOM뿐이라 BAG/ACCESSORY에서 마스크가 무너지는지는 **이번엔 검증 못함**(V0 확장 후 필수 재검증).

| 백엔드 | 주 색상 정확도 | 비고 |
|---|---|---|
| `kmeans_palette`(설계안, CH012 §6.2 그대로: 중앙크롭+배경색추정+saturation필터+kmeans) | **0/7 (0%)** | 전부 오답 |
| `mean_color`(baseline, 전체 평균) | **0/7 (0%)** | 설계안과 동률로 전멸 |
| `vlm`(Qwen3-VL-4B, 4bit) | **5/7 (71%)** | 압도적 우위 |

실패 사례(설계안, 실제로 관찰된 메커니즘):
- `denim.jpg`/`fix.jpg`: 콘크리트/카펫 바닥이 채도 필터를 통과해 배경색이 그대로 1등 클러스터가 됨(truth=BLUE인데 KHAKI/WINE 출력)
- `small_pro.jpg`(클로즈업 크롭): 상품이 프레임을 꽉 채워 "테두리=배경"이라는 배경색 추정 전제 자체가 무너짐(전경 비율 6%)
- `black_washed.jpg`: 작은 로고/자수(보조색 RED)가 픽셀 수 기준 랭킹에서 밀려 탈락

**숫자 → 결정**: CH012 §2.2("색상은 계산 가능한 값이다")는 **원리적으로는 맞지만, §6.2가 명시한 구체적 마스크 방법(중앙크롭+배경색추정+saturation필터)은 이 표본에서 baseline(평균색)보다 나을 게 없었고 VLM에는 크게 뒤졌다.** 마스크 없는 단순 평균색과 동률이라는 건, 지금 마스크 로직이 "정확도에 기여하는 게 없다"는 뜻이다.

**→ 결정 변경**: 가정 5는 **명확히 FAIL**. 색상은 "VLM에 물으면 폼 select에 못 넣는 값이 나온다"(CH012 §2.2)는 원안의 우려는, 이번에 VLM 프롬프트에 **팔레트 코드 목록을 직접 주고 그 중에서 고르게** 했더니 해소됐다(`vlm_control.py`의 `_COLOR_PROMPT_TEMPLATE`) — VLM이 자유 텍스트로 답하게 두지 않으면 이 우려는 성립하지 않는다.

## V4 — score 분포 → 임계값 캘리브레이션

카테고리(`clip_vit_b32`/`en_clip_style`/1단계) score 분포:

| score 구간 | n | 실제 정확도 | 평균 confidence |
|---|---|---|---|
| [0.4, 0.6) | 1 | 0.00 | 0.55 |
| [0.6, 0.8) | 2 | 0.50 | 0.72 |
| [0.8, 1.0) | 4 | 1.00 | 0.92 |

ECE ≈ 0.19. 오답률 ≤10% 제약 하 권장 임계값 = **0.743**(커버리지 5/7=71%, `low_confidence_warning=True` — N<30이라 자동 플래그됨).

**숫자 → 결정**: score와 정답 여부가 **실제로 분리되는 경향**이 보인다(0.4~0.6구간 정확도 0% vs 0.8~1.0구간 100%) — 임계값 기반 autofill/suggest 분기 자체는 카테고리 필드에서 **성립할 근거**가 있다. 원안의 0.7 가정과 이번 권장값(0.743)이 우연히 비슷하지만, **N=7로 임계값을 확정하면 안 된다** — 표본이 늘면 값이 크게 움직일 수 있다.

색상 confidence(설계안 `kmeans_palette`의 1등 클러스터 비중, baseline `mean_color`의 팔레트 거리 역수)는 **오답에서도 높게 나왔다**(예: `mean_color`가 `denim.jpg`를 KHAKI로 틀렸는데 confidence=0.94). **색상 쪽은 score가 정답 여부와 분리되지 않는다** — 지금 상태로는 색상 필드에 임계값 기반 자동 채움을 걸 근거가 없다.

**→ 결정**: 카테고리는 필드별 임계값(서버 결정, CH012 §5.2와 동일 설계) 방향 유지. **색상은 (a) VLM 백엔드로 바꾸거나 (b) confidence 계산 방식 자체를 재설계하기 전까지는 자동 채움을 걸면 안 된다.**

## V5 — VLM 대조군 + VRAM 실측

모델: `Qwen/Qwen3-VL-4B-Instruct`(4bit, bitsandbytes nf4). N=7.

| 항목 | zero-shot(CLIP) | VLM(Qwen3-VL) |
|---|---|---|
| 카테고리 top1 | 0.71 | **0.86** (6/7) |
| 색상 주색상 정확도 | 0.00(kmeans)/0.00(mean) | **0.71** (5/7) |
| 지연(워밍업 후, 이미지당) | 127~146ms(CPU) | 660~2,595ms(GPU) |

VRAM(fresh process, `torch.cuda.memory_allocated()`):

| 단계 | VRAM |
|---|---|
| baseline | 0 MB |
| + Qwen3-VL-4B(4bit) | 2,776 MB |
| + SAM3(fp16, 동시 적재) | **4,421 MB** |
| GPU 총량(RTX 4070 Laptop) | 8,188 MB |
| 여유 | **3,767 MB** |

**숫자 → 결정**: CH012 §12가 리스크로 명시했던 "노트북 VRAM 미측정" — **측정 완료**. 두 모델을 한 프로세스에 동시 적재해도 8GB 중 4.4GB(54%)만 쓰고 3.8GB가 남는다. 이건 **로드된 가중치 기준**이고 실제 동시 추론 시 activation 메모리가 추가로 붙지만, 배치 크기 1 기준으로는 이 정도 여유면 충분할 가능성이 높다.

정확도도 지연도 VRAM도 전부 VLM 쪽에 유리하게 나왔다 — **CH012 §5의 판정 기준("VLM이 유의미하게 정확한데 지연·VRAM이 감당 가능하면 기본 백엔드 결정을 뒤집어야 한다")에 해당하는 신호가 이미 나타났다.** 다만 N=7(그중 카테고리가 2종류뿐)이므로 "유의미하게"라고 통계적으로 단언하기엔 이르다.

## 6. 결론 — 3가지 필수 질문에 대한 답

### 성별 축을 AI가 채우는가, 사용자에게 넘기는가
**사용자에게 넘긴다.** 검증 전에 이미 사용자가 채팅으로 확정(등록 폼에서 성별을 직접 선택하게 구현). 이 스파이크는 그 결정을 뒤집을 새 증거를 만들지 않았고, 만들 필요도 없었다(V2b를 스코프에서 제외한 이유).

### 1단계 30-way와 2단계 중 무엇을 쓰는가
**1단계.** 실측 결과 모든 프롬프트 템플릿에서 1단계가 2단계를 앞섰고(en_clip_style 기준 0.71 vs 0.29), "라벨이 적어지면 2단계가 유리하다"는 원래 가설은 이 표본에서 명확히 기각됐다.

### 기본 백엔드가 zero-shot인가 VLM인가
**이 표본의 증거는 VLM 쪽을 가리키지만, 이 스파이크 하나로 CH012 §2의 아키텍처 결정(GPU 미사용을 기본값으로)을 뒤집기엔 근거가 부족하다.** 구체적으로:

- 카테고리: VLM이 15%p 더 정확(86% vs 71%)했지만, N=7 중 대분류가 TOP/BOTTOM 2종뿐이라 다른 4개 대분류에서도 이 격차가 유지되는지 모른다.
- 색상: VLM이 71%p 더 정확(71% vs 0%)했다 — 이건 격차가 너무 커서 우연이라 보기 어렵다. **색상만큼은 VLM 백엔드로 바꾸는 걸 강하게 권고한다** (팔레트 코드 목록을 프롬프트에 명시하면 CH012 §2.2가 우려한 "폼에 못 넣는 값" 문제도 해소됨, §V3 참고).
- 지연·VRAM: 실제와 유사한 부하에서 CPU classify가 안 느려졌고(§V1), VLM+SAM3 동시 적재도 VRAM 여유가 있었다(§V5) — **두 우려 모두 이 표본에서는 기우로 나타났다.**

**권고**: 카테고리는 원안대로 CPU zero-shot(1단계, 영어 프롬프트, `clip_vit_b32`나 미검증 후보 `siglip_so400m`/`clip_vit_l14` 중 정식 비교 후 선택)을 유지하되, **색상은 VLM로 백엔드를 바꾸는 것을 다음 설계 개정에 반영할 것을 제안한다.** 다만 이 권고 전체는 **V0를 40~60건으로 확장하고 이 스파이크(특히 V2a/V3)를 그대로 재실행한 뒤 확정**해야 한다 — 지금은 "강한 방향성 신호"이지 "결론"이 아니다.

## 8. 업데이트(2026-08-02) — 정답셋 확장(N=10) + CLIP 색상 zero-shot 대조군

**배경**: 팀이 카테고리는 CLIP 파인튜닝(100~200건), 색상은 그 결과에 따라 CLIP 임베딩+분류
헤드 또는 VLM 파인튜닝으로 갈지 저울질하기 시작했다. 파인튜닝(지도학습)에 들어가기 전에,
**CLIP이 색상에 대해 zero-shot으로라도 뭔가 신호를 갖고 있는지**부터 확인했다 — 지금까지
색상 후보에 CLIP 계열이 아예 없었기 때문이다(고전 CV 2종 + VLM뿐).

정답셋도 8건→11건(실제 사진 7→10)으로 늘었다(`navy_logo.png`/`vintage_t.png`/
`black_stain.png` 추가, `vintage_t.png`가 이 정답셋 최초의 걸이샷).

### 실측(N=10, 실제 사진 전부)

| 색상 백엔드 | 주 색상 정확도 |
|---|---|
| `mean_color`(baseline) | 0/10 (0%) |
| `kmeans_palette`(설계안) | 0/10 (0%) |
| **`clip_vit_b32`(zero-shot, 신규)** | **2/10 (20%)** |
| `vlm`(Qwen3-VL, §V5) | 6/10 (60%, N=7 대비 하락 — §V5 갱신치와 동일 이유, 표본 다양성 증가) |

**숫자 → 결정**: CLIP zero-shot은 고전 CV(0%)보다는 낫지만(20%), VLM(60%)에는 한참 못
미친다. 즉 **CLIP의 사전학습 임베딩 자체가 색상 개념을 어느 정도 담고 있다는 신호는 있지만
(0%가 아니라는 게 그 증거), zero-shot만으로는 실전에 못 쓴다.** 이건 카테고리 zero-shot이
곧바로 71%를 낸 것과 뚜렷이 대비된다 — **색상은 카테고리보다 CLIP에게 훨씬 어려운
문제**라는 뜻이고, 파인튜닝(지도학습 분류 헤드)이 선택이 아니라 필수에 가깝다는 근거가
됐다.

**구현**: `color.py`에 `ClipZeroShotColorExtractor` 추가(백엔드 키: `clip_vit_b32`/
`clip_vit_l14`/`siglip_so400m`) — `classify.py`의 `EmbeddingZeroShotClassifier`를 그대로
재사용(합성, 색상 라벨 텍스트만 바꿔치기). 카테고리·색상이 같은 체크포인트를 쓰면 나중에
이미지 인코더 호출을 한 번으로 합칠 수 있다(파인튜닝 단계에서 두 헤드가 같은 임베딩을
공유하는 구조로 이어질 수 있음 — §9 참고).

### 남은 질문

- 이 20%가 "CLIP 임베딩+학습된 분류 헤드"의 상한을 말해주진 않는다 — zero-shot(텍스트 매칭)
  과 지도학습 분류 헤드는 완전히 다른 메커니즘이라, 헤드를 얹으면 훨씬 오를 수 있다. 이번
  결과는 "제로샷은 부족하다"만 확정한다.
- 색상 프롬프트 문구도 카테고리처럼 여러 개 비교 안 했다(`en_clip_style` 스타일 1개만) — 한
  글/영문, 문구 스타일에 따라 카테고리처럼 편차가 클 수 있으니 다음에 템플릿 3종 비교가
  필요하다.

## 10. VLM 카테고리 프롬프트 엔지니어링 실측(2026-08-02) — 혼동쌍 구분 기준 추가

**배경**: VLM 개별 호출(§7-1 대응) 실측에서 카테고리 top1=0.90(9/10)이 나왔는데, 유일한
오답이 `logo_test.jpg`(T_SHIRT를 HOODIE로) 하나였다. 여기에 `taxonomy.py`의
`CONFUSION_PAIRS`(JACKET/COAT 등 6쌍)와, 실측으로 새로 발견된 혼동쌍(T_SHIRT↔SHIRT —
**`CONFUSION_PAIRS`에는 없던 쌍**)의 구분 기준을 프롬프트에 직접 명시하면 오르는지 실측했다.

### 실측(N=10, 실제 사진 전부, 개별 호출 각 1회)

| 프롬프트 버전 | top1 | 비고 |
|---|---|---|
| v1(기존, 구분 기준 없음) | **9/10 (90%)** | 유일한 오답: `logo_test.jpg`(T_SHIRT→HOODIE) |
| v2(혼동쌍 구분 기준 추가) | 7/10 (70%) | v1 대비 **폴로 셔츠 2건(`small_pro.jpg`/`black_stain.png`)이 새로 SHIRT 오답 |
| v3(v2 + 폴로는 예외적으로 T_SHIRT 규칙 추가) | 9/10 (90%) | 폴로 2건 중 `black_stain.png`만 회복, `small_pro.jpg`는 여전히 SHIRT 오답. `logo_test.jpg`는 이번엔 우연히 정답 |
| v4(v3의 "폴로는 예외" → **단추 길이 기준**으로 교체) | **10/10 (100%)** | `small_pro.jpg`/`logo_test.jpg` 둘 다 정답 — v1의 유일한 오답까지 해소 |

**숫자 → 결정**: v2는 가설("구분 기준을 주면 오른다")을 1차로 반박했다 — "카라+단추=SHIRT"
규칙을 모델이 문자 그대로 적용해 폴로 셔츠(카라·단추가 실제로 있음)를 SHIRT로 오분류했다.
v3(폴로는 예외로 T_SHIRT)은 **"이게 폴로다"라는 개념적 인식에 기대는 규칙**이라 인식 자체가
안 되면 예외가 발동하지 않았다(폴로 2건 중 1건만 회복). **v4는 "폴로 개념을 아는지"가 아니라
"단추가 목 부근에서 끝나는지, 밑단까지 이어지는지"라는 더 저수준·구조적인 시각 기준으로
바꿨다**(사용자 제안) — 크롭 범위와 무관하게 확인 가능한 기준이라 v3보다 강건했고, 이번
표본에서는 v1의 유일한 오답(`logo_test.jpg`)까지 해소해 10/10을 기록했다.

**한계(과신 금지)** — v2/v3에서 지적한 것과 동일:
- **각 버전 1회씩만 측정했다.** `generate_from_image()`가 결정적 디코딩(greedy)을 강제하지
  않아 모델 생성에 샘플링이 섞여 있을 수 있다 — v1→v4 개선분 일부가 프롬프트 효과가 아니라
  순수 실행 노이즈일 가능성을 배제할 수 없다.
- 폴로 표본이 2건뿐이라 "단추 길이 기준이 폴로 일반에 통하는지"조차 표본이 너무 작다.
- 결론을 확정하려면 **(a) 정답셋 확장으로 폴로류·셔츠류 표본을 늘리고 (b) 버전당 여러 번(예:
  3회) 반복 측정 후 다수결/평균으로 비교**해야 한다. N=10 만점(100%)은 특히 우연일 여지를
  열어두고 봐야 한다.

**구현**: `vlm_control.py`의 `CATEGORY_PROMPT_VERSIONS`(`"v1"`/`"v2_disambiguation"`/
`"v3_polo_exception"`/`"v4_button_length"`) — `query_category(image_path,
prompt_version=...)`로 스왑. **`ACTIVE_CATEGORY_PROMPT_VERSION` 기본값을
`"v4_button_length"`로 확정**(2026-08-02, 사용자 확인) — 위 한계(N=10, 1회 측정)는 여전히
유효하니, 정답셋 확장 후 재검증에서 뒤집힐 수 있다는 점은 감안할 것.

### 자기일관성(반복 샘플링) 검증(2026-08-03)

위 "1회만 측정" 한계를 실제로 확인했다 — v4로 이미지당 3회씩 반복 호출(N=10 x 3 = 30콜)해
다수결을 냈다. **결과: 30콜 전부 정답, 이미지 10건 전부 3회 응답이 완전히 일치**(다수결
top1=10/10, 불일치 샘플 0건). 단일 실행의 100%가 샘플링 우연이 아니라는 근거가 됐다 —
이 표본에 한해 v4는 강건하다. (N=10이 여전히 작다는 한계, 정답셋 확장 필요성은 그대로
유효하다.)

## 11. CLIP 색상 zero-shot 프롬프트 앙상블 실측(2026-08-03) — **회귀(악화)**

**배경**: §8에서 CLIP 색상 zero-shot이 20%(2/10)로 나온 뒤, 카테고리 프롬프트 개선(§10)과
같은 방향으로 "단일 문구 대신 템플릿 x 색상 동의어 앙상블(원조 CLIP zero-shot 레시피)을
쓰면 오르는가"를 실측했다. 근접색(WHITE/IVORY/BEIGE, NAVY, GRAY/SILVER, BROWN/KHAKI,
SKYBLUE)에만 동의어 2~3개를 추가하고(`color.py`의 `EN_COLOR_SYNONYMS`), 템플릿 4종
(`_COLOR_ENSEMBLE_TEMPLATES`)과 곱해 임베딩을 평균 냈다(`classify.py`의
`EmbeddingZeroShotClassifier.score_label_groups`).

### 실측(N=10, `clip_vit_b32`)

| 구성 | primary 정확도 |
|---|---|
| 기존(단일 템플릿, 단일 단어) | 0.20 (2/10) |
| 템플릿만 앙상블(4종, 코드당 단어 1개로 동일 — 그룹 크기 대칭) | 0.20 (2/10, 변화 없음) |
| 템플릿 x 동의어 앙상블(동의어 개수 불균형 — 원래 계획대로) | **0.10 (1/10, 악화)** |
| 위와 동일 구성 + 그룹 크기를 3으로 패딩(같은 단어 반복, 대칭화) | **0.10 (1/10, 동일하게 악화)** |

**숫자 → 진단**: 그룹 크기 불균형이 원인이 아니었다(패딩해서 대칭으로 맞춰도 그대로
악화됐다 — 반증됨). **템플릿 앙상블 자체는 무해하지만 무익하다**(20%→20%, 순수 노이즈
범위). 진짜 원인은 **동의어 단어 자체**다 — 기존엔 GRAY/NAVY/SILVER 쪽으로 쏠리던 오답이
동의어를 추가한 뒤로는 IVORY로 쏠림이 옮겨갔다(IVORY가 top1으로 뽑힌 샘플이 0건→4건).
즉 이 표본에서 CLIP 색상 zero-shot은 **특정 무채색·중간톤 라벨로 쏠리는 "끌개(attractor)"
현상이 있고, 어떤 단어를 프롬프트에 넣느냐에 따라 그 끌개가 GRAY↔IVORY 사이를 옮겨 다닐
뿐, 근본적인 시각 신호 부족은 그대로**라는 뜻이다. 카테고리 프롬프트 개선(§10)이 통했던
이유(사진에 실제로 보이는 구조적 특징을 명시)가 색상에는 같은 방식으로 적용되지 않는다.

**→ 결정**: 색상 zero-shot 프롬프트/동의어 엔지니어링(개선안 1·2번)은 **폐기** —
템플릿 앙상블은 무해하지만 효과 없음, 동의어 앙상블은 실측상 명백히 악화. 더 시도하지
않는다. §9에서 이미 합의한 대로 **CLIP 색상은 zero-shot이 아니라 지도학습 분류 헤드로
가는 게 맞다**는 근거가 하나 더 늘었다 — 이번 실측은 그 결론을 뒤집을 여지를 주지 못했다.

**구현**: `classify.py`의 `EmbeddingZeroShotClassifier.score_label_groups()`(범용, 라벨당
여러 프롬프트의 정규화 임베딩 평균 -> 재정규화), `color.py`의 `ClipZeroShotColorExtractor`에
`use_ensemble` 옵션 추가, `COLOR_BACKENDS`에 `clip_vit_b32_ensemble`/`clip_vit_l14_ensemble`/
`siglip_so400m_ensemble` 등록. **회귀 결과가 실측으로 남아있다는 걸 보여주려고 코드는
지우지 않고 그대로 남겨뒀다** — `kmeans_palette`와 같은 취지(실패한 설계도 재현 가능하게
유지, 나중에 같은 시도를 반복하지 않도록).

## 12. VLM 색상 프롬프트 엔지니어링 실측(2026-08-03) — v1→v3, 순정확 개선 실패(whack-a-mole)

**배경**: 카테고리(§10)와 같은 방식으로 VLM 색상 프롬프트(`query_color()`)에 팔레트 코드
시각적 앵커 + 근접색 구분 기준을 추가하면 오르는지 실측했다(색상 개선안 1·2번). 카테고리
때의 교훈("1회만 측정하면 샘플링 노이즈와 구분 안 됨")을 반영해 **이번엔 처음부터 이미지당
3회 반복 + 다수결**로 비교했다.

### 실측(N=10, 이미지당 3회 반복 다수결)

| 프롬프트 버전 | primary 정확도 | 비고 |
|---|---|---|
| v1(기존, 구분 기준 없음) | **7/10 (70%)** | `black_washed.jpg`/`vintage_t.png`는 3회 중 1회씩 다른 답(불일치) — 경계 사례 |
| v2_anchored(근접색 5그룹 구분 기준 추가) | 6/10 (60%) | `vintage_t.png`(카키)가 GRAY로 재현 가능하게(3/3) 오분류 — **새 회귀** |
| v3_khaki_gray(v2 + KHAKI vs GRAY 쌍 추가, "탁하다"라는 개념적 표현을 "옅어도 색조가 남아있으면 KHAKI"라는 저수준 기준으로 교체) | 6/10 (60%) | `vintage_t.png`는 회복(3/3 KHAKI)했지만 **`levis_patch.jpg`(파란 데님)가 새로 불안정해짐**(GRAY 2/3) — 원래 없던 문제 발생 |

**숫자 → 결정**: v3가 목표했던 오류(카키→회색)는 고쳤지만 순정확도는 v1보다 낮다(70%→60%,
불일치 포함하면 사실상 동률·소폭 악화) — **하나를 고치면 다른 하나가 깨지는 whack-a-mole
패턴**이 카테고리 v2(폴로 회귀)와 똑같이 재현됐다. 다른 점은: 카테고리는 v3→v4로
개념적 기준(폴로 인식)을 구조적 기준(단추 길이)으로 바꾸자 **모든** 오류가 한 번에
풀렸는데, 색상은 저수준 기준(색조 유무)으로 바꿔도 여전히 다른 색 쌍에서 새 오류가
생겼다. **이건 §11(CLIP 앙상블 실패)과 같은 결론을 VLM 쪽에서도 재확인한 것이다** — 색상은
카테고리와 달리 텍스트 기준 명시로 안정적으로 개선되는 문제가 아니다.

**→ 결정**: 색상 VLM 프롬프트 엔지니어링(개선안 1·2번)도 **더 이상 반복하지 않는다**.
`ACTIVE_COLOR_PROMPT_VERSION`은 `"v1"`로 유지한다(v2/v3 모두 실측상 v1보다 낫지 않음).
프롬프트/앙상블 양쪽 다 시도했고 둘 다 순정확도를 못 올렸다는 게 색상 문제의 성격을
말해준다 — 다음은 이미지 전처리(§13) 검증 후 파인튜닝 검토로 넘어간다.

**구현**: `vlm_control.py`의 `COLOR_PROMPT_VERSIONS`에 `"v3_khaki_gray"` 추가, 기본값은
그대로 `"v1"`.

## 13. 입력 이미지 전처리(화이트밸런스 보정) 실측(2026-08-03) — **성공**

**배경**: §11(CLIP 프롬프트 앙상블)·§12(VLM 색상 프롬프트) 둘 다 텍스트 쪽 개선으로는
순정확도를 못 올렸다. §12의 오답들(`WHITE`->`IVORY`, `BLACK`->`GRAY`/`NAVY`)을 보면 공통
패턴이 있다 — 전부 "실제 색보다 조명이 만든 색 편향에 가깝게 답한" 사례다. 그래서 프롬프트가
아니라 **입력 이미지 자체**를 gray-world 가정 화이트밸런스로 보정하면 오르는지 실측했다.

### 실측(N=10)

| 대상 | 원본 | 화이트밸런스 보정 후 |
|---|---|---|
| VLM(v1 프롬프트, 3회 다수결) | 7/10 (70%, 경계 사례 2건 불일치) | **9/10 (90%, 3회 다수결로 재확인)** |
| CLIP zero-shot(`clip_vit_b32`) | 2/10 (20%) | 3/10 (30%, 소폭 개선) |
| VLM 카테고리(v4, sanity check) | 10/10 | 10/10(변화 없음 — 부작용 없음 확인) |

**VLM 기준 고쳐진 사례**: `black_washed.jpg`(GRAY->BLACK), `logo_test.jpg`(IVORY->WHITE),
`vintage_t.png`(GRAY->KHAKI) — 전부 3회 다수결로 재확인된 안정적인 개선. 유일하게 남은
오답은 `black_stain.png`(여전히 NAVY, 정답 BLACK) — 검은 옷이 화면 대부분을 차지해
"장면 평균이 무채색"이라는 gray-world 가정 자체가 깨지는 경우로 보인다(한계로 문서화).

**숫자 → 결정**: 색상 문제의 상당 부분이 **프롬프트가 아니라 입력 이미지의 조명 색 편향**
이었다 — §11·§12에서 텍스트 쪽으로 아무리 고쳐도 못 올리던 걸 픽셀 전처리 한 줄이
올렸다. **`vlm_control.query_color()`에 `apply_white_balance=True`를 기본값으로 추가**했다
(`color.gray_world_white_balance()`). 카테고리(v4)는 이미 포화 상태라 이 보정으로 오르진
않았지만 부작용도 없어(10/10 유지) 색상 경로에만 적용해도 안전하다.

**한계**: (a) gray-world는 장면 지배색이 실제로 무채색 근처일 때만 성립하는 가정이라
`black_stain.png` 같은 반례가 이미 나왔다 — 더 정교한 화이트밸런스(예: white-patch,
학습 기반)로 개선 여지가 있다. (b) N=10, 검증셋 확장 전까지 과신 금지는 계속 유효하다.
(c) CLIP은 개선폭이 작아(20%->30%) 이 전처리만으로 zero-shot 한계를 넘지는 못한다 —
§9의 파인튜닝 필요성 결론은 CLIP 쪽에는 여전히 유효.

**다음 단계**: 사용자와 합의된 순서대로, 프롬프트(§10~§12)·전처리(§13) 모두 시도해본
뒤 파인튜닝을 검토한다 — 색상은 이번 전처리 결과 덕분에 "VLM + 화이트밸런스 보정"이
지도학습 파인튜닝 없이도 실전에 쓸 만한 후보가 됐다(90%, N=10 기준).

## 14. 대분류(depth 2, 6종) 단독 분류 실측(2026-08-03) — CLIP 회귀, VLM 완벽

**배경**: 소분류(30종) 대신 대분류(OUTER/TOP/BOTTOM/SHOES/BAG/ACCESSORY) 6종만 분류하면
후보가 훨씬 줄어드니 CLIP도 잘하지 않을까 싶어 실측했다. `classify.classify_major_only()`
(CLIP, `en_clip_style`)와 `vlm_control.query_major_category()`(VLM, OUTER/TOP·BAG/ACCESSORY
구분 기준 포함)를 새로 추가해 비교했다(`major_category_and_color_check.ipynb`, 새 노트북).

### 실측(N=10)

| 백엔드 | 대분류 top1 |
|---|---|
| CLIP(`clip_vit_b32`/`en_clip_style`) | **0.20** — 소분류(0.71~0.90)보다 오히려 낮다 |
| VLM(Qwen3-VL, 대분류 구분 기준 프롬프트) | **1.00** |

**숫자 → 진단**: 예상과 반대로 **CLIP은 후보를 줄였는데 더 나빠졌다.** 오답을 보면
거의 전부 `OUTER`로 쏠려 있다(10건 중 8건이 예측=OUTER, 그중 6건은 실제로 TOP인데
0.7~0.9라는 높은 점수로 OUTER를 골랐다). 색상 zero-shot에서 봤던 "특정 라벨로 쏠리는
끌개(attractor)" 현상과 같은 패턴이다 — `"a photo of outerwear"`처럼 포괄적인 대분류
단어가, 소분류의 구체적인 단어(`"a photo of a denim jeans"` 등)보다 CLIP 임베딩 공간에서
오히려 덜 구별되고 더 자주 이기는 것으로 보인다. **즉 CLIP zero-shot은 "범주를 넓게
잡을수록 쉬워진다"는 직관이 반대로 작동한다** — 구체적인 단어 목록(소분류)을 그대로
쓰는 게 CLIP에게는 더 유리하다.

**→ 결정**: CLIP을 쓸 거면 대분류로 내려서 단순화하지 말고 지금처럼 소분류 30-way
zero-shot을 그대로 쓰는 게 낫다(대분류는 `major_of(subcategory)`로 사후 계산하면 된다).
VLM은 대분류 6-way에서 10/10으로 완벽했다 — 다만 이미 소분류 30-way에서도 v4로 10/10을
찍은 전례가 있어서 "쉬워서 당연한 결과"에 가깝다.

### 검증 — CLIP은 소분류로 물어서 대분류로 역산하면 어떤가(2026-08-03, 사용자 제안)

위 권고를 그대로 실측했다: CLIP에게 소분류 30-way(`classify_one_stage`, `en_clip_style`)로
묻고, 사용자에게는 `major_of(예측 소분류)`로 역산한 대분류만 보여주는 방식.

| 방식 | 대분류 top1 |
|---|---|
| CLIP 직접 대분류 질의 | 0.20 |
| **CLIP 소분류 질의 -> `major_of()` 역산** | **1.00** |

소분류 자체는 10건 중 3건 오답(T_SHIRT를 SHIRT로)이었지만, **셋 다 같은 대분류(TOP) 안의
오답이라 역산 결과에는 전혀 영향이 없었다** — 대분류 판정만 필요하면 소분류 정확도가
100%일 필요도 없고, "혼동쌍이 같은 대분류에 속하는가"만 중요하다는 뜻이다(마침
`taxonomy.CONFUSION_PAIRS`에 있는 쌍은 전부 같은 대분류 안에서만 혼동된다 — JACKET/COAT는
둘 다 OUTER, SHOULDER_BAG/CROSS_BAG/TOTE_BAG는 둘 다 BAG). **CLIP으로 대분류가 필요하면
이 방식(소분류 질의 + 역산)을 쓴다** — 검증 완료.

**구현**: `major_category_and_color_check.ipynb` §2-1에 추가. 프로덕션 코드 변경은 없다 —
기존 `classify_one_stage()`/`taxonomy.major_of()`를 조합만 한 것이라 새 함수가 필요 없었다.

## 15. 색상 프롬프트(v2/v3) + 화이트밸런스 결합 재실측(2026-08-03) — 프롬프트는 이제 무의미

|---|---|

| v2_anchored | 7/10 (70%) — 동일 |

`v1`(가장 단순한 프롬프트)로 충분하다** — v2/v3의 추가 문구·유지보수 비용을 들일 이유가
없어졌다.

## 16. 색상 팔레트 스와치 참조 방식 실측(2026-08-03, 색상 개선안 4번) — **회귀**

**배경**: 텍스트로 색 이름을 지시하는 대신, hex 스와치 그리드를 상품 사진과 합성해 VLM이
이미지 대 이미지로 비교 판단하게 하는 방법을 실제로 구현·실측했다(`color.build_swatch_reference()`
+ `vlm_control.query_color_with_swatches()`).

### 실측(N=10, 화이트밸런스 공통 적용)

| 방식 | primary 정확도 |
|---|---|
| VLM v1(텍스트만) + 화이트밸런스 | 7/10 (70%) |
| VLM + 스와치 참조 + 화이트밸런스 | **3/10 (30%)** |

**숫자 → 진단**: 오답이 파란 데님류에 집중됐다(denim/fix/levis_patch/scratch 4건 모두
GRAY/BEIGE로 오분류) — 원래 텍스트만으로는 다 맞히던 항목들이다. 유력한 원인: 상품
사진을 스와치 그리드 폭(320px)에 맞추려고 리사이즈하면서(원본 620x620 → 약 320x320)
해상도가 줄었고, 19칸 스와치가 같은 이미지 안에 빽빽이 들어가면서 모델의 시각적 주의가
분산됐을 가능성이 있다(둘 다 가설, 확정 진단은 아님).

**→ 결정**: 이 방향은 **폐기**한다 — 가장 새로운 아이디어였지만 실측상 명백히 악화됐고,
이미 v1+화이트밸런스(70%, 프롬프트/전처리 중 가장 간단한 조합)가 있는 상태에서 구현
복잡도(이미지 합성)만 추가하는 건 得보다 실이 크다. 재시도한다면 상품 사진을 리사이즈
없이 원본 해상도로 유지하고 스와치를 별도 캔버스로 분리하는 방향이 먼저다.

## 17. CLIP 색상 — 혼동행렬 정식 도입 + content-free 편향 보정 실측(2026-08-03) — **성공**

**배경**: 사용자 질문("CLIP이 색상 구분을 잘 못하는데, 경계값 정책이나 혼동행렬은 정의된
게 있냐")에 대한 감사 결과, **색상 전용 혼동행렬은 지금까지 코드로 만든 적이 없었다**
(카테고리엔 `evaluate.confusion_matrix()`가 있는데 짝이 없었음) — 이번에 `evaluate.
color_confusion_matrix()`로 추가했다. 이 행렬로 CLIP 색상 오답 패턴을 정량적으로 확인한
뒤, 그 패턴에 맞는 보정 기법(content-free 편향 보정)을 새로 적용했다.

### 혼동행렬(N=10, `clip_vit_b32`, 화이트밸런스 미적용)

| 정답 | 오답 예측 분포 |
|---|---|
| BLACK | GRAY 1, NAVY 1 |
| WHITE | GRAY 1, NAVY 1 |
| KHAKI | SILVER 1 |
| BLUE | SILVER 1, SKYBLUE 1, GRAY 1(정답 BLUE 1) |

**진단**: 오답이 GRAY/NAVY/SILVER 세 라벨에 집중된다 — 정답이 무엇이든 이 라벨들 쪽으로
쏠리는 "끌개" 패턴이 행렬로 정량 확인됐다(§14 대분류에서 본 "OUTER 쏠림"과 같은 종류의
현상). 이 라벨들의 CLIP 텍스트 임베딩 자체가 이미지 내용과 무관하게 사전 확률이 높을
가능성이 있다.

### content-free 편향 보정(Zhao et al. 2021, "Calibrate Before Use") 실측

무채색 중립 이미지(RGB 128,128,128)로 각 라벨의 사전 확률을 구해두고, 실제 이미지
점수를 그 사전 확률로 나눠 편향을 상쇄하는 표준 기법을 적용했다(`color.
ClipZeroShotColorExtractor(use_debias=True)`).

| 구성 | primary 정확도(N=10) |
|---|---|
| 기존(단일 템플릿) | 0.20 |
| + 화이트밸런스 | 0.30 |
| + 편향 보정만 | **0.40** |
| + 화이트밸런스 + 편향 보정 | **0.50** |

**숫자 → 결정**: 프롬프트/앙상블/스와치는 전부 실패했는데, **혼동행렬이 알려준 실제
오답 패턴(특정 라벨 쏠림)에 맞춘 보정 기법은 실측상 명확히 통했다** — 0.20에서
0.50으로, CLIP 색상 zero-shot 계열 중 가장 좋은 결과다. `COLOR_BACKENDS`에
`clip_vit_b32_debias`/`clip_vit_b32_wb_debias` 등을 등록했다(`ACTIVE_COLOR_BACKEND`
기본값은 안 바꿨다 — 검증 스파이크 관례상 실측 확정 후에도 사용자 확인 없이 프로덕션
기본값을 못 바꾼다).

**한계**: (a) 여전히 VLM+화이트밸런스(0.90)에는 한참 못 미친다 — §9의 "CLIP은 색상에
지도학습 헤드가 필요하다" 결론을 뒤집을 정도는 아니다. (b) N=10, 편향 사전 확률도 같은
작은 표본에서 구한 거라 표본이 커지면 달라질 수 있다. (c) `use_debias`는 앙상블과
동시에 못 쓴다(이미 폐기된 방향이라 단순화).

**구현**: `evaluate.color_confusion_matrix()`(카테고리 `confusion_matrix()`의 색상 버전),
`color.ClipZeroShotColorExtractor`에 `use_debias` 옵션 + `_compute_debias_prior()` 추가.

## 18. 패션 도메인 특화 체크포인트 후보 선정(2026-08-03) — **실측 대기**

**배경**: §11(앙상블)·§12/§15(색상 프롬프트)·§16(스와치)이 전부 회귀했고, 통한 건
§13/§17의 전처리·편향 보정뿐이다. 카테고리 대분류 직접 질의 0.35(§14), 색상 0.41~0.50에서
막혀 있다. **지금까지 안 건드린 축이 하나 남았다 — 체크포인트 자체다.** `CATEGORY_MODELS`의
기존 후보 4종은 전부 범용(OpenAI CLIP / Google SigLIP)이고, 의류 사진에 특화된 표현을
배운 적이 없다.

### 비교 후보 — 범용 대조군 1 + 패션 특화 3

| 레지스트리 키 | 체크포인트 | 근거 |
|---|---|---|
| `clip_vit_b32` | `openai/clip-vit-base-patch32` | **범용 대조군.** §V2a~§17 모든 실측의 기준선. 없으면 "패션 파인튜닝이 실제로 움직였는가"를 판정할 수 없다 |
| `fashion_clip` | `patrickjohncyh/fashion-clip` | FashionCLIP 2.0. LAION CLIP ViT-B/32 + 패션 상품 80만 건. 모델 카드의 zero-shot weighted macro F1: FMNIST 0.78→0.83, KAGL 0.71→0.73, DEEP 0.58→0.62(베이스 LAION CLIP 대비) |
| `marqo_fashion_clip` | `Marqo/marqo-fashionCLIP` | GCL(카테고리·색상·소재·스타일을 학습 신호로 사용). 자사 벤치마크 recall@1 FashionCLIP 2.0 대비 +22% |
| `marqo_fashion_siglip` | `Marqo/marqo-fashionSigLIP` | 같은 레시피의 SigLIP(ViT-B-16-SigLIP webli) 판, +57%. 공개된 패션 임베딩 중 보고 성능 최고 |

**Marqo 두 모델을 색상에도 거는 이유**: GCL이 색상을 명시적 학습 신호로 썼다고 밝히고
있다. §17에서 CLIP 색상이 막힌 게 "체크포인트가 색상을 안 배워서"인지 "zero-shot 방식
자체의 한계"인지 지금은 구분이 안 되는데, 이 후보가 색상에서도 안 오르면 후자 쪽 근거가
된다(= §9의 파인튜닝/VLM 유지 결론이 굳어진다).

### 실행 방법

**전용 노트북 `fashion_model_compare.ipynb`** 를 위에서부터 실행한다(§14 실측이 끝난
`major_category_and_color_check.ipynb`와 분리했다 — 그쪽은 축이 "대분류 6종 + 색상 기법 +
VLM 대조군"이고 Qwen3-VL 로드가 전제라 GPU가 필요한데, 이 비교는 CLIP 계열만 써서 VLM
없이 돈다).

비교 축을 체크포인트 하나로 고정하려고 정답셋·프롬프트 템플릿(`en_clip_style`)·분류
모드(`one_stage`)·스코어링(코사인 + temperature softmax)은 전 모델 동일하게 뒀다.
재는 것은 세 가지 + 지연:

| # | 테스트 | 지표 |
|---|---|---|
| 1 | 중분류(소분류) 30-way 추론 | `sub_top1` / `sub_top3` |
| 2 | 중분류 → 대분류 역산 | `major_inverted`. **추가 추론 없음** — 테스트 1의 예측을 `major_of()`로 접는다 |
| 3 | 색상 추론 | `color_acc` / `color_acc_wb` (모델당 원본 / 화이트밸런스 2조건) |
| + | 지연 | `benchmark_backend(template_key=en_clip_style, stress="idle")`의 p50/p95/load |

§6 스코어보드가 모델당 한 줄로 정리하고 baseline 대비 `_Δ` 컬럼을 붙인다. §7이
`outputs/report_fashion_compare.json`으로 ECE·임계값 추천·혼동행렬까지 떨군다.

**대분류 6-way 직접 질의는 재지 않는다** — §14에서 범용 CLIP이 0.35로 무너지고 17장 중
12장이 OUTER로 쏠리는 게 확인됐고, 역산(1.00)이 같은 비용에 더 정확해서 직접 질의를 쓸
이유가 없다.

**사전 준비**: `pip install open_clip_torch`(Marqo 두 모델이 `trust_remote_code`로 open_clip
래퍼를 싣는다. 없으면 그 두 개만 스킵되고 나머지는 그대로 돈다) + 체크포인트 다운로드 약 1.5GB.

**구현**: `classify.CATEGORY_MODEL_LOAD_OPTIONS`(모델별 `trust_remote_code`/`feature_api`/
`text_padding`) + `make_embedding_classifier()`(레지스트리 키 → 조립). `EmbeddingZeroShotClassifier`는
`_embed()`로 인코딩 경로를 한 곳에 모으고 forward / `get_*_features()` 두 갈래를 흡수한다 —
**기본값은 기존 경로와 동일해서 §14의 clip_vit_b32 실측(0.35 / 1.00)이 그대로 재현되는 걸
확인했다**(리팩터로 인한 회귀 없음). `color.ClipZeroShotColorExtractor`는 model_id 대신
레지스트리 키를 받도록 바꿨다(로딩 옵션이 두 곳에 갈라지지 않게).
