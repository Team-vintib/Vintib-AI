# VLM 고도화용 데이터 수집 브리핑 (상품 정보 분류: 카테고리 + 색상)

**용도**: 이 저장소 검증 결과를 바탕으로, 별도 환경(맥북)에서 VLM 고도화용 크롤링 데이터를
수집하는 작업에 필요한 컨텍스트를 정리한 문서. 그대로 복사해서 전달해도 되게 작성했다.

**근거**: `.claude/plans/ai/CH012-~2.MD`(설계), `AI/validation/CLASS/product-info-check/REPORT.md`(1차 검증 결과), 이 채팅에서 확정된 BE taxonomy(2026-08-01).

---

## 0. 왜 VLM 데이터를 모으는가 — 검증 결과 요약

실제 사진 7장(작은 표본, 방향성 신호일 뿐 확정 아님)에 CLIP zero-shot과 Qwen3-VL-4B-Instruct를
같이 돌려본 결과:

| 항목 | zero-shot(CLIP, 최적 프롬프트) | VLM(Qwen3-VL-4B) |
|---|---|---|
| 카테고리 top1 | 0.71 | **0.86** |
| 색상 주색상 정확도 | 0.00(k-means+팔레트) / 0.00(평균색) | **0.71** |
| 지연 | CPU 127~146ms | GPU 660~2,600ms |
| VRAM(SAM3와 동시 적재) | — | 4.4GB / 8GB(RTX 4070 Laptop) |

색상은 특히 격차가 커서(0% vs 71%) 원래 설계(고전 CV 색상 추출)를 VLM으로 바꾸는 쪽에
무게가 실렸다. 카테고리도 VLM이 15%p 더 정확했다. **그래서 VLM(Qwen3-VL 계열)의 정확도를
더 끌어올리는 작업(파인튜닝 또는 프롬프트/few-shot 데이터 확충)이 다음 단계로 필요하다.**
지금 저장소의 정답셋은 8건(실제 사진 7건)뿐이라 파인튜닝은커녕 검증용으로도 턱없이 부족하다.

## 1. 모델 구조

- **분류 대상 필드**: 카테고리(소분류 코드, 30종) + 색상(주색상/보조색상). **성별은 AI가 채우지 않는다** — 사용자가 등록 폼에서 직접 선택하기로 이미 확정됨. 브랜드·소재도 이번 스코프 밖(추후 FE와 별도 협의).
- **카테고리 taxonomy**: 3-depth — 성별(depth1, 분류 안 함) × 대분류(depth2, 6종) × 소분류(depth3, 30종). 모델은 **소분류 코드만** 예측한다.

  | 대분류 | 소분류(순서 고정) |
  |---|---|
  | OUTER | JACKET, COAT, CARDIGAN, VEST, HOODIE_ZIP_UP |
  | TOP | T_SHIRT, SHIRT, KNIT, HOODIE, SWEATSHIRT |
  | BOTTOM | DENIM, SLACKS, CARGO_PANTS, SKIRT, SHORTS |
  | SHOES | SNEAKERS, BOOTS, LOAFER, SANDALS |
  | BAG | BACKPACK, SHOULDER_BAG, TOTE_BAG, CROSS_BAG, POUCH |
  | ACCESSORY | HAT, BELT, SCARF, JEWELRY, WATCH, SUNGLASSES |

  최종 `categoryId = f(성별, 소분류)`이지만 이 조합은 BE/폼 통합 단계에서 하니까, **크롤링/라벨링 단계에서는 소분류 코드만 있으면 된다**(성별 라벨은 몰라도 됨).

- **색상 팔레트(잠정, placeholder)** — BE/FE 확정 전이라 이 저장소가 임시로 정의한 값이다. 확정되면 바뀔 수 있으니 **색상 코드 이름 자체보다 "이런 세분화 수준(18종 + MULTI)으로 라벨링한다"는 감각만 참고**할 것: `BLACK, WHITE, GRAY, IVORY, BEIGE, BROWN, KHAKI, NAVY, BLUE, SKYBLUE, GREEN, YELLOW, ORANGE, RED, PINK, PURPLE, WINE, SILVER, GOLD` + 패턴/멀티컬러용 특수값 `MULTI`.

- **후보 아키텍처**:
  - zero-shot: CLIP/SigLIP 이미지·텍스트 임베딩 코사인 유사도 (닫힌 라벨셋 분류에 적합, 학습 불필요)
  - VLM: Qwen3-VL-4B-Instruct(4bit 양자화) — 이미지 + "다음 목록 중 하나만 골라라" 프롬프트 → 생성형 응답을 라벨과 매칭. **지금 데이터 수집은 이 VLM 경로를 개선하기 위한 것.**

## 2. 서비스 흐름

1. 사용자가 상품 사진을 올리면 **두 파이프라인이 동시에** 돈다.
2. **분류 파이프라인**(가벼움, 이번 개선 대상): 카테고리·색상을 판정해 등록 폼의 해당 필드를 **프리필**. 사용자가 수정 가능. score가 낮으면 자동 채움 대신 "제안 칩"만 보여주거나 아예 비워둠(필드별 임계값, 서버가 결정).
3. **품질검수 파이프라인**(무거움, SAM3+Qwen-VL 하자 판정): 별도로 돌고, 로딩 UI로 진행 상황만 보여줌. 사용자는 이 완료를 기다리지 않고 상품 등록을 제출할 수 있음.
4. 성별은 사용자가 폼에서 직접 고른다(이 파이프라인이 만들지 않음).

---

## 3. 파이프라인 (분류 쪽)

```
상품 사진(대표 이미지 1장)
  → (전처리: 리사이즈 등)
  → VLM에 프롬프트로 질의:
      - 카테고리: "다음 소분류 30개 목록 중 정확히 하나만 골라라"
      - 색상: "다음 팔레트 코드 목록 중 주색상/보조색상을 골라라(JSON)"
  → 응답 텍스트를 라벨 목록과 매칭(자유 텍스트라 대소문자/포함관계로 매칭)
  → 필드별 confidence/score → 임계값 판정(자동 채움 / 제안 / 미채움)
  → 폼 프리필
```

**중요**: 색상은 VLM에게 자유 텍스트로 묻지 않는다 — "차콜 그레이 계열의 다크 네이비"처럼 폼
select에 못 넣는 답이 나오기 때문. **반드시 팔레트 코드 목록을 프롬프트에 명시해서 그 중
하나를 고르게** 한다(이 방식으로 실측 71% 정확도가 나왔다).

## 4. 필요한 데이터쌍

### 4.1 최소 요구 스키마 (파인튜닝/few-shot용)

| 필드 | 필수 | 설명 |
|---|---|---|
| `image` | ✅ | 상품 사진 원본(가능하면 고해상도 원본을 보관하고, 학습 시점에 리사이즈) |
| `subcategory_code` | ✅ | 위 30종 코드 중 하나 — **원본 쇼핑몰 카테고리를 그대로 쓰지 말고 이 코드로 매핑**(§5 참고) |
| `primary_color` | ✅ | 위 팔레트 코드 중 하나(또는 `MULTI`) |
| `secondary_color` | 선택 | 뚜렷한 보조색이 있을 때만. 없으면 `null` |
| `shot_type` | 권장 | `worn`(착용샷) / `flat`(평면·제품샷) / `hanging`(걸이샷) — 아래 도메인 갭 문제 때문에 중요 |
| `source_site` | 권장 | 크롤링 출처(사이트별 매핑 테이블 관리에 필요, §5) |
| `source_category_raw` | 권장 | 원본 사이트의 카테고리 텍스트(나중에 매핑을 재검토/보정할 때 필요) |

### 4.2 도메인 갭 — 반드시 고려할 것

CH012 설계 문서와 이번 검증(§0)이 공통으로 지적한 문제: **CLIP/SigLIP도, 지금 쓰는
Qwen3-VL도 전부 "깨끗한 쇼핑몰 스튜디오 사진"에 가까운 데이터로 학습됐다.** 그런데 우리
실제 서비스 입력은 **개인 판매자가 스마트폰으로, 바닥에 펼쳐놓거나 옷걸이에 걸어서, 구김진
채로 찍은 중고 사진**이다. 신상품 쇼핑몰(무신사·지그재그류)만 크롤링하면 이 도메인 갭이
그대로 남는다.

**권장**:
- 가능하면 **중고/리세일 플랫폼**(당근마켓, 번개장터, 중고나라 등)의 상품 사진도 섞을 것 — 실제 서비스 입력 분포에 더 가깝다.
- 신상품 쇼핑몰 사진만 쓸 수밖에 없다면, 최소한 `shot_type`을 라벨링해서 나중에 "제품샷만 잘 맞고 실사용 사진은 못 맞추더라"는 걸 구분해서 평가할 수 있게 할 것.
- 정 안 되면 데이터 증강(배경 교체, 구김 시뮬레이션, 랜덤 크롭/조명 변화)으로 도메인 갭을 좁히는 것도 고려.

### 4.3 커버리지 요구사항

이번 저장소 검증(N=7)은 대분류 2종(TOP/BOTTOM), 촬영유형 1종(flat)에만 몰려 있어서
**검증 근거로도 부족했다.** 수집 데이터는 최소한 이 편향을 반복하면 안 된다:

- **6개 대분류 전부** 포함(OUTER/TOP/BOTTOM은 물론 SHOES/BAG/ACCESSORY도) — 특히 후자 3개는 색상 마스크 로직이 아예 검증된 적이 없다.
- **촬영유형 3종**(착용샷/평면샷/걸이샷) 골고루.
- **혼동되기 쉬운 소분류 쌍**을 의도적으로 다수 포함: `JACKET`↔`COAT`, `CARDIGAN`↔`HOODIE_ZIP_UP`, `HOODIE`↔`HOODIE_ZIP_UP`, `KNIT`↔`SWEATSHIRT`, `T_SHIRT`↔`SWEATSHIRT`, `SLACKS`↔`CARGO_PANTS`, `SHOULDER_BAG`↔`CROSS_BAG`↔`TOTE_BAG`.
- **단색/패턴·프린트/멀티컬러**를 고르게.
- 수량: 검증용 정답셋은 40~60건이면 되지만, **파인튜닝용 학습 데이터는 그보다 한 자릿수 이상 많아야** 의미가 있다(소분류당 최소 수십 건 이상을 목표로 잡을 것 — 30개 소분류 x 대분류별 난이도 고려해서 우선순위 조정).

## 5. 지시사항 — 카테고리 매핑을 직접 설계할 것

**쇼핑몰마다 카테고리 체계가 다르다.** 크롤링한 원본 사이트의 카테고리 라벨(예: "아우터 > 자켓 > 블루종")을 그대로 쓸 수 없고, 위 §1의 우리 taxonomy(대분류 6종, 소분류 30종)로 매핑해야
학습/평가에 쓸 수 있다. **이 매핑 방법 자체를 설계하는 게 이번 작업의 핵심 과제 중 하나다.**
아래는 그 설계 과정에서 반드시 짚어야 할 질문이지, 답을 정해준 게 아니다:

1. **사이트별 카테고리 트리를 먼저 조사할 것.** 사이트마다 대분류/소분류 깊이·이름이 다르다 — 우리 소분류 코드와 1:1로 안 맞는 경우가 훨씬 많을 것이다.
2. **1:N / N:1 매핑을 어떻게 처리할지 정할 것.** 예: 어떤 사이트는 "니트"와 "스웨터"를 하나로 묶는데 우리는 `KNIT`/`SWEATSHIRT`로 나눈다. 반대로 어떤 사이트는 우리보다 더 세분화돼 있을 수도 있다 — 이럴 때 원본 사진을 보고 사람이 재분류할지, 특정 규칙으로 자동 매핑할지 판단이 필요하다.
3. **매핑 테이블을 코드/데이터로 관리할 것** — `(source_site, source_category_raw) -> our_subcategory_code` 형태로 버전 관리 가능하게 만들 것을 제안한다(하드코딩된 if문보다는 별도 매핑 파일/테이블). 우리 taxonomy가 나중에 바뀔 수 있다는 점도 감안(`AI/validation/CLASS/product-info-check/taxonomy.py`의 `TAXONOMY_VERSION` 참고 — 이 저장소도 아직 BE seed 데이터가 커밋되지 않은 상태라 확정본이 아니다).
4. **매핑 신뢰도가 낮은 항목은 표시해 둘 것.** 자동 매핑이 애매한 카테고리(예: "정장 자켓"이 OUTER인지 그냥 TOP 계열 격식복인지)는 `mapping_confidence` 같은 필드로 남겨서, 나중에 사람이 우선 검수할 대상을 구분할 수 있게 할 것.
5. **우리 taxonomy에 아예 없는 카테고리가 나올 수 있다.** 이럴 땐 임의로 가장 비슷한 코드에 욱여넣지 말고, "매핑 불가" 상태로 별도 보관해서 나중에 taxonomy 자체를 확장할지 논의할 근거로 남길 것.
6. 참고용으로 이 저장소의 `taxonomy.py`(코드 목록·순서), `color.py`(팔레트), `REPORT.md`(검증 배경)를 그대로 가져가도 된다 — 이번 대화에 실려 있는 정보와 100% 동일하다.
