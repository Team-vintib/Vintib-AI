# 브랜드 유사도 그래프 고도화 전략

S15P11A108-199 · 설계(`.claude/plans/ai/001-brand-similarity-graph.md`) 이후, 임베딩 소스가
**크롤링 수집 텍스트**로 바뀐 것을 전제로 유사도 산정·구현 스택·FE 전달 방식을 확정한다.

## 1. 배경 / 스코프

티켓 `-199`는 "추천 알고리즘 고도화"지만, 이 문서가 다루는 것은 **브랜드 유사도 그래프
서비스 한 갈래**다. 사용자 로그 기반 개인화 상품·방송 추천은 완전히 별개 서비스이며
`.claude/plans/ai/002-personalized-recommendation-mvp.md`와 `app/recommend/personalize/`에서
독립적으로 다룬다. 두 서비스는 코드도 아티팩트도 공유하지 않는다.

| | 브랜드 유사도 그래프 (이 문서) | 개인화 추천 (002) |
| --- | --- | --- |
| 입력 | 브랜드 서술 텍스트 (유저 무관) | 유저 행동 로그 |
| 계산 시점 | **전부 오프라인** 사전계산 | 요청 시점 온라인 집계 |
| 응답 | 모든 유저에게 동일한 맵 | 유저마다 다른 랭킹 |
| 코드 | `app/recommend/` | `app/recommend/personalize/` |

레퍼런스는 Fruits Family **Brand Radar** — 브랜드를 2D 맵에 배치한 네트워크 시각화다.

### 001 설계로부터의 변경점

001은 임베딩 소스를 "**AI 파트가 직접 큐레이션한** 브랜드 소개·평가 텍스트"로 확정했다.
이번 라운드는 그 소스를 **크롤링으로 수집한 브랜드 역사·아이덴티티 + 커뮤니티 반응 +
우리가 카테고라이즈한 결과**로 확장한다. 분량이 늘고 성격이 섞이는 변경이라, 001이 전제한
"텍스트 하나를 임베딩해서 코사인" 구조로는 처리되지 않는다 — 3장·5장이 그 이유와 대안이다.

## 2. 현재 상태 (코드 기준)

### 2.1 실제 파이프라인

```
[오프라인]  app/recommend/pipeline/build_artifact.py
  brands.yaml (id, name 만)         ← 소개·평가 텍스트 필드 없음
  data/images/<id>/*                ← 이미지 없으면 ValueError 로 중단
      │
      ├─ embed.py        embed_images()  CLIP clip-ViT-B-32   ★ 이미지 임베딩
      ├─ aggregate.py    그룹 평균 → L2 정규화 대표 벡터 1개/브랜드
      ├─ similarity.py   코사인 전체 행렬 → knn_edges(k=8) + top_neighbors(n=50)
      ├─ layout.py       project_2d()  UMAP 시도 → 실패 시 PCA 폴백 → [0,100] 정규화
      └─ artifact.py     meta/nodes/edges/neighbors.json 저장

[온라인]  app/recommend/{router,service}.py   — 표준 라이브러리만, 아티팩트 조회 전용
  GET /recommend/graph?entity=&focus=&k=            (k 기본 10, 최대 50)
  GET /recommend/{entity}/{id}/similar?k=
      아티팩트 없으면 503 / 없는 id 는 404
```

**현재 이 서비스는 503을 반환한다.** `app/recommend/artifacts/`가 존재하지 않고
(`.gitignore:26`), `brands.yaml`도 없다(`.gitignore:28` — 리포에는 `brands.example.yaml`만).
한 번도 아티팩트가 생성된 적이 없다.

### 2.2 구성 요소

| 항목 | 현재 값/방식 | 위치 |
| --- | --- | --- |
| 임베딩 | **CLIP 이미지** `clip-ViT-B-32` | `pipeline/embed.py:10` |
| 브랜드 대표 벡터 | 항목 벡터 **산술 평균** → L2 정규화 | `pipeline/aggregate.py:35` |
| 유사도 | 코사인, 전체 N×N 행렬 | `pipeline/similarity.py:6` |
| 엣지 | kNN `k=8`, `threshold=0.0`, 무방향 dedup(큰 쪽 채택) | `pipeline/build_artifact.py:25` |
| 이웃 목록 | 상위 `n=50` 사전계산 | `pipeline/build_artifact.py:26` |
| 노드 크기 | 항목 **개수**를 8.0~30.0 으로 min-max 스케일 | `pipeline/build_artifact.py:49` |
| 2D 좌표 | UMAP(cosine, `random_state=seed`) → PCA 폴백 | `pipeline/layout.py:10` |
| 저장 | JSON 4파일 (`meta/nodes/edges/neighbors`) | `artifact.py:18` |
| 서빙 캐시 | `lru_cache` 싱글턴 + 프로세스 인메모리 dict | `service.py:37,97` |
| 노드 필드 | `id, name, x, y, size, thumbnail` | `schemas.py:19` |
| 엣지 필드 | `source, target, weight` (raw 코사인) | `schemas.py:28` |

### 2.3 계획(001)과 코드가 어긋나 있다

001에 "⚠️ 텍스트 기반으로 재작성이 필요"로 적혀 있고, **아직 재작성되지 않았다.**

- `embed.py`는 여전히 CLIP 이미지 전용이다. 텍스트 임베딩 함수가 없다.
- `brands.example.yaml`에 `description`/`evaluation` 필드가 없다 — `id`, `name`, `images`,
  `thumbnail`뿐이다.
- `build_artifact.py:65`가 이미지를 못 찾으면 `ValueError`로 중단한다 → **텍스트만으로는
  실행 자체가 불가능**하다.
- `requirements-pipeline.txt`에 `torch`/`sentence-transformers`/`Pillow`(CLIP용)가 남아 있다.

반면 **텍스트 임베딩 함수는 이미 리포에 있다** — `pipeline/embed_catalog.py:55`의
`embed_texts()`가 `kanana-nano-2.1b-embedding`으로 L2 정규화 임베딩을 만든다. 개인화(002)용으로
쓰이고 있을 뿐이고, 브랜드 그래프가 재사용할 수 있다(5.5 참고).

## 3. 개선이 필요한 지점

### 3.1 세 성격의 텍스트를 한 벡터로 평균하면 축이 붕괴한다 (핵심)

`aggregate.py`는 브랜드에 속한 모든 항목 벡터를 **산술 평균**해 대표 벡터 1개로 만든다.
이미지에서는 타당했다(같은 브랜드 상품 사진들의 중심). 그런데 크롤링 텍스트는 성격이 다른 것이
섞인다:

| 텍스트 종류 | 유사도의 의미 |
| --- | --- |
| 브랜드 역사·아이덴티티 | **계보적 유사** — 같은 뿌리/철학/시대 |
| 커뮤니티 반응 | **수용적 유사** — 같은 사람들이 좋아하고 같이 언급함 |
| 카테고라이즈 결과 | **분류적 유사** — 같은 태그를 우리가 붙였음 |

이 셋을 평균하면 세 축이 하나로 뭉개져서, "왜 유사한가"를 말할 수 없고 축을 바꿔 볼 수도 없다.
계보적으로는 무관하지만 커뮤니티에서 같이 소비되는 브랜드 쌍(그래프에서 가장 흥미로운 관계)이
평균에 희석돼 사라진다. **평균 풀링은 이 데이터에 맞지 않는다** — 5.1의 다면(faceted) 벡터가 대안이다.

추가로, 브랜드 역사 문서는 길다. `embed_texts()`의 `max_length=512`(`embed_catalog.py:59`)로는
잘린다 — 청킹 또는 장문 지원 모델이 필요하다(5.5).

### 3.2 절대 코사인 임계값이 아무것도 걸러내지 못한다

`knn_edges(threshold=0.0)`이 기본값이다. 밀집 문장 임베딩은 **이방성(anisotropy)** 때문에
임의의 두 문장도 코사인이 높은 좁은 양수 대역에 몰리는 것으로 알려져 있다. 그 경우 `0.0`은
어떤 엣지도 제거하지 않고, 모든 노드가 정확히 `k=8`개 엣지를 갖는 **균질한 그래프**가 된다.

시뮬레이션으로 결과를 확인했다(실제 임베딩이 아니라 공통 성분을 섞은 합성 벡터 30개, N=30, k=8):

| | 등방 벡터 | 공통 성분 큼(이방성 모사) |
| --- | --- | --- |
| 코사인 범위 | -0.160 ~ 0.181 | **0.870 ~ 0.926** |
| 음수 코사인 비율 | 54.7% | **0.0%** |
| 엣지 수 (threshold 0.0 / 없음) | 141 / 142 | **174 / 174 — 동일** |
| 엣지 weight 폭 | 0.175 | **0.027** |

두 가지가 동시에 문제다. (1) 임계값이 무의미해진다. (2) `weight`가 0.899~0.926 폭 0.027에
갇혀서, FE가 이 값을 선 굵기·투명도에 그대로 매핑하면 **모든 엣지가 똑같이 보인다.**

> 우리 데이터에서 kanana/bge-m3의 실제 코사인 분포는 **아직 측정하지 않았다.** 시드셋을
> 만들면 가장 먼저 재야 할 값이다(3.7). 위 표는 "그 대역이 좁을 때 무슨 일이 생기는가"를
> 보인 것이고, 대응책(5.2·5.4)은 분포를 측정한 뒤 확정한다.

### 3.3 "특정 기준" 유사도를 표현할 구조가 없다

유사도가 코사인 하나뿐이다. "아메카지끼리", "80년대 브랜드끼리", "같은 가격대끼리"처럼
명시적 기준으로 유사도를 잡거나 가중할 수 없다. 더 근본적으로, **노드에 카테고리 필드 자체가
없다**(`schemas.py:19` — `id/name/x/y/size/thumbnail`). 우리가 카테고라이즈한 결과를
아티팩트에 실을 자리가 없어서, FE는 클러스터별 색상 구분조차 할 수 없다. 5.3이 대안이다.

### 3.4 focus 서브그래프에 엣지 없이 떠 있는 노드가 생긴다 (코드 확인)

`build_artifact.KNN_K = 8`인데 `router.get_graph`의 `k` 기본값은 **10**이다. `service.get_graph`는
`neighbors.json`(상위 50 저장)에서 상위 `k`개를 노드로 넣고, 엣지는 **양 끝이 모두 `keep`에 있는
기존 kNN 엣지만** 남긴다(`service.py:64-71`). 9·10번째 이웃은 focus의 top-8 밖이므로, 상대방의
top-8에 focus가 들어 있지 않으면 **엣지가 없다.**

위 시뮬레이션에서 focus 30개에 대해 `k=10` 요청 시 **평균 1.3개 노드가 엣지 없이 떠 있었다**
(등방 39개/30, 이방성 38개/30 — 벡터 분포와 무관하게 재현). FE에는 "이유 없이 떠 있는 점"으로
보인다. `k > KNN_K`인 모든 요청에서 발생하고, `k`는 최대 50까지 허용된다.

### 3.5 UMAP 레이아웃은 한 번도 실행된 적이 없다

`layout.py`는 UMAP 우선·PCA 폴백인데, 로컬 `.venv`에 `umap`이 설치되어 있지 않다(`torch`,
`transformers`, `sentence-transformers`도 없다). `import umap`이 실패하면 조용히 PCA로
떨어진다(`layout.py:17-26`) — **실제 경로는 항상 PCA였다.** 고차원 정규화 벡터의 상위 2개
주성분이 설명하는 분산은 보통 작아서, 맵이 뭉치거나 축이 해석 불가능해질 수 있다.

UMAP을 설치해도 문제가 남는다. `project_2d`가 `n_neighbors`를 넘기지 않아 기본값 15가 쓰이는데,
브랜드 수십 개 규모에서는 **데이터의 절반이 이웃**이 되어 지역 구조가 사라진다.

그리고 더 근본적인 불일치: **좌표는 벡터에서, 엣지는 kNN에서 각각 다른 목적함수로 계산된다.**
UMAP은 엣지를 최소화 대상으로 삼지 않으므로, 굵은 엣지로 연결된 두 노드가 화면에서 멀리
떨어져 그려질 수 있다. 맵의 신뢰도를 직접 깎는다(6.1이 대안).

### 3.6 노드 크기가 "우리가 얼마나 많이 썼는지"를 나타낸다

`_node_sizes(counts)`는 브랜드별 **항목 개수**를 크기로 매핑한다(`build_artifact.py:49`).
이미지에서는 "상품 사진이 많다"는 약한 인기 신호였지만, 텍스트로 바뀌면 `counts`는 **크롤링한
문서 조각 수** = 큐레이션 분량이다. 위키 문서가 긴 브랜드의 원이 커진다. 사용자가 크기를
인기·거래량으로 읽을 것이므로 **오해를 유발하는 지표**다. 실제 신호(등록 상품 수, 낙찰 건수,
조회수)로 바꾸거나, 없다면 크기를 균일하게 두는 편이 낫다.

### 3.7 품질 지표가 0건이다

라이브 댓글은 `-196`에서 recall/precision을 실측했고 `-197`이 그 수치를 우선순위로 전환했다.
브랜드 그래프에는 **정답셋도 지표도 측정 코드도 없다.** 임베딩 모델을 바꾸거나 가중치를
조정해도 좋아졌는지 말할 수 없다. `test/model_selection/recommendation_benchmark.py`에
Recall@K/Precision@K/NDCG@K 구현이 이미 있으므로, 필요한 것은 정답셋이다.

### 3.8 서빙이 아티팩트를 다시 읽지 않는다

`get_recommend_service`는 `lru_cache` 싱글턴이고, 로드한 아티팩트를 `self._cache` dict에
영구 보관한다(`service.py:37,50`). 무효화 경로가 없다 → **아티팩트를 재생성해도 실행 중인
서버는 낡은 그래프를 계속 반환한다.** 재배포·재시작이 유일한 갱신 수단이다. 그래프를 주 단위로
재빌드할 계획이면 운영상 걸림돌이다.

### 3.9 thumbnail 경로를 FE가 해석할 수 없다

`build_artifact.py:70`이 thumbnail을 **파이프라인 `data/` 기준 상대경로**로 저장한다
(예: `images/kapital/0.jpg`). `app/main.py`는 `/results`만 정적 마운트하며 `data/`는 노출하지
않고, 그 디렉터리는 `.gitignore` 대상이라 배포 이미지에도 없다. FE가 이 문자열을 받아도
**연결할 대상이 없다.** 브랜드 로고를 어디서 서빙할지 결정이 필요하다(6.2).

### 3.10 크롤링 데이터 자체의 리스크

코드 문제가 아니라 데이터 문제다. 파이프라인 설계 전에 정해야 한다.

- **저작권·robots.txt** — 커뮤니티 게시글·매거진 기사 원문을 그대로 저장·재배포하면 문제가
  된다. 원문 대신 **파생 요약/집계만** 보관하는 편이 안전하다(4.2와 같은 결론).
- **PII** — 커뮤니티 반응에는 작성자 닉네임·계정·거래 내역이 섞인다. 수집 단계에서 제거한다.
- **홍보 문구 노이즈** — 브랜드 공식 소개문은 모든 브랜드가 "장인정신", "타임리스"를 말한다.
  변별력이 없는 상투구가 임베딩을 서로 끌어당겨 3.2의 이방성을 악화시킨다.
- **동명이의** — 브랜드명이 일반명사와 겹치면(`Supreme`, `Needles`) 크롤링이 무관한 문서를
  긁는다. 수집 시 도메인 화이트리스트 + 브랜드명 문맥 검증이 필요하다.
- **시점 편향** — 커뮤니티 반응은 수집 시점의 유행에 쏠린다. 최신 몇 달만 긁으면 지금 뜨는
  브랜드끼리 붙는다. 수집 기간을 고정하고 `meta.json`에 남겨 재현 가능하게 한다.

## 4. 데이터 수집·정제 설계

### 4.1 3계층(facet) 텍스트 스키마

브랜드마다 성격별로 **분리된 텍스트 필드**를 유지한다 — 합치는 시점은 임베딩 이후다(5.1).
`brands.yaml`을 다음 구조로 확장한다.

```yaml
- id: kapital
  name: KAPITAL
  # --- facet 1: 역사·아이덴티티 (위키/브랜드 공식/매거진 크롤링 → LLM 정규화)
  identity: |
    1984년 일본 오카야마 코지마에서 설립. 창립자 히라타 토시키요.
    인디고 염색과 보로(襤褸)·자시코 자수 등 일본 전통 기법을 워크웨어에
    결합한 것이 정체성. 대표 아이템은 켄디 재킷, 보로 패치워크 데님.
  # --- facet 2: 커뮤니티 반응 (커뮤니티/리셀/리뷰 크롤링 → LLM 집계)
  reception: |
    실착 평은 오버사이즈·독특한 패턴을 즐기는 층에 호평. 가격대가 높아
    입문 난도가 있다는 언급이 반복됨. 비슷한 결로 45R, 비즈빔이 함께 거론된다.
  # --- facet 3: 카테고라이즈 결과 (우리가 붙인 라벨 — 벡터가 아니라 별도 축)
  tags: [아메카지, 워크웨어, 일본, 인디고]
  era: 1980s
  origin: JP
  price_tier: high
  # --- 표시용
  logo: https://<cdn>/brands/kapital.png
  # --- 재현성
  sources:
    - {url: "https://...", type: wiki, crawled_at: "2026-07-26"}
```

`identity`/`reception`은 **원문이 아니라 정규화된 서술**이다(4.2). `tags`/`era`/`origin`/
`price_tier`는 **임베딩에 넣지 않는다**(4.3).

### 4.2 크롤링 원문 → LLM 정규화

원문을 그대로 임베딩하면 3.10의 노이즈·PII·저작권 문제를 전부 벡터 공간으로 들여온다.
중간에 정규화 단계를 둔다.

```
크롤링 원문(도메인 화이트리스트, robots.txt 준수)
   → 중복 제거 · PII 마스킹 · 브랜드명 문맥 검증(무관 문서 폐기)
   → LLM 정규화: facet별 고정 스키마로 3~6문장 요약 강제
       · identity  프롬프트: 설립 시기/지역/창립자/기법/대표 아이템/계보만. 홍보 형용사 금지.
       · reception 프롬프트: 반복 등장하는 평가 축 + 함께 언급된 브랜드명. 개별 게시글 인용 금지.
   → brands.yaml 커밋 대상 아님(.gitignore:28) · 원문은 리포 외부 보관
```

- 오프라인 배치이므로 **비용·지연 제약이 없다.** 레지스트리의 `kanana-1.5-2.1b-instruct`
  또는 외부 API 중 아무 쪽이든 된다.
- "홍보 형용사 금지 / 고정 스키마 강제"가 핵심이다. 상투구를 프롬프트 단계에서 제거하는 것이
  3.2 이방성 완화에 5.2의 후처리보다 더 효과적일 수 있다.
- LLM 정규화 결과는 **사람이 검수한 뒤 시드셋에 넣는다.** 브랜드 역사에 사실 오류가 섞이면
  그래프 전체의 신뢰를 잃는다. 브랜드 수십 개 규모에서는 전수 검수가 현실적이다.
- `reception`의 "함께 언급된 브랜드명"은 5.3의 공동언급 신호로도 재사용된다 — 정규화 단계에서
  브랜드명 리스트를 **구조화 필드로 따로** 뽑아 두면 두 번 일하지 않는다.

### 4.3 카테고라이즈 결과는 벡터에 넣지 않는다

`tags: [아메카지, 워크웨어]`를 텍스트에 이어 붙여 함께 임베딩하는 것이 가장 쉬운 길이지만
권하지 않는다.

- 태그는 **이미 이산적이고 정확한 신호**다. 임베딩을 거치면 "아메카지"와 "워크웨어"의 거리가
  모델의 사전 지식에 좌우되어, 우리가 의도한 분류 경계가 흐려진다.
- 태그를 벡터에 녹이면 태그 기여도를 **끌 수도 조절할 수도 없다.** "태그 무시하고 서술만으로
  본 유사도"를 볼 수 없게 된다.
- 태그는 Jaccard 같은 집합 유사도로 직접 계산하는 것이 정확하고 설명 가능하다(5.3).

태그는 임베딩 밖의 **독립 축**으로 두고, 하이브리드 스코어에서 가중 결합한다.

## 5. 유사도 설계 — 무엇을 어떻게

### 5.1 다면(faceted) 임베딩 + 가중 결합

facet별로 **따로 임베딩해 따로 보관**하고, 유사도 단계에서 결합한다.

```
identity  텍스트 → 임베딩 → V_identity   (N, D)
reception 텍스트 → 임베딩 → V_reception  (N, D)
                                  │
        코사인 각각 계산 → S_identity, S_reception  (N, N)
                                  │
        S_text = a·S_identity + b·S_reception     (a+b=1, meta.json에 기록)
```

facet 텍스트가 길어 청킹이 필요하면, **facet 내부에서만** 평균한다(같은 성격의 조각이므로
평균이 타당하다). facet 간 평균은 하지 않는다 — 3.1이 그 이유다.

이 구조가 주는 것:

- **축 전환** — `axis=identity|reception|blend` 파라미터로 "계보가 비슷한 브랜드"와 "같은
  사람들이 좋아하는 브랜드"를 갈아 볼 수 있다. 기존 `entity` 파라미터와 같은 패턴이고, 서빙은
  아티팩트 디렉터리만 갈아 읽으면 되므로 **로직 변경이 없다.**
- **설명 가능성** — 엣지마다 어느 facet이 얼마나 기여했는지 알 수 있다 → 6.2의 `reason` 필드.
- **점진적 구축** — `reception` 크롤링이 늦어지면 `identity`만으로 먼저 맵을 낸다.

`aggregate.py`의 `aggregate_by_group()`은 그룹 평균 유틸로서 facet 내부 청크 평균에 **그대로
재사용된다** — `group_ids`에 브랜드 id를 넘기는 방식이 동일하다.

### 5.2 임베딩 공간 후처리 — 이방성 제거

3.2의 좁은 양수 대역을 넓힌다. 셋 다 오프라인 numpy 몇 줄이고, 값싼 순서대로:

1. **평균 중심화** — 코퍼스 평균 벡터를 빼고 재정규화. 공통 성분(모든 브랜드 서술이 공유하는
   "빈티지 의류 브랜드다")을 제거한다. 가장 싸고 효과가 크다.
2. **all-but-the-top** — 상위 d개 주성분 제거(d ≈ D/100). 1의 일반화.
3. **행별 z-정규화** — `z_ij = (s_ij - mean_i) / std_i`. 절대 유사도를 "이 브랜드 기준으로
   유별나게 비슷한가"로 바꾼다. 이방성에 가장 강건하고, **상대 임계값을 쓸 수 있게 해준다**(5.4).

먼저 3.2에 적힌 대로 **실제 분포를 측정**하고, 대역이 좁으면 1 → 3 순으로 적용한다.
어떤 후처리를 적용했는지는 `meta.json`에 기록해 그래프의 재현성을 유지한다.

### 5.3 하이브리드 스코어 — 명시 기준을 결합

`-199` 티켓 원문의 "재랭킹, 협업 필터링 결합"에 대응하는 부분이다. 임베딩 코사인 하나가 아니라
가중합으로 최종 유사도를 만든다.

```
score(i,j) = w_text     · S_text(i,j)              # 5.1 (후처리 후)
           + w_tag      · Jaccard(tags_i, tags_j)  # 카테고라이즈 결과
           + w_comention· PMI_norm(i,j)            # 커뮤니티 공동언급
           + w_meta     · match(era, origin, price_tier)
```

- **`Jaccard(tags)`** — 우리가 정한 분류 경계를 그대로 반영한다. 4.3의 결론.
- **`PMI_norm` (공동언급)** — 커뮤니티 텍스트에서 브랜드 i와 j가 같은 문서에 함께 등장한
  빈도를 정규화 상호정보량으로 만든다. **임베딩이 아닌 유사도 신호**이고, "같이 소비되는
  브랜드"를 직접 잡는다는 점에서 협업 필터링의 아이템 공동출현과 같은 성격이다. 유저 로그가
  없는 지금 얻을 수 있는 가장 협업 필터링에 가까운 신호이며, 4.2 정규화 단계에서 브랜드명
  리스트만 뽑아 두면 계산은 카운팅뿐이다. **비용 대비 가치가 가장 높은 항목으로 본다.**
- **`match(meta)`** — 시대/원산지/가격대 일치 여부. 0/1 또는 거리 기반.
- 가중치는 `meta.json`에 기록한다. 유사도가 왜 그렇게 나왔는지 감사 가능해야 한다.
- 가중치 자체를 API 파라미터로 열지는 **않는다.** 사전계산 아티팩트 구조가 깨지고(요청마다
  행렬 연산), 사용자가 만질 만한 값도 아니다. 프리셋(`axis`)으로만 노출한다.

전부 오프라인이다. **서빙 코드는 이 장을 통틀어 한 줄도 바뀌지 않는다** — 아티팩트만 읽으므로.

### 5.4 엣지 선택 — 상호 kNN + 상대 임계

`threshold=0.0` 절대 임계(3.2)를 버린다.

- **상호(mutual) kNN** — i가 j의 top-k이고 **동시에** j가 i의 top-k일 때만 엣지를 만든다.
  인기 노드가 모두와 연결되는 허브 현상을 줄이고, 엣지에 "서로가 서로를 가깝다고 본다"는
  대칭적 의미를 준다. 현재 `knn_edges`는 한쪽만 만족해도 엣지를 만들고 가중치 큰 쪽을 채택한다.
- **상대 임계** — 5.2의 z-점수 기준으로 자른다(예: `z > 1.0`). 노드마다 엣지 수가 달라지는데,
  그게 옳다 — 실제로 고립된 브랜드는 엣지가 적어야 한다.
- **`KNN_K`와 라우터 `k` 정합** — 3.4의 떠 있는 노드를 없앤다. 둘 중 하나다: `KNN_K`를 라우터
  최대값(50)까지 올려 엣지를 넉넉히 만들고, 아니면 focus 서브그래프에서 **엣지 없는 이웃 노드를
  제외**하거나 focus 직결 엣지를 그 자리에서 합성한다. 후자는 `k`가 이웃 수를 뜻하는 의미가
  유지되므로 더 낫다.
- **렌더용 weight 분리** — `weight`는 FE 표현용으로 0~1 재스케일하고, 원본 코사인은
  `score_raw`로 함께 싣는다(6.2). 3.2에서 폭 0.027이 확인된 문제의 직접 대응이다.

### 5.5 구현 스택 결정

| 단계 | 무엇으로 | 근거 |
| --- | --- | --- |
| 크롤링 | 리포 외부 또는 `pipeline/crawl/`, 원문은 git 미포함 | 저작권·용량(3.10). 서빙과 무관한 오프라인 |
| LLM 정규화 | `kanana-1.5-2.1b-instruct` 또는 외부 API | 오프라인이라 비용·지연 무관(4.2) |
| **facet 임베딩** | **`bge-m3`** 우선, `kanana-nano-2.1b-embedding` 대안 | 아래 참고 |
| 임베딩 호출부 | `embed_catalog.embed_texts()`를 `app/shared/`로 승격 | 이미 텍스트 임베딩 구현체다(2.3). CLAUDE.md가 공용 임베딩 로더 위치로 `app/shared/`를 지정 |
| 후처리·유사도·레이아웃 | numpy (기존 `similarity.py`/`layout.py` 확장) | N=수십~수백에서 O(N²)이 문제되지 않음 |
| 공동언급 PMI | 표준 라이브러리 카운팅 | 모델 불필요(5.3) |
| 저장 | **JSON 아티팩트 유지, pgvector 도입 안 함** | 아래 참고 |
| 서빙 | 기존 `router.py`/`service.py` 그대로 | 아티팩트 조회 전용이라 변경 불필요 |

**임베딩 모델 — `bge-m3`를 권한다.** 001은 `kanana-nano`/`bge-m3` 둘 다 후보로 뒀고
`model_registry.ACTIVE_EMBEDDING`은 `kanana-nano`다. 그런데 브랜드 역사·아이덴티티 서술은
문서 단위로 길고, `embed_texts()`는 `max_length=512`로 자른다(3.1). `bge-m3`는 훨씬 긴
입력을 받으므로 **청킹 없이 facet 문서를 한 번에** 임베딩할 수 있다. `kanana-nano`(2.1B)보다
가볍다는 이점도 있다. 다만 두 모델의 실제 유사도 품질은 우리 브랜드 텍스트로 **비교 측정한
적이 없다** — 3.7의 정답셋을 만든 뒤 Recall@K로 결정한다. 그때까지는 잠정 권고다.

**pgvector를 이번 라운드에서 도입하지 않는다 — 001의 "고도화 -199 = pgvector 이관"을 뒤집는
결정이다.** 근거: pgvector가 해결하는 것은 *요청 시점 벡터 검색*인데, 브랜드 그래프는 유사도·
이웃·좌표를 **전부 오프라인에서 계산**해 조회만 한다(`service.py`에 행렬 연산이 0건). 노드가
수십~수백이라 인메모리 JSON이 더 빠르고 운영 부담도 없다. pgvector가 실제로 필요해지는 것은
요청마다 벡터가 달라지는 **개인화(002)** 쪽이다. 3.8의 아티팩트 갱신 문제는 pgvector가 아니라
리로드 경로로 푸는 것이 맞다.

## 6. FE 전달 및 그래프화

### 6.1 레이아웃을 어디서 계산하는가 — 서버 유지

세 가지 선택지가 있고, **서버 사전계산(현재 방식)을 유지**하되 알고리즘을 바꾼다.

| 방식 | 장점 | 문제 |
| --- | --- | --- |
| **A. 서버 사전계산 x,y (현재·권고)** | 모든 유저·세션에 **동일한 맵**. FE 번들 경량. 재현 가능 | 레이아웃 품질이 오프라인 알고리즘에 종속 |
| B. FE force-directed | 인터랙션(드래그·확장)이 자연스러움 | 로드마다 배치가 달라짐 — "지도"의 정체성이 깨진다. 수백 노드에서 수렴 지연 |
| C. 하이브리드 | 서버 x,y를 초기값으로 FE가 미세 조정 | 안정성 확보하면서 인터랙션 획득. focus 서브그래프에만 제한 적용 |

**A를 고르는 이유는 "지도"이기 때문이다.** 사용자가 두 번째 방문에서 같은 위치에서 같은
브랜드를 찾을 수 있어야 하고, 그러려면 좌표가 서버에서 고정되어야 한다. B는 이 성질을 잃는다.
focus 서브그래프 확장 인터랙션이 필요하면 그 화면에만 C를 쓴다.

**알고리즘은 바꾼다.** 3.5에서 (a) UMAP이 실행된 적 없고 (b) 좌표와 엣지가 서로 다른
목적함수라는 두 문제를 확인했다. 대안:

- **kNN 그래프 위의 force-directed/spring 레이아웃을 오프라인에서 계산**한다(networkx
  `spring_layout` 등, 결정적 seed 고정). 우리가 **그리는 엣지를 그대로 최소화 대상으로**
  삼으므로, 굵은 엣지로 연결된 노드가 실제로 가까이 배치된다 — 좌표와 엣지가 일치한다.
  UMAP처럼 무거운 의존성도 필요 없다.
- UMAP을 유지한다면 `n_neighbors=min(15, N-1)`을 **명시적으로 전달**하고, `umap-learn`을
  실제로 설치해 폴백이 아닌 경로로 검증한다. 미설치 시 조용히 PCA로 떨어지는 동작은
  최소한 로그를 남기게 바꾼다.
- 어느 쪽이든 `meta.json`에 실제 사용된 레이아웃 알고리즘을 기록한다. 지금은 UMAP인지
  PCA인지 아티팩트만 보고 알 수 없다.

### 6.2 확장 응답 스키마

기존 필드를 유지하며 더한다(FE 파괴적 변경 없음). 전부 오프라인 사전계산이라 지연 영향 없음.

```jsonc
// GET /recommend/graph?entity=brand&axis=blend&focus=kapital&k=10
{
  "entity": "brand",
  "axis": "blend",                    // + 축 전환 (5.1)
  "focus": "kapital",
  "meta": {                           // + 맵 해석·재현에 필요한 정보
    "embedding_model": "BAAI/bge-m3",
    "layout": "spring_knn",           // 3.5 — 무엇으로 배치했는지 명시
    "weights": {"text": 0.5, "tag": 0.2, "comention": 0.2, "meta": 0.1},
    "built_at": "2026-07-26T…Z"
  },
  "nodes": [{
    "id": "kapital", "name": "KAPITAL",
    "x": 42.1, "y": 71.8,
    "size": 18.4,
    "size_metric": "product_count",   // + 크기가 무엇인지 (3.6)
    "logo": "https://<cdn>/brands/kapital.png",  // + 절대 URL (3.9)
    "tags": ["아메카지", "워크웨어"],   // + 색상·필터용 (3.3)
    "cluster": 2,                     // + 군집 id (색상 그룹)
    "era": "1980s", "origin": "JP"
  }],
  "edges": [{
    "source": "kapital", "target": "45r",
    "weight": 0.82,                   // 렌더용 0~1 재스케일 (3.2)
    "score_raw": 0.913,               // 원본 유사도 (설명·디버깅)
    "reason": ["identity", "comention"]  // + 어느 축이 기여했는지 (5.1)
  }]
}
```

핵심은 **`reason`**이다. "왜 이 두 브랜드가 이어져 있나"를 툴팁으로 보여줄 수 있고, 이 그래프가
납득되느냐를 좌우한다. 다면 임베딩(5.1)의 부산물이라 추가 계산이 사실상 없다.

`logo`는 **절대 URL**로 준다 — 3.9의 상대경로는 FE가 해석할 수 없다. 브랜드 로고를 어디에
둘지(외부 CDN / BE 정적 / `/results` 유사 마운트 신설) 결정이 필요하다.

### 6.3 렌더링 스택 권고 (FE 스코프)

FE 스택은 Vue 3.5 + TypeScript + Vite다. 노드 수십~수백 + 엣지 수백 규모에서:

- **`cytoscape.js`** — 성숙하고 TS 타입이 있으며, `layout: { name: 'preset' }`으로 **우리가
  보낸 x,y를 그대로** 배치에 사용한다(6.1 A와 정확히 맞물린다). 노드 이미지·툴팁·클릭 이벤트가
  기본 제공된다. 첫 구현으로 권한다.
- **`sigma.js` v3** — WebGL 기반으로 노드 수천 개 이상에서 유리하다. 지금 규모에는 과하다.
- 순수 SVG + d3 — 통제력은 최대지만 히트 테스트·줌·라벨 겹침을 직접 다뤄야 한다.

인터랙션 계약은 이미 있는 두 엔드포인트로 충분하다: 맵 로드는 `focus` 없이 `/graph`,
노드 클릭 시 `focus={id}`로 서브그래프, 사이드 패널은 `/{entity}/{id}/similar`.

**최종 채택은 FE 파트 결정이다.** 이 절은 권고이고, 협의가 필요하면 코드를 고치는 대신
`.claude/requests/fe/`에 요청 문서를 남긴다(루트 CLAUDE.md 규율).

### 6.4 페이로드와 캐싱

- **전체 맵 크기** — N=200, k=8이면 엣지 800~1600개. 4자리 소수 JSON으로 약 100KB 내외,
  gzip이면 훨씬 작다. **MVP 규모에서 LOD·페이지네이션은 필요 없다.** 노드가 1000개를 넘거나
  썸네일을 인라인으로 실을 때 다시 본다. 지금 넣으면 근거 없는 복잡도다.
- **캐시 헤더가 없다.** 아티팩트는 재빌드 사이에 완전히 정적이므로 `ETag` +
  `Cache-Control: public, max-age=…`이 그대로 맞는다. `meta.built_at`을 ETag로 쓰면 된다.
  값싼 개선이고, 3.8의 리로드 경로와 함께 처리하면 무효화까지 일관된다.

## 7. 로드맵 (제안)

**1단계 — 텍스트 파이프라인 실동작 (001 미완 작업 정리)**
`001`이 남긴 "텍스트 기반 재작성"을 끝내 아티팩트를 처음으로 만든다. facet 스키마(4.1)로
`brands.yaml` 확장, `embed_texts()`를 `app/shared/`로 승격, `build_artifact.py`의 이미지 강제
의존 제거(3.10 → `ValueError` 경로), `requirements-pipeline.txt`에서 CLIP/Pillow 제거.
시드 브랜드는 크롤링 없이 **수동 20~30개**로 시작해 파이프라인을 먼저 통과시킨다.
**동시에 코사인 분포를 측정한다**(3.2) — 이후 모든 임계값 결정의 전제다.

**2단계 — 측정 기반 마련**
정답셋(유사 브랜드 쌍 수십 개)을 만들고 `recommendation_benchmark.py`로 Recall@K를 잰다(3.7).
`bge-m3` vs `kanana-nano`를 여기서 결정한다(5.5). 이 단계 없이 3단계로 가면 고도화가
좋아졌는지 말할 수 없다.

**3단계 — 유사도 품질**
5.2 후처리 적용, 5.4 상호 kNN + 상대 임계, `KNN_K`/라우터 `k` 정합(3.4), 렌더용 weight 분리.
레이아웃을 kNN 그래프 spring으로 교체(6.1). 매 변경을 2단계 지표로 재측정한다.

**4단계 — 크롤링 + 다면화**
크롤링·LLM 정규화 파이프라인(4.2) 구축, `reception` facet 추가, 공동언급 PMI(5.3),
`axis` 파라미터. 여기서 그래프가 질적으로 달라진다.

**5단계 — 운영·FE 연동**
아티팩트 리로드 경로(3.8), ETag/캐시(6.4), 노드 크기 실신호 교체(3.6), 로고 서빙 결정(3.9),
FE 그래프 화면 연동(`.claude/requests/fe/`).

순서의 근거: 1·2단계는 **측정 없이는 3단계 이후 판단이 불가능**하기 때문에 앞에 둔다. 4단계의
크롤링은 가장 값이 크지만 공수와 리스크(3.10)도 가장 크므로, 파이프라인이 검증된 뒤로 미룬다.

## 8. 참고 — 이미 확보된 것

고도화에서 손대지 않아도 되는 부분을 명확히 해 둔다.

- **오프라인/온라인 분리가 이미 맞다.** 서빙(`service.py`)에 행렬 연산이 0건이고 표준
  라이브러리만 쓴다. 5장의 유사도 고도화가 전부 오프라인이므로 **서빙 코드는 바뀌지 않는다.**
- **엔티티 추상화가 작동한다.** `EntityType`(brand/seller)로 분기하고 아티팩트가 엔티티별
  디렉터리다. 상점 유사도로 전환할 때 `aggregate`의 `group_ids`만 바꾸면 된다.
- **아티팩트 부재를 503으로 처리한다.** 파이프라인 미실행 상태에서도 앱이 뜨고, 무거운
  의존성이 서빙에 없다 — `AI/CLAUDE.md`의 서빙 경량 규약을 이미 지킨다.
- **재사용 자산** — `embed_catalog.embed_texts()`(텍스트 임베딩), `aggregate_by_group()`(facet
  내부 청크 평균), `recommendation_benchmark.py`(Recall@K/NDCG@K),
  `recommendation-embedding-finetune/`(bge-m3 파인튜닝, 품질이 부족할 때).
- **`axis` 확장이 기존 패턴과 동형이다.** `entity`가 이미 같은 방식(파라미터 → 아티팩트
  디렉터리)으로 동작하므로 새 설계가 아니다.
