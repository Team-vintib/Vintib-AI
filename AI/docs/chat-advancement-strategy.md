# 라이브 댓글 관리 고도화 전략

S15P11A108-197 · 프로토타입 구현(S15P11A108-192)과 정확도 평가(S15P11A108-196) 이후 개선 방향 정리.

## 1. 배경

프로토타입(`AI/app/chat/`)은 모델·BE 계약·RAG 백엔드가 모두 미확정인 시점에 만들었기 때문에,
**완결 파이프라인을 목업으로 세우고 흔들리는 부분을 교체 가능한 경계 뒤로 밀어 넣는 것**이 목표였다.
정확도는 애초에 목표가 아니었다.

그 다음 라운드에서 실제 정확도를 측정했고(`-196`), 어디가 약한지 정량적으로 드러났다. 이 문서는
새로 측정하지 않고 **그 수치를 개선 우선순위로 전환**한다. 측정 방법·전체 결과·오탐/미탐 사례
목록은 `.claude/plans/ai/004-live-comment-moderation-evaluation.md`에 있으므로 여기서 중복
서술하지 않는다.

## 2. 현재 상태 (프로토타입 기준)

### 2.1 실제 파이프라인

```
POST /chat/moderate  (동기 REST — 메시지큐 없음)
    │
    ├─ 1) SpamDetector        규칙: 10초 윈도우 rate-limit + 근접중복(SequenceMatcher)
    │        └ 걸리면 SPAM/HIDE 반환하고 종료
    ├─ 2) AbuseClassifier     사전 문자열 매칭 (임베딩 아님)
    │        └ 걸리면 ABUSIVE/BLOCK 반환하고 종료
    └─ 3) QuestionDetector    정규식(물음표 + 키워드)
             └ 질문이면 QuestionClusterer.add()
                    ★ 임베딩 ①  faq.py:117  embed(질문)  → cluster.vector 저장
                    └ 클러스터 크기 ≥ 2 → REPEATED_QUESTION + 티켓 발급
                           │
                           ▼  BackgroundTasks (응답 이후)
                      Retriever.search(cluster.canonical)
                    ★ 임베딩 ②  faq.py:199  embed(같은 질문)  ← ①과 중복
                           └ 그라운딩 게이트 → AnswerGenerator → AnswerStore
                                  └ 점수 미달이면 아무것도 만들지 않음
```

흔히 가정하지만 **사실이 아닌** 것 세 가지. 다음 설계가 이 오해 위에 얹히지 않도록 명시한다.

- **댓글 입력 뒤에 메시지큐가 있다** → 없다. 동기 REST다. Redis는 `StateStore`/`AnswerStore`
  **스텁으로만** 존재하고 chat 경로에서 쓰이지 않는다(큐 도입 논의는 5.4 참고).
- **분류기가 임베딩 기반이다** → 아니다. `classifier.py`에 `embed` 호출이 0건이고 욕설 사전
  문자열 매칭이다. **임베딩은 반복질문 경로에서만** 계산된다(위 ①②).
- **악성 처리와 반복질문 처리가 병렬 분기다** → 아니다. 순차 **단락 평가**이고, 악성이면 반환
  하므로 질문 게이트에 도달하지 않는다.

### 2.2 구성 요소

| 항목 | 현재 값/방식 |
| --- | --- |
| 악성 분류기 | `rule_based` — 욕설 사전 + 우회패턴 정규화 (`registry.ACTIVE_CLASSIFIER`) |
| 스팸 탐지 | 규칙 — 사용자별 10초 윈도우 rate-limit(4건) + 근접중복(ratio 0.85, 2건) |
| 질문 판별 (B-1) | 물음표 + 키워드 정규식 |

| 근거 검색 (B-3) | `MockRetriever` — 목업 FAQ 6건 + bigram 코사인 |

## 3. 개선이 필요한 지점

### 3.1 악성 판정 정확도 — 사전 어휘의 협소함

악성 recall 16.7%는 기존 baseline(`kor_unsmile` 58.3%)의 약 1/3.5다. 원인은 우회 처리 실패가
아니라 **사전 어휘 자체가 좁은 것**이다 — 우회 변형별 recall이 원문 17.1% · 웃음패딩 19.0% ·
초성체 14.3% · 띄어쓰기 14.3%로 **고르게** 낮다. 우회가 원인이라면 원문 recall만 높아야 한다.
평가셋의 악성 문장 다수("실력은 없네", "양심 있냐", "한심하다", "정떨어진다")가 사전에 없다.

### 3.2 오탐 — 부분 문자열 매칭과 일반명사 충돌

Set B의 함정 정상 8건이 **전부** 오탐이었다. 원인이 두 갈래로 갈린다.

- **부분 문자열 매칭**이 다른 단어의 일부를 잡는다 — `시발점`(시발), `등신대`(등신),
  `닥쳐오는`(닥쳐), `꺼지지 않는`(꺼지)
- **사전 어휘가 일반명사와 겹친다** — `강아지 새끼`, `쓰레기 분리배출`, `죽어라 일하고`

전자는 매칭 방식 문제이고 후자는 사전 구성 문제다. 규칙 기반을 폴백으로라도 남긴다면 둘 다
고쳐야 한다.

### 3.3 우회 패턴 커버리지

정규화가 실제로 값을 하는 축과 그렇지 않은 축이 갈렸다.

| 우회 유형 | 결과 |
| --- | --- |
| 구두점 삽입 (`개.새.끼`) | **3/3 (100%)** — 정규화가 유효 |
| 모음 늘이기 (`시이이발`) | 1/3 |
| 부분 로마자화 (`si발`) | 1/3 |
| 문자 치환 (`s1발`) · 손가락(`ㅗㅗ`) · 사전 미포함(`졸라`) | 각 0/1 |

### 3.4 문맥형 악성 — 구조적 한계

욕설 어휘 없이 수준·외모·능력을 낮추는 문장 6건이 전부 미탐이었다("얼굴이 참 특이하시네요ㅋㅋ",
"이런 걸 파는 사람 수준 알만하다" 등). 어휘 사전 방식으로는 **원리적으로 잡을 수 없다** —
사전을 늘려도 해결되지 않는 종류다.

### 3.5 반복질문 RAG — 검색·생성이 목업/스텁

근거 문서 정확도·침묵 정확도가 100%로 나왔지만, 이는 목업 FAQ 6건에 대한 결과다.
목업 임베더는 문자 bigram 어휘 매칭이라 표현이 겹치지 않으면 근거가 있어도 못 찾는다
(`"재고 남았나요?"` ↔ `"재고 아직 남아 있나요?"` = 0.330으로 임계치 0.35 미달). 답변 생성도
근거 문서를 그대로 반환하는 템플릿이라 문맥에 맞춘 응답이 아니다.

### 3.6 임계치 근거

- 클러스터링 임계치 `0.30`은 최적이 아니다. 스윕 결과 **`0.35`가 recall 손실 없이 precision을
  87.5%→91.3%로 올린다**.
- 그라운딩 임계치 `0.35`는 타 프로젝트에서 차용한 값이라 근거가 약하다. 목업 세트에서는 우연히
  잘 갈랐을 뿐이다.
- 원칙: **임베딩 모델을 바꾸면 임계치를 반드시 다시 스윕**해야 한다. 모델마다 코사인 스케일이
  달라, 같은 문장 세트에서 세 모델은 0.8에서 precision·recall이 둘 다 0.0으로 붕괴했다.

### 3.7 응답 지연 — 병목은 생성이 아니라 전달 경로

티켓이 "반복 질문 응답 지연시간 단축"을 요구하는데, 실측상 판정은 p95 0.01ms이고 목업 생성도
즉시다. **현재 병목은 생성이 아니라 폴링 간격**이다. 생성 LLM을 도입하기 전까지는 전달 경로
전환이 유일한 실질 개선이며, 이는 BE 협의가 필요하다.

### 3.8 다중 워커 정합성

상태가 프로세스 인메모리라 워커가 늘면 도배 판정이 새어 나가고(윈도우가 프로세스마다 갈림)
답변 조회도 실패할 수 있다(생성한 워커와 조회하는 워커가 다름).

### 3.9 파이프라인 중복 연산 — 같은 문장을 두 번 임베딩

2.1의 ①②가 **같은 문장에 대한 임베딩**이다. `QuestionClusterer.add()`가 계산한 결과는
`cluster.vector`에 이미 저장돼 있는데, `service.generate_answer`가
`retriever.search(cluster.canonical, ...)`을 호출하면서 그 문장을 처음부터 다시 임베딩한다.

지금은 bigram 해싱이라 비용이 없다. 그러나 실모델로 바꾸면 **답변 경로의 임베딩 비용이 정확히
두 배**가 된다 — `kanana_nano`의 실측 추론 지연이 mean 991.4ms이므로 약 1초가 그대로 두 번이다.
반복질문이 잦은 방송에서 누적 비용이 커진다.

우선순위 "상" 6건은 **아키텍처 변경 없이 레지스트리 키·상수·매칭 로직·인터페이스만 손대면 된다**.
다만 실모델 교체는 코드가 한 줄이어도 배치 결정이 걸려 있다.

### 4.1 실모델 교체의 숨은 비용 — 서빙 의존성 정책과 충돌

`ACTIVE_CLASSIFIER`를 바꾸는 것 자체는 한 줄이지만, `HuggingFaceClassifier`가 동작하려면
**서빙 프로세스에 torch·transformers가 있어야 한다.** 이는 `AI/CLAUDE.md`의
"서빙 경로(router/service)는 표준 라이브러리·경량 의존성만" 규약과 정면으로 충돌한다.
추가로 모델 로드가 71.9s이고, `docker-compose.yml`의 AI 서비스는 `mem_limit: 1g`이다.

선택지는 셋이고, 결정이 선행돼야 한다.

| 방안 | 장점 | 대가 |
| --- | --- | --- |
| **A. 서빙에 torch 추가** | 구현이 가장 단순(키 1줄) | `requirements.txt`에 torch → 이미지 수 GB, `mem_limit` 상향 필요, 규약 위배 |
| **B. 분류기를 워커로 분리** | 서빙 경량 유지, 기존 워커·Redis 큐 구조(`infra-architecture.md`) 재사용 | 큐 왕복이 생겨 **게시 전 동기 판정(p95 300ms)** 전제가 흔들림 |
| **C. ONNX Runtime 등 경량 런타임** | torch 없이 추론, 메모리·이미지 절감 | 모델 변환·검증 공수, 라벨 스케일 재확인 필요 |

현재 판정 지연이 목표의 3만분의 1 수준(0.01ms vs 300ms)이라 **예산은 충분히 남아 있다** —
실모델 20ms를 얹어도 여유가 크다. 따라서 병목은 지연이 아니라 **의존성·메모리**다. A는 규약을
바꾸는 결정이고 B는 아키텍처 결정이므로, 1단계 착수 전에 이것부터 정해야 한다.

## 5. 파이프라인 최적화 전략

정확도와 별개로, **같은 일을 두 번 하지 않는지**를 본다. 지금은 목업이라 전부 공짜지만 실모델
전환 시 그대로 비용이 된다.

### 5.1 임베딩 1회 계산 후 재사용

3.9의 중복을 없앤다. `Retriever`에 벡터를 직접 받는 경로(예: `search_by_vector(vector, top_k)`)를
열고, `service.generate_answer`가 `cluster.canonical` 대신 이미 가지고 있는 `cluster.vector`를
넘긴다. 답변 경로 임베딩이 2회 → 1회가 된다.

> **불변식**: 이 최적화는 **클러스터러와 retriever가 같은 임베더를 쓴다**는 전제에서만 성립한다.
> 현재는 둘 다 `registry.EMBEDDER_BACKENDS`의 활성 설정 하나를 공유하므로 성립한다. pgvector로
> 넘어가면서 문서 임베딩과 쿼리 임베딩이 다른 모델이 되면 **벡터를 그대로 넘기는 것이 오답을
> 만든다.** 인터페이스에 이 전제를 주석으로 못박고, 다른 임베더를 쓰는 구현은 벡터 경로를
> 지원하지 않도록(명시적 예외) 만든다.

### 5.2 마이크로배치 임베딩

동시에 유입된 댓글을 짧은 윈도우(수십 ms)로 묶어 임베딩을 1회 호출하면 GPU 활용률이 오른다.
단 **답변 경로에만 적용한다** — 판정은 동기라 배치 대기 시간이 그대로 응답 지연이 된다.
답변 생성은 이미 응답 이후로 미뤄져 있어(BackgroundTasks) 배치 지연을 흡수할 여지가 있다.

### 5.3 단락 평가 순서 — 이미 최적

현재 순서는 규칙(스팸) → 사전(악성) → 정규식(질문) → 임베딩(클러스터링)으로 **비용 오름차순**이다.
가장 싼 검사가 가장 먼저 걸러내므로 평균 비용이 최소다. 실모델을 도입해도 이 순서는 유지해야
한다 — 분류기가 20ms가 되면 그 앞의 스팸 규칙이 걸러주는 양이 곧 절약분이다.

향후 순서를 바꿀 때 이 근거를 확인할 것. 예컨대 "질문 먼저 판별"로 바꾸면 도배 댓글까지
임베딩하게 되어 비용이 역전된다.

### 5.4 메시지큐 도입 여부

현재 chat 경로에 큐는 없다. 큐는 독립 결정이 아니라 **4.1의 방안 B를 택하면 필수로 따라오는 것**
이다. 게이트웨이용 Redis 큐 인프라(`infra-architecture.md`)를 재사용할 수 있다.

숨은 비용: **도배 판정은 순서 의존적**이다(사용자별 슬라이딩 윈도우). 큐로 비동기화하면 같은
사용자의 댓글 순서 보장이 필요해지고, 그러려면 사용자 단위 파티셔닝이 있어야 한다. 큐를 넣는
비용에 이 항목을 반드시 포함해서 계산할 것.

## 6. 시멘틱 캐싱 전략

### 6.1 적용 경계 — 판정에는 쓰지 않는다

**리스크가 비대칭이다.** 답변은 캐시가 틀리면 부적절한 답을 주거나 침묵으로 끝나지만, 판정은
캐시가 틀리면 **정상 발언이 차단되거나 악성이 통과한다.** 게다가 어휘가 겹치는 두 문장이 정반대
라벨일 수 있다 — "미친 예쁘다"(정상 속어)와 "미친놈이네"(악성)는 표면이 가깝다.

- **답변 경로 → 시멘틱 캐시 적용**
- **판정 경로 → 정확일치 캐시만** (6.3)

### 6.2 답변 시멘틱 캐시 — 2계층

**L1 세션 캐시 (현재 이미 존재)**
`QuestionClusterer` + `AnswerStore`가 사실상 시멘틱 캐시다. 유사 질문을 하나로 묶어 클러스터당
1회만 생성하고 저장한다. `live_id` 단위 격리를 **유지한다** — "이 방송에서 몇 명이 물었나"를
세는 건 세션 단위여야 하기 때문이다. 이 계층은 바꿀 것이 없다.

**L2 전역 캐시 (신규)**
현재는 방송이 바뀌면 같은 질문도 처음부터 다시 생성한다. "배송 얼마나 걸려요?"는 모든 방송에서
반복되므로 전역 재사용 이득이 크다. 질문 임베딩을 키로, 생성된 답변을 값으로 둔다.

**캐시 키 스코프가 이 전략의 핵심 설계 결정이다.**

| 질문 성격 | 예 | 스코프 |
| --- | --- | --- |
| 상품 무관 | 배송 기간, 교환·반품, 결제 수단 | **전역** 재사용 가능 |
| 상품 의존 | 사이즈, 재고, 가격 | **상품 단위** — 전역에 넣으면 다른 상품의 답을 준다 |

스코프를 구분하지 않고 전역 캐시를 켜면 **지연을 줄이는 대신 오답을 배포하는 기능**이 된다.
지식원(현재 `data/mock_faq.json`)에 `scope: global | product` 필드를 두고, 캐시 키를
`scope == product`일 때 상품 id로 분리하는 방식을 제안한다.

**무효화**: TTL을 기본으로 두고, 상품 정보 변경(재고 소진·가격 변동) 시 해당 상품 스코프를
무효화한다. 변경 감지는 BE 이벤트가 필요하므로 협의 대상이다.

### 6.3 판정 정확일치 캐시

`classifier.normalize()` 결과를 키로 판정 결과를 캐싱한다. 유사도를 쓰지 않으므로 6.1의 위험이
없다. 라이브 채팅은 도배·복붙 비중이 높아 정확일치만으로도 히트율이 상당하다 — 실모델 도입 후
히트 시 20ms → 0ms다. 스팸 탐지가 이미 근접중복을 세고 있어 히트율을 추정할 재료도 있다.

### 6.4 임베딩 캐시

문장 → 벡터를 LRU로 캐싱한다. 5.1이 답변 경로의 중복을 없애는 것이라면, 이것은 방송 전체에서
반복되는 문장의 재계산을 없앤다. numpy 배열은 hashable이 아니므로 문자열 키로 받아 배열을
돌려주는 래퍼가 필요하다(`functools.lru_cache`를 그대로 쓸 수 없다).

### 6.5 측정 지표

캐시는 넣고 나서 효과와 위험을 같이 봐야 한다.

- **히트율** — 계층별(L1/L2/정확일치/임베딩)
- **히트 시 지연 / 미스 시 지연** — 절약분의 실측
- **오답 재사용률** — 시멘틱 캐시의 위험 지표. 캐시가 반환한 답변이 그 질문의 정답 근거 문서와
  다른 비율. 기존 평가 하네스(`evaluation.py`)의 근거 정확도 로직을 캐시 경유 경로에 그대로
  적용하면 측정된다
- **캐시 크기 / 축출률** — 메모리 상한 설계용

### 6.6 구현 위치

기존 경계를 그대로 쓴다. L1은 `AnswerStore` 뒤에서 인메모리로 즉시 가능하고, L2는 프로세스 간
공유가 필요하므로 Redis(`-188`)에 의존한다. 판정 캐시는 `AbuseClassifier` 데코레이터로 감싸면
분류기 구현과 무관하게 동작한다.

## 7. 로드맵 (제안)

**1단계 — 정확도 즉시 개선 + 저비용 최적화 (아키텍처 변경 없음)**
- 오탐 수정: 경계 인식 매칭 + 사전 어휘 정비 → 오탐 8건 해소
- 클러스터링 임계치 0.35로 조정
- 임베딩 벡터 재사용(5.1) — 실모델 전환 전에 넣어야 두 배 비용을 애초에 안 만든다
- 판정 정확일치 캐시(6.3)
- 실모델 배치 방안(4.1 A/B/C) 결정 → 결정된 방식으로 `kcelectra_base_hate` 도입
- 검증: **같은 평가셋으로 재측정**하고 `test_chat_evaluation.py`의 회귀 게이트 하한을 갱신

**2단계 — RAG 실구현**
- pgvector 검색 연동(`-184`), `MockRetriever` → `PgvectorRetriever` 교체
- 임베더 후보 재검토(`kure_v1`)와 **임계치 재스윕**을 같은 라운드에서 수행

**3단계 — 운영 정합성**
- Redis 상태 공유(`-188`) — `StateStore`/`AnswerStore` 구현만 교체
- **L2 전역 시멘틱 캐시(6.2)** — Redis 의존이라 같은 라운드에서. 캐시 키 스코프 설계가 선행
- 답변 전달을 폴링 → 푸시(SSE/WebSocket)로 전환, BE 협의 선행

**4단계 — 품질 고도화 (MVP 이후)**
- 생성 LLM 도입 + 프롬프트 튜닝. 근거 밖 발언을 막는 검증 단계가 함께 필요
- 마이크로배치 임베딩(5.2) — 생성 LLM 도입으로 답변 경로가 무거워진 뒤에 의미가 있다
- 실제 방송 채팅 로그 200~300건 확보 후 분류기 파인튜닝. 현재 평가셋은 합성·수제이므로
  정상:악성 비율(126:84)부터 실측치로 재조정
- 그라운딩 임계치 확정 (CHAT-003)

## 8. 참고 — 구조적으로 이미 확보된 것

`-192`에서 교체 지점을 세 곳으로 고정해 뒀기 때문에, 위 항목 대부분이 **경계 뒤만 바꾸면 적용
된다**.

- **모델·백엔드**: `app/chat/registry.py`의 `ACTIVE_*` 키. 분류기·임베더·retriever·generator·
  상태저장소 다섯 축이 모두 여기서 스왑된다
- **BE 계약**: `app/chat/schemas.py` 한 파일
- **RAG**: `service.get_chat_service()` 팩토리에서 구현체 한 줄

임계치도 전역 상수가 아니라 `registry.EMBEDDER_BACKENDS[key]` 안에 들어 있어, 임베더를 바꾸면
임계치가 따라온다(3.6의 원칙을 코드가 강제한다).

그리고 **평가 하네스와 회귀 게이트가 이미 있다**(`-196`). 개선 후 `python -m
app.chat.pipeline.evaluate`를 다시 돌리면 같은 평가셋으로 개선폭을 즉시 정량 확인할 수 있고,
오탐/미탐 게이트가 부분집합(`found <= KNOWN_*`) 방식이라 **개선하면 자동으로 통과**한다.
