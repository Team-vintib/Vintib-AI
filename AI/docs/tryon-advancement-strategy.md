# 가상 시착 고도화 전략

S15P11A108-195 · 1차 구현(CatVTON 워커 연결, S15P11A108-210) 이후 개선 방향 정리.

## 1. 배경

1차 구현(`worker/tryon_worker_example.py`)은 `worker/models/catvton`의 검증 스크립트(`verify_fit_tryon.py`)를 워커 구조에 그대로 옮긴 것으로, 정확도보다 **파이프라인이 끝까지 도는지(배관 검증)**에 초점을 맞췄다. 고도화는 이 기준으로 나눠서 접근한다.

- **추론 속도**: 현재 스펙 그대로는 요청 1건당 처리 시간이 사용자 대기 경험에 영향을 줄 수준인지 측정이 필요
- **이미지 품질**: 마스크 경계, 원단 질감 보존, 인물 왜곡 여부
- **지원 카테고리 확장**: 현재 `mask_type="upper"`(상의) 고정 — 하의/아우터/원피스 등 확장 필요

## 2. 현재 상태 (1차 구현 기준)

| 항목 | 현재 값/방식 |
|---|---|
| 베이스 모델 | CatVTON (`zhengchong/CatVTON`, `booksforcharlie/stable-diffusion-inpainting`) |
| 추론 스텝 | `num_inference_steps=20` |
| guidance scale | `2.5` |
| 해상도 | 768×1024 고정 |
| 지원 fit_type | regular / oversized / cropped |
| 지원 카테고리 | 상의(upper)만 |
| 마스크 생성 | `AutoMasker`(DensePose + SCHP 기반) |
| 워커 모델 로딩 방식 | 워커 프로세스 시작 후 첫 job 처리 시 1회 로드, 이후 재사용 (lazy loading) |

## 3. 개선이 필요한 지점

### 3.1 추론 속도

- ~~현재 `num_inference_steps=20`은 CatVTON 권장 기본값 수준. 스텝을 낮추면(예: 12~15) 속도는 빨라지지만 품질 저하 가능 — 실측 비교 필요~~
  **정정(§7 실측)**: `CatVTONPipeline` 자체 기본값은 50이고, 20은 오히려 다운튜닝된 값이었다. 실측 결과
  50이 20보다 원단 재현력이 낫다고 판단해 50으로 올렸다 — 속도보다 품질을 우선한 결정. 스텝을
  더 낮추는 실험은 아직 안 했다.
- lazy loading 방식이라 **워커 기동 후 첫 요청은 모델 로딩 시간이 그대로 응답 지연에 포함됨**. 실사용 시나리오에서 이게 허용 가능한지, 아니면 워커 기동 시점에 미리 로드(eager loading)해둘지 결정 필요
- 배치 처리(fit_type 여러 개를 한 번에) 지원 여부 — 현재는 job 하나당 fit_type 하나

### 3.2 이미지 품질

- `composite_with_original`로 마스크 안/밖을 원본과 합성하는 방식이라, **마스크 경계 부분의 부자연스러운 경계선**이 생길 가능성 있음 — blur factor(현재 9) 튜닝 여지
- guidance_scale(현재 2.5)을 높이면 원단 조건 반영이 강해지지만 인물 왜곡 위험도 같이 증가 — 트레이드오프 실측 필요
  → **실측 완료(§7)**: 3.0으로 확정. 30(CFG 정상 범위 1~10 밖) 시도는 과포화·구조 붕괴 위험이 커서 보류.
- 생성 시드가 고정(`manual_seed(42)`)되어 있어 항상 같은 결과가 나옴 — 사용자별 다양성을 줄지, 재현성을 유지할지 정책 결정 필요

### 3.3 지원 카테고리 확장

- 현재 `AutoMasker(..., mask_type="upper", ...)`로 상의 전용
- 하의(lower), 아우터(outer), 원피스(dress) 등 확장 시 `mask_type` 값과 그에 맞는 마스크 로직 검증 필요 (CatVTON/AutoMasker가 기본 지원하는 타입 확인부터)
  → **하의는 §7에서 검증 완료.** 모자/신발은 `AutoMasker`의 일반 로직 자체가 못 타서(3.3.1) 별도
  로직을 새로 만들었다.

#### 3.3.1 모자/신발이 일반 로직을 못 타는 이유

`AutoMasker.cloth_agnostic_mask()`의 upper/lower/overall/inner/outer 공통 로직은 "이 부위를
마스킹할 때 다른 옷(예: 하의를 마스킹할 때 상의)을 보호 대상으로 뺀다"는 `PROTECT_CLOTH_PARTS`
전제 위에서 동작한다. 모자/신발은 이 전제가 성립하지 않는다:

- **모자**: DensePose의 24개 신체 부위 인덱스(`DENSE_INDEX_MAP`)에 머리/두피에 대응하는 항목이
  아예 없다(SMPL 몸 표면 모델 자체에 모발이 없어서). 게다가 인물이 이미 모자를 쓰고 있지 않으면
  SCHP `Hat` 라벨도 비어 있어, 마스크 대상이 될 재료가 아무것도 없다.
- **신발**: DensePose `feet` 인덱스는 있지만, `PROTECT_CLOTH_PARTS['shoes']`를 채우지 않으면
  상의/바지를 보호할 방법이 없어서 일반 로직의 "보호 대상 아닌 모든 영역" 폴백이 몸통까지
  통째로 마스크로 잡아버린다(§7에서 실측으로 발견).

두 경우 다 일반 로직을 타면 잘못된 결과가 나와서, `_hat_mask()`/`_shoes_mask()`라는 완전히 별도
경로를 새로 만들었다(§7).

## 4. 적용 가능 기법 조사 및 우선순위

| 기법 | 목적 | 예상 효과 | 적용 난이도 | 우선순위 |
|---|---|---|---|---|
| ~~추론 스텝 다운튜닝 (20→12~15)~~ → **업튜닝 20→50 (§7 실측)** | 품질 | 원단 재현력 향상(다운튜닝 아님) | 낮음 (파라미터 변경) | 상 |
| Eager loading (워커 기동 시 모델 미리 로드) | 속도(체감) | 첫 요청 지연 제거 | 낮음 | 상 |
| blur_factor / guidance_scale 튜닝 | 품질 | 경계선 자연스러움, 원단 반영도 | 낮음 (실측 반복 필요) | 상 |
| 카테고리 확장 (하의/아우터/원피스) | 기능 범위 | 지원 상품 범위 확대 | 중간 | 중 |
| 파인튜닝 (자체 데이터셋) | 품질 | 도메인 특화(빈티지 의류) 정확도 향상 | 높음 (데이터셋 구축 필요) | 하 (MVP 이후) |
| 경량화 (양자화, 증류 모델) | 속도 | GPU 메모리·추론 시간 감소 | 높음 | 하 (노트북 GPU 한계 확인 후) |
| 결과 캐싱 (동일 person+cloth+fit 조합) | 속도 | 반복 요청 시 즉시 응답 | 중간 (캐시 키 설계, 스토리지 필요) | 중 |
| 배치 처리 (fit_type 3종 한 번에) | 효율 | GPU 활용률 개선 | 중간 | 중 |

우선순위 "상"으로 표시한 항목은 **모델 교체나 재학습 없이 파라미터/구조 조정만으로 가능**해, 1차 구현 구조(`_ensure_loaded()` / `run_inference()`)를 유지한 채 바로 적용 가능하다.

## 5. 로드맵 (제안)

**1단계 — 파라미터 튜닝 (모델 교체 없음)**
- 추론 스텝, guidance_scale, blur_factor 조합별 실측 비교
- Eager loading으로 전환, 워커 기동 시간 대비 체감 응답속도 개선 확인

**2단계 — 캐싱 도입**
- 동일 입력(person+cloth+fit_type) 재요청 시 캐시 결과 반환
- 캐시 키 설계, 저장 위치(현재 EC2 로컬 디스크 구조 재사용 가능한지 검토)

**3단계 — 카테고리 확장**
- 하의부터 우선 확장 (빈티지 의류 카테고리 비중 고려)

**4단계 — 경량화/파인튜닝 검토 (MVP 이후)**
- 노트북 GPU(6GB VRAM 등) 제약 안에서 실행 가능한 경량화 기법 조사
- 자체 데이터셋 확보 시 파인튜닝 검토

## 6. 참고 — 구조적으로 이미 확보된 것

현재 워커 구조(`base_worker.py` + `run_inference()`)는 모델 내부 구현을 게이트웨이·큐·API 계약과 분리해뒀기 때문에, 위 고도화 항목들은 **`TryonWorker` 클래스 내부만 수정하면 적용 가능**하다. 게이트웨이(`AI/app/gateway/`), Job/Result 스키마, Caddy 라우팅 등은 변경할 필요가 없다.

## 7. 로컬 검증 실측 결과 (`S15P11A108-367`)

`AI/validation/TRYON/AI_tryon/CatVTON/`(`worker/models/catvton`을 그대로 복제한 실험용 스냅샷,
[`NOTE.md`](../validation/TRYON/AI_tryon/CatVTON/NOTE.md) 참고)에서 진행한 검증 결과다.
**아직 프로덕션(`worker/models/catvton`, `worker/tryon_worker_example.py`)에는 반영 안 됨** —
검증 폴더에서만 확인된 내용이고, 실제 적용 여부는 별도 결정.

### 7.1 추론 파라미터 확정

- `num_inference_steps`: 20 → **50** (`CatVTONPipeline` 자체 기본값과 동일). 원단 재현력이
  20보다 낫다고 판단해 확정.
- `guidance_scale`: 2.5 → **3.0**. 비교 삼아 30(CFG 정상 범위 1~10 밖)도 시도했으나, 이 파이프라인의
  classifier-free guidance 수식(`noise_pred_uncond + guidance_scale * (noise_pred_text -
  noise_pred_uncond)`)이 그 정도 배수를 감당하도록 학습되지 않아 과포화·구조 붕괴 위험이 크다고
  보고 채택하지 않음.

### 7.2 카테고리 확장 — 하의(lower)

`mask_type="lower"` + 하의 이미지(`image/pants.jpg`)로 정상 동작 확인. `person.jpg`/`person2.jpg`
둘 다 상의만/하의만/상의+하의(순차 적용 — 파이프라인이 `condition_image`를 한 번에 1장만 받아서,
상의를 먼저 입힌 결과 위에 하의를 이어서 입히는 방식으로 구성) 조합을 전부 확인했다.

### 7.3 카테고리 확장 — 모자/신발 (신규 마스킹 로직 필요)

3.3.1에서 설명한 구조적 이유로 `AutoMasker`에 `_hat_mask()`/`_shoes_mask()`를 새로 추가했다
(`model/cloth_masker.py`).

- **모자**: SCHP `Hair` 라벨(+ 이미 모자를 쓰고 있었다면 `Hat` 라벨) 바운딩 박스를 위/좌우로
  확장하는 기하학적 추정. 챙이 넓은 모자(갓 스타일)로 테스트해보니 머리 폭에 딱 맞춰서는 챙이
  잘렸다 — **모자는 몸 실루엣(머리) 범위를 넘어 배경 영역까지 마스크가 나가는 게 정상**이라는
  결론으로, 위쪽 90%/좌우 40% 여유를 뒀다(임시값, 다른 모자 형태로 추가 검증 필요).
- **신발**: DensePose `feet` 인덱스(+ 기존 신발 라벨)를 발목 위쪽까지 확장. 처음엔 신발도
  기존 upper/lower와 같은 일반 로직을 태웠는데, `PROTECT_CLOTH_PARTS['shoes']`가 상의/바지를
  보호할 방법이 없어서 몸통까지 통째로 마스크에 잡히는 게 실측으로 나왔다(3.3.1) — 그래서
  모자와 같은 방식(전용 함수)으로 교체했다.

### 7.4 마스크 경계 버그 — 손이 주머니에 들어간 지점

상의+하의 조합 테스트 중, 손을 주머니에 넣은 포즈에서 하의 생성 결과에 **원본 청바지 원단이
그대로 남는 지점**을 발견했다. 원인은 `strong_protect_area`의 손 보호 로직
(`hands_protect_area`)이 DensePose 손 영역을 팽창(dilate)시킨 뒤 보호 대상으로 잡는데, 이
팽창 폭이 실제 손 크기보다 넓어서 바로 옆 바지 원단까지 같이 보호돼버린 것 — `mask_type`과
무관하게 항상 적용되는 로직이라 하의 마스킹에도 영향을 준다.

손가락 경계 보호 자체(팽창을 아예 없애면 손끝이 다른 포즈에서 잘려 보일 위험)는 유지하되, 손
보호 전용으로 다른 용도(전체 마스크 팽창 등)와 공유하지 않는 더 작은 커널을 따로 둬서 여백만
줄였다(`hands_dilate_kernel`, 기존 `dilate_kernel`의 절반 크기).

### 7.5 체형/의류 치수 기반 adaptive 마스킹 (`S15P11A108-368`)

`fit_type`(regular/oversized/cropped) 고정 3단계 대신, 실제 신체 치수와 의류 치수 차이를
연속적으로 반영하는 로직을 구현했다. 설계: `.claude/plans/ai/011-tryon-adaptive-masking.md`.

**구현 범위**: 두 데이터 소스가 이번 세션에 부분적으로 갖춰졌다 — 의류 치수는 `garment_
measurement` 기능이, 신체 치수는 BE `member_body_profile`(height_cm/weight_kg만 확정
컬럼)이 제공한다.

- **너비(바지 허리, 스키니/배기)**: `body_waist_cm` ↔ `WAIST_WIDTH`. 평평하게 편 원단 폭이
  몸에 맞았을 때 둘레의 절반과 같다는 물리적 관계를 쓴다. 로직은 구현했지만 BE
  `member_body_profile`에 waist 컬럼이 아직 없어(`.claude/requests/be/
  005-tryon-adaptive-fit-data.md`) 실제로는 계속 비활성 상태다 — 데이터가 생기면 바로
  켜지는 구조로만 준비해뒀다.
- **길이(기장) 축은 의도적으로 뺐다.** 처음엔 키 대비 총장 비율로 마스크 하단을 잘라 기장을
  연속적으로 조절하려 했는데, 이 방식은 잘려나간 부분(팔뚝·다리 등)의 맨살을 diffusion이
  항상 새로 생성해야 한다 — **AI 가드레일상 맨살 생성은 정책적으로 피해야 해서 폐기했다.**
  실제로 원했던 건 "옷이 짧아지는 것"이 아니라 "핏(스키니/배기)이 조절되는 것"이었어서,
  옷이 덮는 신체 범위 자체는 그대로 두고 폭만 조절하는 너비 축만 남겼다.
- **범위 밖**: 상의/원피스 가슴(bust) 너비 축. 겨드랑이 랜드마크가 없어 대응하는 의류
  치수 자체가 없다(`AI/app/measurement/schemas.py`). 폭 축이 없는 상의/원피스는 지금
  적응형 마스킹이 아예 안 켜지고 항상 `fit_type` 고정 3단계로 동작한다.

**여전히 남아있는 한계**: 마스크 크기 조절은 diffusion이 그 영역을 다시 그리도록 유도하는
정도지, 원단이 실제로 늘어지는 물리를 시뮬레이션하는 게 아니다 — 비율을 연속값으로 정교하게
잡아도 결과가 그만큼 정확히 반영된다는 보장은 없다(고정값 방식과 근본적으로 같은 한계).

측정값이 없거나 대응하는 축이 없으면(둘 다 선택값이라 대부분의 경우 그럴 것이다) 기존
`fit_type` 고정 3단계로 그대로 폴백한다 — 데이터 없는 케이스에서 기존 동작이 전혀 안 바뀐다.

`scale_px`·`max_px` 같은 첫 버전 상수는 알파 테스트(`AI/docs/tryon-alpha-test-data-format.md`)로
실제 팀원 체형·의류 데이터가 모이면 보정 대상이다.

**검증**: `AI/validation/TRYON/AI_tryon/CatVTON/verify_adaptive_masking.py`로 마스크뿐
아니라 실제 옷을 입힌 합성 결과까지 육안 확인했다 — 타이트/루미 케이스에서 바지 폭이
방향대로 좁아지고 넓어지는 걸 확인. 이 검증 중 진짜 버그 하나를 발견해 고쳤다: 바지 마스크
컷오프를(당시엔 길이 축이 있었다) torso 행 범위 기준으로 계산해서 다리 마스크 대부분이
사라지는 문제였다 — 길이 축 자체를 없애면서 이 문제도 함께 해소됐다.

## 8. 하의 길이 불일치(긴 원본 → 짧은 레퍼런스) 문제 해결 (`S15P11A108-499`)

### 8.1 문제

원본 사진의 기존 의류(긴바지)보다 짧은 레퍼런스(반바지)를 입힐 때, `AutoMasker`의
`mask_type="lower"` 마스크는 다리 전체(허리~발목)를 잡는다. 이 마스크 전체를 CatVTON이
반바지 레퍼런스만으로 채우려니, 실제로는 **레퍼런스 원단을 다리 끝까지 그냥 이어 그려서
"반바지"가 아니라 "긴바지"처럼 나오는 문제**가 있었다(§7의 하의 지원과는 별개 이슈 —
길이가 원본과 비슷한 레퍼런스는 문제없이 작동했고, 원본보다 훨씬 짧은 레퍼런스일 때만
발생).

### 8.2 원인 진단 — 어텐션 맵 실측

`verify_attention_map.py`로 CatVTON self-attention(`attn1`)의 실제 가중치를 캡처해서
확인했다. CatVTON은 인물 latent와 레퍼런스 의류 latent를 세로로 이어붙인 하나의 캔버스
(`torch.cat([masked_latent, condition_latent], dim=-2)`, `model/pipeline.py:139`)로
UNet에 넣고 self-attention이 그 안에서 서로를 참조하게 하는 구조다.

발목 위치 쿼리의 어텐션을 재보니 **원본(인물) 쪽에 89.9%, 레퍼런스 쪽엔 10.1%**만
집중돼 있었다. 다만 `masked_image = image * (mask < 0.5)`(`model/pipeline.py:132`)로
마스크 영역은 VAE 인코딩 전에 이미 0으로 지워지므로, 이건 "원본 청바지 픽셀을 보고
이어 그리는" 게 아니라 **"다리 모양으로 뚫린 빈 영역 = 옷 한 벌로 통째로 채워야 한다"는
학습된 형태 기반 편향(shape prior)**이다. 레퍼런스가 가진 약한 신호(10%)로는 이 기본
판단을 뒤집지 못했다.

이 편향의 강도는 마스크의 절대 면적(=체형 크기)에 비례하는 것으로 보인다 — 같은 조건에서
작은 체형(철수)은 성공, 큰 체형(둘리)은 실패하는 패턴이 반복 확인됐다.

### 8.3 해결책 — 3단계 조합 (체형·마스크는 건드리지 않음)

**주의**: 마스크를 직접 잘라내거나 체형(실루엣) 자체를 바꾸는 방식은 검토했으나 채택하지
않았다 — "체형은 그대로 두고 그 위 옷의 핏만 조절한다"는 원칙과 맞지 않고, 마스크를
수동으로 잘라내는 것은 모델이 스스로 판단해야 할 것을 우리가 대신 정해버리는 것이라
제외했다.

1. **Worn-reference condition image**: 플랫레이(제품 단독) 사진 대신, FLUX.2-Klein-4B로
   생성한 "실제로 입은 사람" 사진을 `condition_image`로 쓴다
   (`generate_worn_references.py`). 플랫레이는 "이 옷이 몸에서 어디까지 오는지"에 대한
   정보가 약한데, 입은 형태의 레퍼런스는 이 정보를 명시적으로 준다.
2. **체형 매칭**: 레퍼런스 인물의 체형을 타겟 인물과 맞춘다(마른 체형/여성/큰 체형 각각
   별도 생성, `worn_references/pants_worn_reference_{name}.png`). 노출 없이 상의를 입힌
   채로 생성해서 불필요한 노출 콘텐츠도 피한다. 이것만으로 작은/중간 체형(철수/영희)은
   완전히 해결됐지만, 큰 체형(둘리)은 여전히 부족했다.
3. **Self-attention 어텐션 부스팅**: `verify_attention_boost.py`. self-attn 레이어에서
   **다리 하단(무릎 아래) 위치의 쿼리에 한해, 레퍼런스 의류 쪽(key) 로짓에 +6.0을
   가산**해서 softmax 이후 그쪽 가중치가 커지도록 추론 시점에 직접 교정한다. 재학습 없이
   형태 기반 편향을 상쇄하는 방식. 고해상도 레이어(`seq_len > 4096`)는 메모리 폭증을
   피하려고 원래의 fused attention 커널로 폴백한다(속도 영향 거의 없음, 50스텝 기준
   1.9s/it 유지).

### 8.4 결과

철수(마른 체형)/영희(여성)/둘리(큰 체형) 세 체형 모두 일관되게 반바지 길이가 정확히
렌더링되고, 그 아래 다리는 자연스러운 맨살로 나오는 걸 확인했다(`attention_boost_result/`).
체형에 따른 실패 편차가 완전히 해소됐다.

**검증**: `verify_mask_size_compare.py`(마스크 절대 면적 비교), `verify_attention_map.py`
(어텐션 가중치 실측), `verify_attention_boost.py`(3명 전체 최종 검증) —
`AI/validation/TRYON/AI_tryon/CatVTON/`에 있다.

## 9. 사이즈(체형-의류 치수) 기반 폭 조절 검증

§8.5에서 예고한 대로, §7.5의 `adaptive_fit.py` 폭 축(width_ratio → dilation_px)을 §8의
길이 렌더링 픽스(worn-reference + 체형 매칭 + attention 부스팅)와 결합해서 실제
프로덕션 경로로 테스트했다(`verify_size_fit_combined.py`). `AutoMasker(...,
body_measurements={"waist_cm": ...}, garment_measurements={"WAIST_WIDTH": 38.0})` —
지금까지는 실제 BE 데이터가 없어 항상 `None`으로 비활성이던 경로다. 같은 반바지
(WAIST_WIDTH=38cm 가정)를 허리둘레가 다른 세 체형(영희 65cm/철수 75cm/둘리 110cm)에게
입혀서 자동으로 루즈/레귤러/타이트하게 나오는지 확인했다.

### 9.1 재현성 버그 — generator 재사용

`torch.Generator(device="cuda").manual_seed(42)`를 루프 **밖**에서 한 번만 만들어 세
케이스에 재사용했다. `pipeline.py`의 `randn_tensor(..., generator=generator, ...)`가
호출마다 이 generator의 내부 상태를 전진시키므로, 첫 케이스(영희)만 실제로 seed=42였고
이후 케이스(철수/둘리)는 사실상 재현 불가능한 임의 상태로 생성됐다 — 둘리 결과에서 다리
전체를 덮는 격자무늬(청바지 데님이 비쳐 보이는 듯한) 아티팩트로 나타났다. 케이스마다
`manual_seed(42)`를 새로 호출하도록 고치자 해당 아티팩트는 사라졌다.

### 9.2 AI 모델 사진 해상도 불일치 → 신발 잘림

`cheolsu.png`/`younghee.png`/`dooly.png`가 768×1152(FASHN VTON PoC용 구도)로 생성돼
있었는데, CatVTON 스크립트들은 `resize_and_crop(image, (768, 1024))`로 리사이즈한다.
이 함수는 세로를 중앙 기준 대칭 크롭해서 위/아래 각 64px씩 잘라내는데, 인물 사진 구도상
아래쪽 64px에 신발 끝부분이 걸려 세 인물 모두 신발이 잘려 나왔다. AI 모델 사진을
CatVTON 작업 해상도(768×1024)로 직접 재생성해서(`models_ai_generated/
regenerate_at_catvton_resolution.py`) 크롭이 사실상 no-op이 되도록 고쳤다.

### 9.3 컴포지팅 고스트 아티팩트 (원인 가설, 미해결)

위 두 버그를 고친 뒤에도 폭 조정량이 0에서 멀어질수록(영희 +3.4px 팽창/둘리 -6.2px
수축) 마스크 경계를 따라 반투명 이중윤곽("고스트")이 남는다 — 조정량이 거의 0인
철수(+0.3px)는 깨끗하다. `composite_with_original()`이 `mask_processor.blur
(blur_factor=9)`로 부드럽게 처리된 마스크의 중간 알파(0~1) 구간에서 생성 이미지와 원본
이미지를 섞는 구조인데, 마스크 경계를 인위적으로 넓히거나/좁히면 그 경계가 diffusion이
실제로 그린 옷의 경계와 어긋나서 이 블렌딩 아티팩트가 생기는 것으로 추정한다. 다음
세션에서 원인을 확정하고 수정한다.

## 10. Fit-aware worn-reference를 상의/아우터로 확장, 그래픽 정확도 문제 해결, 액세서리는 FLUX로 전환 (`S15P11A108-506`)

9.5에서 예고한 대로 §8.3의 fit-aware worn-reference(레퍼런스 이미지 자체에 타이트/루즈
정도를 반영)를 마스크 지오메트리 조절 대신 폭 축에도 적용했다. 청바지(§9)에서 시작해
그래픽 티셔츠(상의), 아우터(재킷)까지 같은 원리로 확장했고, 그 과정에서 그래픽 정확도
문제와 아우터 특유의 프레이밍 버그를 새로 발견하고 해결했다. 마지막으로 모자/신발
액세서리는 CatVTON 경로 자체를 포기하고 FLUX만으로 전환했다.

### 10.1 상의(그래픽 티셔츠) — 세분화된 fit-aware worn-reference

§9의 바지 폭 조절 원리(`ratio = garment_measurement_cm / body_measurement_cm`)를 상의에
그대로 적용했다. 가슴둘레(허리 역할) + 전체길이(총장 역할)에 더해, 어깨너비/소매길이
축을 추가로 도입해 핏을 더 세분화했다(`generate_worn_reference_top_fitaware.py`).
tight/loose 방향 각각 7단계로 잘게 나누고, 문구에 실제 `% too big/small` 수치를
그대로 박아서 사이즈마다 프롬프트가 겹치지 않게 했다(이전엔 정성적 문구만 써서 인접
사이즈가 같은 문구로 묶여 같은 이미지가 나오는 버킷 충돌 버그가 있었다).

- **레귤러 구간 비대칭 버그**: `ratio < 1.0`이면 무조건 타이트 분기로 빠지는 코드라
  `[0.95, 1.0)` 구간이 "레귤러"에 절대 도달하지 못했다(둘리 XXL=0.977이 "약간
  타이트"로 잘못 나온 원인) — `0.95 <= ratio <= 1.05`를 가장 먼저 검사하는 대칭 분기로
  수정.
- **극단 구간 프롬프트 재배치**: FLUX.2의 텍스트 인코더가 `AutoModelForCausalLM`
  기반이라 문장 앞쪽 내용에 더 강하게 반응한다는 게 §9에서 이미 확인됐는데, 상의에서도
  동일하게 극단(가장 타이트/가장 루즈) 구간에서 `"IMPORTANT: ... must look extremely
  X -- NOT Y."`를 문장 맨 앞에 배치해야 편향(체격 큰 사람 → 평범한 핏으로 되돌아가는
  학습된 기본값)을 상쇄할 수 있었다.
- **미해결로 남은 것**: XXL 기장이 여전히 과도하게 길게 나오는 문제가 있는데, 기장
  문구 자체가 아니라 위 "extremely oversized" 강조 재배치가 기장까지 같이 부풀리는
  것으로 보인다 — 원인 후보만 확인했고 수정은 못 했다.

### 10.2 그래픽(프린트) 정확도 문제 — worn-reference를 person 자리에 넣는 방식으로 해결

그래픽 프린트가 있는 티셔츠(`top.jpg`, 포켓몬 프린트)를 §8.3 방식(FLUX worn-reference를
`condition_image`로)으로 시도하니, CatVTON이 **worn-reference에 VLM 캡션을 거쳐 다시
그려진(그래서 열화된) 그래픽**을 그대로 재현했다 — 실제 상품의 정확한 그래픽이 아니라
"그래픽 비슷한 것"이 나왔다. `CatVTONPipeline.__call__`은 `condition_image`를 1장만
받는 구조라 "핏 정보용 worn-reference"와 "그래픽 정확도용 실제 상품 사진"을 동시에 줄
방법이 없다.

- **시도 1(폐기)**: `concat_dim=-2` 캔버스를 2블록(사람+레퍼런스)에서 3블록(사람+
  worn-reference+실제 상품 사진)으로 확장(`verify_top_dual_reference.py`). 이미지 1장에
  9분 이상 걸려(정상 2블록은 1.5~2분) 실용성이 없다고 판단해 완료 전에 중단.
- **시도 2(채택)**: `image`(사람) 자리에 원본 사람 사진 대신 worn-reference를,
  `condition_image` 자리엔 실제 상품 사진을 그대로 넣는다(`verify_top_worn_ref_as_
  person.py`). 표준 2입력 구조를 그대로 쓰되 입력만 바꾸는 방식이라 구조 변경이
  필요 없다. `AutoMasker`가 DensePose(신체 부위)뿐 아니라 SCHP(실제 의류 파싱)도 같이
  쓰는 걸 이용한다 — worn-reference에 이미 그려진 헐렁한 실루엣을 SCHP가 그대로 마스크
  모양으로 잡아주므로, 마스크 자체가 핏을 반영한 채로 그 안을 실제 상품 사진으로 채울
  수 있다. XXL(가장 루즈한 케이스로 마스크 모양 차이가 가장 잘 보임) 검증 결과, 마스크가
  오버사이즈 실루엣을 정확히 따라갔고 최종 결과의 그래픽도 실제 상품과 일치했다.

### 10.3 아우터(재킷) — 인물이 사이즈별로 확대되는 프레이밍 버그

같은 원리를 알파테스트3 아우터(오버셔츠形 재킷, `outer.jpg`)에 적용하면서, 옷이
오버사이즈로 묘사될수록 **카메라가 인물 자체를 확대해서 찍는** 프레이밍 버그를
발견했다. 재킷 폭이 넓어지는 것과는 별개로, SCHP로 머리 크기(Hair|Face 라벨, 옷과
무관한 지표)만 따로 재보니 M~XXL 사이에 head height가 188→260px(38% 차이)로
벌어졌다 — 사람 자체가 커지고 있었다.

**후처리 정규화 시도(부분 실패)**: SCHP 인체 파싱으로 바운딩박스를 검출해 기준
이미지에 스케일을 맞추는 후처리(`fix_worn_reference_framing.py`)를 시도했다.

- 1차(배경색 차이로 전경 검출): 흰 운동화가 흰 배경과 색이 비슷해 경계가 부정확 —
  실제로는 XXL에서 발이 프레임 밖으로 잘렸는데도 M과 거의 같은 bbox로 검출됐다.
- 2차(SCHP 전신 bbox): 색상 문제는 해결됐지만, 전신 bbox의 아래쪽이 거의 항상
  이미지 맨 아래 행에 닿아서(신발이 실제로 잘리든 안 잘리든) 사이즈가 달라져도 bbox
  높이가 거의 안 바뀌는 포화 현상이 있어 스케일 지표로 못 썼다.
  → 옷과 무관한 **머리(Hair|Face) bbox**로 지표를 바꾸니 정확한 스케일 차이가
  잡혔다.
- 근본 한계: 스케일은 맞출 수 있어도, 이미 프레임 밖으로 잘려나간 픽셀(발)은
  후처리로 복원할 수 없다 — XXL을 머리 크기 기준으로 축소하니 잘린 채로 캔버스
  여백만 커지는 결과가 나왔다.

**해결책(채택) — FLUX2 참조 이미지 편집 모드**: `Flux2KleinPipeline`이 `image=`
파라미터로 참조 이미지를 조건으로 받는 편집 모드를 지원한다(레퍼런스 latent를 생성
latent와 이어붙여 self-attention이 참조하게 하는 구조, FLUX Kontext류와 같은 원리).

- 이미 재킷을 입은 worn-reference를 참조로 주고 "핏만 바꿔라"고 지시하니, 프레이밍은
  완벽히 고정됐지만 **이미 그려진 재킷을 갈아치우는 걸 모델이 거부**해서 핏 변화
  자체가 거의 반영되지 않았다(8/24스텝 둘 다 동일하게 실패 — 스텝 문제가 아니었다).
- 재킷이 전혀 없는 **원본 베이스 사진**(`models_ai_generated/heedongi.png`)을 참조로
  주고 "이 사람에게 이런 핏의 재킷을 입혀라"는 새 생성 프롬프트로 바꾸자 두 문제가
  동시에 해결됐다 — 기존 옷을 지우는 게 아니라 새로 입히는 것이므로 핏 반영이 잘
  되고, 포즈/스케일/카메라 프레이밍(발이 보이는지 여부까지)은 참조 사진 그대로
  상속된다. 8/24스텝 비교 결과 품질 차이가 없어 8스텝으로 유지(속도 3배 이득).

`generate_worn_reference_outer_fitaware.py`를 이 방식으로 재작성하고 M/L/XL/XXL
전체를 재생성 + `verify_outer_worn_ref_as_person.py`(10.2의 worn-reference-as-person
방식)로 재검증했다 — 4개 사이즈 전부 인물 크기/포즈/프레이밍이 완전히 동일하게
유지됐다. 다만 사이즈 간 핏 차이 자체는 다소 은은한 편이고(재킷이 원래 오버핏
스타일이라 M도 넉넉해 보임), XXL 손목 부근에 작은 마스크 잔여 아티팩트가 남아있다.

### 10.4 액세서리(모자/신발) — CatVTON 포기, FLUX만으로 전환

알파테스트3에 모자(`hat.jpg`, 버킷햇)/신발(`shoes.jpg`, 샌들)이 추가됐다. 사이즈
조절이 필요 없는 카테고리라 CatVTON 없이 FLUX만으로 시도했다.

**CatVTON 경로 재확인(실패)**: `AutoMasker`의 `mask_type`은 upper/lower/overall/
inner/outer만 지원한다 — 모자/신발 전용 마스크 로직이 없다(§3.3.1/§7.3에서 이미
확인된 구조적 한계와 동일). §7.3에서 `_hat_mask()`/`_shoes_mask()`를 `cloth_masker.py`에
새로 추가했다고 기록돼 있었으나, **이후 커밋(`7f03fc4`, S15P11A108-499 하의 길이
렌더링 수정)에서 해당 함수들이 삭제된 채 복구되지 않았다** — 이번 세션에 그 사실을
git 히스토리로 확인했다. 이번 세션에서 SCHP 파싱 결과로 마스크를 직접 만들어(신발은
기존 SCHP `Left-shoe`/`Right-shoe` 라벨, 모자는 Hair|Face bbox를 위/좌우로 확장한
사각형) 다시 시도했지만(`verify_alpha3_hat_shoes_heedongi.py`), 두 경우 다 실패했다:

- **모자**: 마스크는 대략 맞는 위치에 잡혔지만, 결과물은 버킷햇이 아니라 베이지색
  상자/원통 형태로 나왔고 색상도 틀렸다(검정 → 베이지).
- **신발**: 마스크는 SCHP가 정확히 잡았지만, 마스크 모양 자체가 원본 운동화
  실루엣에 묶여 있어서 샌들의 오픈토/스트랩 형태 자체가 나올 수 없었다. 색상도
  틀렸다(검정 → 베이지).

CatVTON은 상의/하의 의류 try-on 전용으로 학습된 모델이라 액세서리는 학습 분포
밖이고, 마스크를 아무리 정밀하게 잡아도(신발처럼) 원본 실루엣에 묶이는 형태 문제나
(모자처럼) 레퍼런스 반영이 약해 기본 색상 편향으로 되돌아가는 문제를 해결하지
못했다.

**해결책 — FLUX2 참조 편집으로 완전 전환**: 10.3에서 검증한 "원본 사진 참조 +
새로 입혀라" 방식을 그대로 재사용했다(`generate_hat_shoes_flux.py`). VLM으로
모자/신발 상품 사진을 캡션(색상/소재/스타일)한 뒤, `image=[원본 사진]` + "이
사람에게 {캡션} 씌워라/신겨라" 프롬프트로 생성 — 마스크/인페인팅이 아예 없는 통짜
재생성이라 신발 형태가 원본 실루엣에 묶이는 문제 자체가 발생하지 않는다.

모자만/신발만/모자+신발 동시 세 가지 케이스 전부 성공했다 — 버킷햇은 챙이 넓은
정확한 형태와 검정색으로, 샌들은 크로스 스트랩 형태와 검정색으로 정확히
반영됐다. 다만 모자+신발을 **동시에** 편집한 케이스에서만 청바지 색이 원래
파란색보다 어둡게(검정에 가깝게) 바뀌는 부수 효과가 있었다 — 개별 편집(모자만,
신발만) 케이스에서는 나타나지 않았다.

## 11. 프로덕션 승격 — VLM + FLUX + CatVTON (`S15P11A108-504`)

§9~§10에서 검증한 fit-aware worn-reference 기법을 프로덕션 `worker/tryon_worker_example.py`로
승격했다. 검증 때와 결정적으로 다른 점 하나: **타겟이 실제 고객 사진이다.** §9~§10은 전부
고정된 AI 모델 4명(희동이/도우너/둘리/마이콜)에게 입혀보는 검증이었지만, 프로덕션
`tryon_worker_example.py`는 원래 실제 고객 사진(`user_image_url`) + 상품 사진을 받아
합성하는 계약이었다 — 이 계약을 유지한 채 VLM+FLUX 단계를 앞에 붙였다.

### 11.1 캐싱 포기

처음엔 "worn-reference는 상품+사이즈당 한 번만 만들면 되는 자산"이라는 생각으로 생성
결과를 캐싱해서 고객마다 재사용하는 구조를 검토했다. 하지만 타겟이 실제 고객 사진으로
확정되면서 이 전제가 깨졌다 — worn-reference는 "그 고객 사진"을 참조로 생성해야 결과에
그 고객 본인이 나오므로, 고객마다 다시 생성해야 한다. 재사용 이점 없이 매 요청마다
FLUX를 다시 돌리는 쪽으로 결정했다(사용자 확정).

### 11.2 신체 치수 — 실측 대신 키/몸무게 근사

§9~§10의 핏 계산(`ratio = garment_measurement_cm / body_measurement_cm`)은 실제 신체
치수가 있어야 하는데, BE `member_body_profile`엔 아직 `height_cm`/`weight_kg`만 확정
컬럼이고 가슴/허리/엉덩이 실측 컬럼은 없다(`.codex/requests/be/
003-onboarding-tryon-profile-api.md`, 아직 열려있음). 새 BE 스캔 기능을 기다리는 대신,
**키/몸무게 기반 근사 공식**(`worker/models/catvton/body_estimate.py`)으로 대체했다 —
키 대비 부위별 평균 비율에 BMI 편차 보정을 곱하는 방식. 정밀한 회귀식이 아니라 v1
근사치라는 걸 코드에 명시했고, 실측 컬럼이 생기면 그 값이 우선한다(`body_waist_cm`이
payload에 있으면 근사를 건너뜀).

### 11.3 세 모델 순차 로드 (동시 상주 아님)

VLM(Qwen3-VL-4B) + FLUX.2-Klein-4B + CatVTON을 한 워커 프로세스 안에서 순차로 로드/
언로드한다 — `worker/garment_measurement_worker_example.py`가 이미 "한 프로세스 안에서
여러 무거운 모델을 순차 체이닝"하는 전례였다. 프로덕션엔 GPU 서버가 없고 팀원 노트북
(6GB급)이 워커로 붙는 구조라(`AI/docs/infra-architecture.md`), 세 모델 동시 상주는 안
되지만 순차 로드라면 피크 VRAM이 가장 큰 단일 스테이지(FLUX, ~5-6GB) 수준으로 억제된다.
FLUX 사용 종료 직후 `del`+`torch.cuda.empty_cache()`(`worker/models/tryon_flux/
generator.py`의 `Flux2KleinGenerator.unload()`).

새 VLM/FLUX 단계는 `quality_check_worker_example.py`/`stt_worker_example.py`가 이미 쓰는
"`FEATURE_BACKEND=mock` 기본값, GPU 없이 전 경로 검증" 컨벤션을 그대로 따른다
(`TRYON_VLM_BACKEND`/`TRYON_FLUX_BACKEND`, `worker/README.md` 참고). CatVTON 자체는
원래부터 mock이 없었고 이번에도 추가하지 않았다.

### 11.4 파이프라인 구조 — 하의 전용 어텐션 부스팅(§8)은 안 가져옴

§10.2에서 검증한 worn-reference-as-person 방식으로 통일했다 — `image=worn-reference`
(FLUX가 방금 생성), `condition_image=실제 상품 사진`, 마스크는 `AutoMasker`로
worn-reference에서 새로 계산한다. §8의 어텐션 부스팅(하의 길이 렌더링 보정)은 이번엔
안 가져왔다 — worn-reference-as-person 방식은 마스크를 worn-reference에서 새로 계산하므로
애초에 올바른 길이가 마스크에 반영될 걸로 기대한다. 하의 길이 문제가 재현되면 그때
되살린다(코드는 `AI/validation/TRYON/AI_tryon/CatVTON/model/attn_processor.py`에 남아있다).

### 11.5 `fit_type`에서 `cropped` 제거

§7.5에서 "기장(길이) 축은 AI 가드레일상 맨살 노출 우려로 뺐다"고 이미 결정했는데,
프로덕션 `MaskFitType`엔 `cropped`(옷을 짧게 만들어 마스크 하단을 제외하는 옵션)가 그
결정과 충돌한 채 남아 있었다 — enum 값만 안 지워진 것. `AI/app/tryon/schemas.py`/
`worker/tryon_worker_example.py` 둘 다에서 제거했다. `cloth_masker.py`의 `cropped` 분기
자체(벤더 코드)는 안 건드리고, 우리 쪽 API/워커 레벨에서 그 값을 절대 못 넘기게만 막았다.

### 11.6 아직 못 푸는 것 — 카테고리 자동 판별

상품 카테고리(하의/상의/아우터/액세서리)가 AI로 전혀 안 넘어온다 — `Product.categoryId`는
raw `Long` FK뿐이고 AI의 35종 taxonomy와 연결할 방법이 없다. `mask_type`을 AI가 스스로
판단 못 해서, 지금은 요청 payload의 `mask_type` 값을 그대로 신뢰한다. BE 요청 문서
(`.claude/requests/be/007-tryon-product-category.md`)를 남겼다.
