# 결과/입력 이미지 접근 제어 검토

S15P11A108-371(EC2 인프라 배관 E2E 검증) 진행 중 발견한 이슈. 결정된 방향은 아직 없고,
검토한 방법 3개를 비교해 둔다.

## 배경

`AI/app/gateway/router.py`의 `/results/*`(`app/main.py`의 `StaticFiles` 마운트)는 현재
**읽기 인증이 전혀 없다.** 워커가 파일을 올릴 때(`/ai/workers/upload-image`, `-upload-json`)는
`X-API-Key`로 막혀 있지만, 올라간 파일을 읽는 쪽은 URL만 알면 누구나 접근 가능하다.

파일명이 `uuid4().hex`(128비트)라 무작위로 추측하는 건 사실상 불가능하고 디렉터리 목록도
막혀 있어 "URL을 아는 사람만" 볼 수 있는 상태이긴 하다. 그런데도 문제로 보는 이유:

- `user_image_url`은 회원의 몸 사진이다(BE 스키마 `member_body_profile.body_photo_url` 예정
  용도). 상품 사진과는 다른 급의 민감정보 — 유출되면 특정 URL 하나만 새어나가도(브라우저
  히스토리, 서버 로그, 스크린샷 공유 등) 그 사람 몸 사진이 영구 공개된다.
- 만료가 없다. 한 번 생성된 URL은 삭제 전까지 계속 유효하다.
- `infra-architecture.md`의 "향후 과제" 목록에도 이 문제는 없다 — 지금까지 명시적으로 다룬
  적이 없는 갭이다.

파일-URL 매핑 자체(`/results/*` → EC2 디스크)는 웹의 표준적인 정적 파일 서빙 방식이라
문제가 아니다. S3 IAM 권한이 없어 로컬 디스크로 대체한 것도 인프라 문서에 이미 근거가
있다(§3.5). 문제는 그 위에 접근 제어가 없다는 것.

## 방법 비교

### 1. 서명된 URL (Signed URL)

게이트웨이가 `image_url`을 만들 때 만료시간(`exp`)과 서버만 아는 비밀키로 서명한 값(`sig`)을
쿼리스트링에 붙인다. 예: `.../results/tryon-results/xxx.png?exp=1735689600&sig=a1b2c3...`

`/results/*`를 지금의 `StaticFiles` 마운트 대신, 서명·만료를 검증하는 커스텀 라우트로
바꿔서 처리한다.

- **장점**: AI 파트 안에서 완결된다 — BE 인증 시스템과 얽힐 필요가 없다. S3 presigned URL과
  정확히 같은 개념이라, 원래 이 아키텍처가 하려던 것(S3 대체)의 방향과 일치한다.
- **단점**: `StaticFiles` 마운트를 커스텀 라우트로 바꿔야 한다(약간의 구현 비용). 서명 비밀키
  관리(환경변수 하나 추가)가 필요하다.
- **필요한 선행 작업**: 없음. 바로 구현 가능.

### 2. JWT 기반 인증 프록시

BE가 발급한 JWT를 AI 게이트웨이가 검증해서, 해당 job을 요청한 회원 본인만 결과를 볼 수 있게
막는다.

- **장점**: 가장 안전하다 — "본인 것만" 이라는 진짜 인가(authorization)가 걸린다.
- **단점**: ① BE의 JWT 검증 로직(시크릿·클레임 구조)을 AI가 가져와야 해서 두 파트가 얽힌다.
  ② 지금 `Job`/`JobResult` 스키마엔 "누가 요청했는지"(회원 ID)가 아예 없어서 스키마부터
  손대야 한다. ③ BE와 협의(요청 문서)가 선행돼야 한다.
- **필요한 선행 작업**: BE와 JWT 검증 방식 협의, Job 스키마에 회원 식별자 추가.

### 3. 보관 기간 정책(retention, 자동 삭제)

일정 기간(예: N일) 지난 결과물을 배치로 삭제한다. `infra-architecture.md` §8 "향후 과제"에
이미 있는 항목이다.

- **장점**: 디스크 사용량 관리도 겸한다.
- **단점**: **접근 제어가 아니다** — 살아있는 동안은 여전히 URL만 알면 누구나 본다. 노출
  시간을 줄일 뿐, 방법 1·2와 같이 가는 보완책이지 단독 해결책이 아니다.
- **필요한 선행 작업**: 없음. 별도로 언제든 추가 가능.

## 검토 결과

방법 1(서명된 URL)을 권장한다 — AI 파트 안에서 끝나고, 원래 아키텍처 의도(S3 대체)와
방향이 맞고, 지금 일정에 맞는 구현 비용이다. 방법 2는 BE와의 조율 비용이 커서 지금 범위를
넘는다. 방법 3은 병행하면 좋지만 그 자체로는 문제를 해결하지 않는다.

## 확인이 필요한 미결정 사항

- 방법 1을 실제로 채택할지, 채택한다면 구현 계획(`.claude/plans/ai/`)을 언제 쓸지 — 아직
  결정 안 됨.
- `user_image_url`처럼 입력 이미지도 같은 문제가 있다(오늘 테스트에서 `/results/test-inputs/`에
  올린 것도 마찬가지로 무인증 공개 상태). 결과물뿐 아니라 입력 이미지 업로드 경로 전체에
  같은 정책을 적용해야 한다.
