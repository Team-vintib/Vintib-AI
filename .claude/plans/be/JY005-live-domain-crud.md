## 배경/목표

라이브 방(Room)은 채팅·경매·시착 전부의 컨테이너다. 이번 주는 **실시간(WebSocket) 이전의 REST 토대**를 만든다 — 방을 생성/조회하고, 방에 상품을 걸고, 상품에 경매 조건을 설정하는 것까지. WebSocket·시그널링·입찰은 다음 주(Phase 4~5)로 넘긴다. ERD의 live 관련 테이블은 -296에서 이미 확정됐으므로 그 스키마를 그대로 구현한다.

**서윤 의존을 뒤로 미루는 것이 핵심 설계 원칙.** 상품 도메인(서윤)이 아직 없으므로, 상품을 참조하는 부분(-319)은 조회 인터페이스 스텁으로 격리해 라이브 자체 로직은 독립적으로 완성·테스트한다.

## 작업 내용

새 `live` 도메인 패키지(`com.ssafy.backend.live.{controller,service,entity,repository,dto}`)와 `auction` 패키지(경매 설정만 우선)를 `.claude/skills/scaffold` 컨벤션으로 신설한다. 모든 응답은 `ApiResponse<T>` 래퍼, 새 엔드포인트는 `.claude/skills/swagger` 컨벤션(`@Tag`/`@Operation`/`@ApiResponses` + DTO `@Schema`)으로 문서화한다.

- **엔티티는 -84(LIVE-001)에서 소유**한다. 예약·즉시 개설이 같은 `Live` 엔티티를 쓰므로 -84를 먼저 머지한 뒤 나머지 브랜치를 분기해 파일 생성 충돌을 없앤다(홈 도메인과 동일한 순차 전략).
- **상품 참조는 포트로 격리** — `live` 서비스가 의존하는 상품 조회는 인터페이스(`ProductQueryPort` 등)로 정의하고, 이번 주는 스텁 구현으로 채운다. 서윤 상품 도메인 완성 후 실제 구현으로 교체(교체점 국소화).
- **상태 enum은 ERD 확정값을 따른다** — 방송 상태(예정/진행/종료 등), 경매 상태. 홈 Mock(-279)에서 쓴 `broadcastStatus` 문자열과 정합성을 맞춘다.
- **-442·-86은 이번 주 "뼈대"까지** — 상태 전이는 API/서비스 골격과 단위 검증까지 하되, 종료 시 정리할 채팅·경매 방은 아직 없으므로 정리 로직은 훅만 남긴다. 상품 연결은 스텁 기반 CRUD까지.
- **-95(경매 설정)은 단순 HTTP.** 이 데이터가 DB에 있어야 다음 주 '경매 시작' WebSocket 이벤트를 발행할 수 있으므로 이번 주에 미리 만든다. 미등록 상품 경매 불가 검증 포함.

## 구현 중 결정 (계획과 달라진 것)

- **시각 타입은 `LocalDateTime`.** ERD는 근거와 함께 `TIMESTAMPTZ`를 못 박았으나, 기존 `BaseTimeEntity`·홈 Mock DTO가 전부 `LocalDateTime`이라 여기만 `OffsetDateTime`으로 가면 더 어긋난다. 다음 주 `auction.scheduled_end_at` 기반 카운트다운·5초 연장을 붙일 때 다시 본다.
- **`Live`는 `@Builder` 대신 정적 팩터리 두 개(`schedule`/`openNow`)만 연다.** 개설 경로가 둘이고 채워야 할 시각 필드가 달라, 빌더를 열면 "SCHEDULED인데 `scheduledAt`이 없는" 조합을 만들 수 있다.
