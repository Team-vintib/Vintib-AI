# CH016 — 내부 호가 기반 가격 비교 + 외부 검색 헷지 (설계)

> 대상 티켓: 에픽 `S15P11A108-211 [PROD] 상품 등록·판매` → 스토리 `-313 [PROD-010] 가격 책정`
> → `-494 [PROD-010 | AI] 가격 검색 로직 고도화`. 브랜치 미정.
>
> 선행: `CH003`(서비스 골격) / `CH004`(네이버 신상품가 — 이번에 처음 계산에 쓴다) /
> `CH005`(등급별 밴드 대안) / `CH015`(comps 가격 분포 — 같은 티켓 `-494`의 앞 라운드.
> `validation/PRICE/pricing-histogram-check/`의 실측 자산을 재사용한다)
>
> 산출 범위: **설계만.** 사용자 승인 후에만 구현에 착수한다.

---

## 1. 배경과 목표

지금 comps(시세 근거)는 **외부 LLM 웹검색 1회**로만 얻는다. 평균 1.7건·7.7초·매 요청 과금이고
정확도는 측정된 적이 없다(`-494` 점검 결과).

방향을 뒤집는다 — **우리 플랫폼에 등록된 상시판매 상품의 호가를 1차 근거로 쓰고, 외부 검색은
그 시세가 적정선인지 검증하는 헷지로 쓴다.** 외부 검색이 주경로에서 빠지면 지연·비용이
사라지고, 근거의 출처가 우리 데이터가 된다.

'요즘 당근 AI 개발'에서 얻은 인사이트 중 이 라운드에 대응하는 것은 두 가지다.

- **예외 처리를 프롬프트가 아니라 결정론적 후처리 레이어로 뺀다**(당근은 빅쿼리 뷰 테이블).
  → §3.2의 정규화·§3.5의 앵커 clamp·§3.4의 자릿수 게이트가 그 레이어다. BE에 **뷰**를
  요청하는 것(§3.1)도 같은 발상의 직접 적용이다.
- **분류 태스크는 구조화된 출력의 enum으로 받는다.** → 브랜드를 자유입력이 아니라 선택형으로
  받으면 §3.2의 매칭 문제가 애초에 사라진다(§7 FE/BE 요청).

'유사 게시글(임베딩)'은 **이번 범위가 아니다** — 유사상품 추천이 아니라 동일 상품 가격 비교다.

## 2. 확정된 전제

| 항목 | 결정 |
| --- | --- |
| 내부 데이터 | **상시판매 상품의 등록 호가**(낙찰가 아님) |
| 비교 단위 | **동일 상품**. 유사상품 추천이 아니다 |
| 조회 방식 | AI 게이트웨이가 BE DB를 **읽기 전용 직접 조회** |
| 더미 데이터 | FE팀이 연결 후 생성. **이번 라운드에서 만들지 않는다** |
| 테스트 | DB 없이 `test/`·`validation/`에서 전부 검증 가능해야 한다 |

호가 기준이라 내부·외부가 **같은 성질**(둘 다 판매 희망가)이 된다. 체결가 vs 호가의 비대칭
편향을 걱정할 필요가 없어 헷지 임계값을 대칭으로 잡을 수 있다.

## 3. 핵심 설계 결정

### 3.1 데이터 소스 — 테이블이 아니라 뷰

BE에 **상시판매 상품 가격 조회용 뷰**를 요청한다. AI가 조인 로직을 모르게 하고, BE 내부 스키마
변경에 완충을 둔다. 필요한 컬럼: 브랜드·상품명·카테고리·가격·**판매 상태**·등록일시·검수 등급.

- **읽기 전용을 권한 수준에서 보장**한다(코드가 SELECT만 쓰는 것과 계정이 SELECT만 할 수
  있는 것은 다르다).
- SQL은 `app/pricing/store.py` 한 곳에만 둔다 — 스키마 결합을 한 파일로 격리한다.
- `config.py`의 `db_*`(BE 공유 DB)가 이걸로 **처음 실제 사용**된다. *"아직 어느 코드도
  db_*를 안 쓴다"* 주석도 같이 갱신한다.
- 커넥션 풀은 작게 잡는다(ai 컨테이너 `mem_limit: 1g`, `MAX_CONCURRENT_JOBS = 2`).

### 3.2 동일 상품 키 — 이 설계의 최대 난점

빈티지·세컨핸드에는 SKU가 없다(LAB-21이 크림을 부적합 판정한 근거와 같다). 그래서 키를
만들어야 한다: `정규화(브랜드) + 정규화(모델명/품번)`.

- 정규화: 소문자화, 공백·특수문자 제거, **브랜드 별칭 테이블**(리바이스/Levi's/LEVIS),
  모델번호 패턴 추출(501, 04511-3773 등).
- `app/product_classifier/`는 카테고리·색상만 다루고 **브랜드·모델은 취급하지 않는다** —
  키는 판매자 입력 텍스트에서 만들어야 한다.
- **매칭 실패가 정상 경로다.** 0건이면 예외가 아니라 외부 단독 경로로 폴백한다. 기존
  `ReasonCode` 계약(근거 부족은 `success` + `priced=false`)을 그대로 따른다.
- **적용 범위를 좁게 인정한다** — 모델명이 표준화된 품목(리바이스 501, 칼하트 디트로이트
  자켓 등)에만 동일 상품이 성립한다. "빈티지 체크 플란넬 셔츠 오버핏"류는 성립하지 않는다.
  eBay식 정확도 차등(LAB-21)과 같은 구조이므로 결함이 아니라 범위의 정의로 문서화한다.

### 3.3 호가의 편향 완화 — 안 팔린 물건이 시세를 부풀린다

호가는 미판매 건도 포함한다. 과다호가로 남은 물건이 계속 조회되면 내부 중앙값이 위로 부풀고
**시간이 지날수록 심해진다**(팔린 건 빠지고 안 팔린 건 남으므로). 세 가지로 완화한다.

1. **판매 상태 가중** — 판매완료된 호가는 "체결된 호가"라 신뢰도가 높다. 판매중보다 무겁게 본다.
2. **최신성 가중** — 등록일시 기준. 지금 수집만 하고 아무도 읽지 않는 `listed_at`이 드디어
   쓰이는 자리다(LAB-15가 2순위 지표로 꼽은 항목).
3. N일 이상 미판매 건은 가중을 낮추거나 제외한다.

가중치·기간은 임의값으로 시작하고 `registry.py`에 상수로 노출한다(기존 계수들과 같은 성격의
부채임을 주석에 명시).

### 3.4 헷지 판정 — 3층, 이진 판정은 1곳만

⚠️ **KS 검정·Mann-Whitney 같은 분포 검정은 쓰지 않는다.** 외부 평균 1.7건 vs 내부 한 자리
수에서는 검정력이 0이고, 의미 없는 p값이 응답에 실린다.

- **L0 자릿수 게이트 (이진 판정 — 임계값이 필요한 유일한 지점)**
  외부 중앙값이 내부의 약 3배를 넘으면 시세 차이가 아니라 **다른 물건**이다. 이 값은 통계가
  아니라 **원인에서 나온다**: 신품 vs 중고 2~4배 / 세트·부속품 3~5배 / 통화 미변환 약 1,000배.
  즉 근거 있는 임계값이며 임의값 부채가 아니다.
- **L1 구간 겹침 (연속값)** — 두 IQR의 `교집합 폭 / 합집합 폭`. 소표본에서도 계산되고,
  CH006 히스토그램과 시각적으로 그대로 대응한다("두 막대그래프가 겹치는가").
- **L2 연속 감쇠 (임계값 없음)** — 겹침이 적을수록 신뢰도를 매끄럽게 깎고 range를 넓힌다.
  기존 `_confidence()`가 이미 연속 가중 구조라 그대로 붙는다.

**어느 쪽이 맞는지 자동으로 택하지 않는다** — 정답셋 없이는 판단 근거가 없다. 불일치는 가격을
내되 range를 넓히고 판매자에게 알리는 것으로 처리한다.

**내부 표본이 최소 N건 미만이면 헷지를 돌리지 않는다.** 1건 vs 1건 비교로 경고를 띄우는 것은
넌센스다.

### 3.5 앵커 clamp — CH004의 네이버 신상품가를 드디어 계산에 쓴다

분포 비교의 품질은 입력 정제에 좌우된다. 개별 매물 단위로 먼저 걸러낸다.

- **상한**: 신품가 중앙값의 0.9배 이상 → 중고 시세가 아니라 신품
- **하한**: 신품가의 3% 미만 → 배송비·부속품 수준, 본품이 아님
- 절대 방어: 1,000원 미만 / 1억 초과

CH004가 *"가격 계산 반영은 다음 라운드"*로 미뤄 둔 부분이 여기서 처음 쓰인다.

### 3.6 격리(quarantine) — 드롭하지 않는다

이상 판정된 외부 결과를 버리지 않고 **참고용으로 분리 노출**한다. 산정에서는 빼되 사유와 함께
응답에 남긴다. 판매자가 직접 판단할 수 있고, 우리가 잘못 걸렀을 때 정보가 사라지지 않는다.
`retail_items`를 분리한 CH004 패턴과 같다.

### 3.7 판매자 문장 — 경매·상시판매 모두에서 "가격 조언"이 된다

`rationale`(한국어 근거 문장)에 판정 결과를 얹는다.

| 판정 | 문장 방향 |
| --- | --- |
| 일치 | 외부 시세와도 비슷한 수준임을 명시 |
| 내부 > 외부 | 우리 플랫폼 호가가 X% 높음. 빠른 판매는 하단, 시세를 기다리면 상단 |
| 내부 < 외부 | 외부 시세가 X% 높음. 가격을 올려도 여지가 있음 |
| L0 게이트 걸림 | 외부 결과가 상품과 일치하지 않아 참고에서 제외했음 |

### 3.8 구조 — 기존 인터페이스에 얹는다

`CompsSource` 인터페이스에 `internal` 백엔드를 추가하면 `registry.ACTIVE_COMPS_SOURCE` 한 줄로
스왑된다. 임계치가 백엔드별로 묶여 있어 내부 백엔드는 `min_comps_for_pricing`을 올릴 수 있다.

**DB 없이 테스트 가능해야 하므로 로직과 접근을 분리한다.**

- 순수 함수: 키 정규화, 매칭, 편향 가중, 겹침 계산, 자릿수 게이트, 앵커 clamp
- `ObservationStore` 인터페이스 + `PostgresObservationStore`(SELECT 1개) +
  **`InMemoryObservationStore`**(파이썬 리스트)
- 그러면 `ACTIVE_COMPS_SOURCE="internal"`로 두고도 DB·네트워크 없이 전 경로가 돌고 CI에서
  그대로 검증된다. `comps.py`가 파싱 함수를 *"네트워크 없이 테스트되는 순수 함수"* 로 분리해
  둔 것과 같은 방식이다.

### 3.9 헷지 실행 시점 — 요청 단위가 아니다

매 요청에 외부 검색을 붙이면 내부 우선의 이득(7.7초→수십 ms, 과금 0)이 사라진다.

- 상품 등록 시점: **내부 조회만**
- 백그라운드: 상품군별로 하루 N건씩 외부 검증 → 판정 결과를 **상품군 단위로 저장**해 재사용
- 예외: 내부 매칭 0건이면 그때만 실시간 외부 검색으로 폴백

GMS 쿼터가 요청 수와 무관하게 하루 N회로 예측 가능해진다.

## 5. 범위 밖 (명시적 배제)

- 유사상품 추천·임베딩 검색(당근 인사이트 ④) — 동일 상품 비교가 목표다
- pgvector 활용 — 위와 같은 이유로 이번엔 필요 없다
- 경매 낙찰가 반영 — 스키마에 `price_kind` 칸만 남긴다
- 더미 데이터 생성 — FE팀이 연결 후 수행
- 등급별 시세 밴드(CH005 대안 1)·히스토그램(CH006) — 별도 라운드
- 판매자 채택률 추적 — BE 협의가 선행돼야 한다

## 6. 미결정 사항

- **동일 상품 키의 최종 정의** — 브랜드+모델번호만으로 할지, 사이즈·색상까지 포함할지.
  포함하면 정밀해지지만 매칭률이 급감한다. 시뮬레이션(§4 마지막 항목)으로 먼저 잰다.
- **대상 상품군 3개** — FE 시연 상품과 맞춘다. 모델명이 표준화된 품목이어야 한다(§3.2).
- **최소 표본 N** — 내부 몇 건부터 가격을 내고, 몇 건부터 헷지를 돌릴지.
- **헷지 배치 주기·하루 N건** — GMS 쿼터 예산과 함께 정한다.
- 편향 가중치(판매상태·최신성)를 임의값 부채로 남길지, 이번에 근거를 만들지.

## 7. 다른 파트에 요청할 것 (`.claude/requests/`)

**BE**
- 상시판매 가격 조회용 **뷰** + **읽기 전용 계정**(§3.1). 컬럼 계약을 문서로 고정
- `PricingResult`에 교차검증·격리 필드 추가 (계약 변경)

**FE/BE 공통**
- **브랜드를 자유입력이 아니라 선택형(enum)으로** 받도록 상품 등록 폼 변경 검토(§1).
