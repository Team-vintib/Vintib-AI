## Context — 왜 필요한가

`-192`에서 만든 72개 테스트는 **"코드가 명세대로 동작하는가"** 를 검증한다(단위·API 테스트).
`-196`이 요구하는 건 성격이 다르다 — **"판정이 실제로 얼마나 정확한가, 무엇을 틀리는가"** 다.

Jira 결과물 3개:
- 비매너 판정 정확도 테스트
- 반복 질문 응답 근거 적절성 테스트
- **오탐/미탐 사례 정리** ← 핵심 산출물

티켓 설명은 특히 "kanana zero-shot의 오탐 이슈가 모델 선정 단계에서 이미 관찰된 바 있음 — 실제
구현에서 개선 여부 확인"을 요구한다. 즉 모델 선정 단계 수치와 **대조 가능한** 측정이어야 한다.

사전 탐색에서 이미 실제 결함을 확인했다(18건 표본):

| 유형 | 사례 | 원인 |
| --- | --- | --- |
| 오탐 | `강아지 새끼 너무 귀여워요` / `쓰레기 분리배출 하고 왔어요` | 사전 어휘가 일반 명사와 겹침 |
| 오탐 | `여기가 시발점이네요` / `등신대 사진 보고 왔어요` | **부분 문자열 매칭**이 다른 단어의 일부를 잡음 |
| 미탐 | `시이이발` / `s1발` / `ㅗㅗ` / `졸라` | 모음 늘이기·문자 치환·사전 미포함 |
| 미탐 | `얼굴이 참 특이하시네요ㅋㅋ` / `이런 걸 파는 사람 수준 알만하다` | 문맥 기반 우회적 조롱 — 사전 방식의 **구조적 한계** |

이 결함들을 정량화해서 실모델 도입 근거를 만드는 것이 이번 라운드의 목표다.

## 평가셋 설계 — 두 세트로 나눈다

"기존 수치와 대조"와 "새 오탐 발굴"은 요구가 상충한다(같은 샘플이어야 대조 가능 vs 새 샘플이어야
새 결함 발굴). 그래서 세트를 분리한다.

### Set A — 호환셋 (210건, 기존 벤치마크와 동일 샘플)

`test/model_selection/classifier_benchmark.ipynb` §2의 생성 로직을 **그대로 포팅**한다.
생성기 3개(`to_chosung` / `to_spaced` / `with_laugh_suffix`)와 기반 문장 리스트가 전부 순수
stdlib이라 의존성 없이 옮길 수 있다. `test/`를 import하지 않고 재선언한다(규약).

- 정상 126건 = 템플릿 21 × 접미사 6
- 악성 84건 = 문장형 42(원문 21 + 웃음패딩 21) + 짧은비속어 42(원문 14 + 초성체 14 + 공백 14)
- 라벨 분포 정상:악성 = 126:84 (3:2)

**이 세트로만 문서 수치와 대조한다** — `kor_unsmile` 악성 recall 58.3%, `kcelectra_base_hate`
98.8%가 같은 210건 기준이므로 규칙 기반 수치를 같은 표에 놓을 수 있다.
(⚠️ 포팅 시 알려진 흠: `_NORMAL_SUFFIXES`의 `" 감사합니다"`가 이미 같은 말로 끝나는 템플릿에
붙어 `…감사합니다 감사합니다`가 생긴다. 원본 재현이 목적이므로 **그대로 둔다**.)

### Set B — 확장셋 (수제, 오탐/미탐 발굴용)

Set A에 없는 축을 손으로 채운다.

- **hard negative(오탐 유발)**: 사전 어휘를 포함하지만 정상인 문장 — `강아지 새끼`, `시발점`,
  `등신대`, `쓰레기 분리배출`, `죽어라 일했다`, `미친 예쁘다`, `소백산`, `사부님`
- **문맥형 악성**: 어휘로는 안 잡히는 우회적 조롱·인신공격
- **추가 우회 변형**: 모음 늘이기(`시이이발`), 문자 치환(`s1발`), 구두점 삽입(`개.새.끼`)
  → 생성기 2개를 새로 만든다(`with_vowel_stretch`, `with_char_substitution`)

Set A/B 지표를 각각 내고 나란히 보고한다. **합치지 않는다** — 합치면 대조 가능성이 깨진다.

### Set C — 반복질문 평가셋

- **paraphrase 그룹** 6개(사이즈·재고·가격·배송·교환·결제), 그룹당 3~4 표현 + 각 그룹에
  기대 근거 문서 id(`faq_size_01` 등) 부여
- **지식베이스 밖 그룹** 4개(매장 위치·주차·브랜드 역사·다음 방송 일정) — 침묵해야 하는 케이스

## 측정 지표

리포에 confusion matrix·F1·FP/FN 리포터가 **전혀 없어** 이번에 새로 만든다. 기존 자산의 모양은
최대한 따른다(`classifier_benchmark.BenchResult`의 `latency_stats()` nearest-rank 방식,
`embedding_benchmark.precision_recall_at()`의 pairwise TP/FP/FN 계산).

### 비매너 판정

| 지표 | 정의 |
| --- | --- |
| confusion matrix | TP/FP/FN/TN (악성=positive) |
| accuracy | 전체 정확도 |
| precision / recall / F1 | 악성·정상 각각 |
| latency | mean / p50 / p95 / p99 (ms) — 설계 목표 p95 300ms 검증 |
| **오탐 사례** | 정상→악성 오판 문장 + 매칭된 사전 어휘(`AbuseResult.label`) |
| **미탐 사례** | 악성→정상 오판 문장 + 우회 변형 종류 |

### 반복질문 응답 근거

| 지표 | 정의 |
| --- | --- |
| 클러스터링 pairwise P/R | 같은 그룹 쌍을 묶었는지 (활성 임계치 기준) |
| 임계치 스윕 | 0.10~0.90, 0.05 간격 — 현재 0.30이 최적 근방인지 |
| 근거 문서 정확도 | in-KB 질문의 top-1 `doc_id` == 기대 문서 비율 |
| **침묵 정확도** | 지식베이스 밖 질문에서 답변을 만들지 않은 비율 (목표 100%) |
| **근거 있는데 침묵** | 미탐 — 어휘 비중첩으로 임계치 미달한 케이스 |
| **근거 없는데 답변** | 오탐 — 환각. 0건이어야 함 |

## 모듈 구조

`app/recommend/pipeline/`의 오프라인 배치 관례를 따른다. 평가 대상이 프로덕션 코드이고 기본
백엔드가 전부 의존성 없으므로 **하네스 전체가 CI에서 실행된다**(torch 가드 불필요).

| 파일 | 책임 |
| --- | --- |
| `app/chat/eval_dataset.py` | Set A/B/C 생성. 우회 변형 생성기 5개 + 수제 코어 상수. 순수 stdlib |
| `app/chat/evaluation.py` | 지표 계산. `ModerationEval` / `FaqEval` dataclass + confusion·P/R/F1·latency + FP/FN 사례 수집 |
| `app/chat/pipeline/__init__.py` | 신규 |
| `app/chat/pipeline/evaluate.py` | CLI 러너. argparse + `print("[evaluate] …")` + 마크다운 리포트 기록 |
| `app/chat/tests/test_chat_evaluation.py` | 지표 계산 유닛테스트 + **CI 회귀 게이트** |

**재사용할 기존 자산**:
- `app/chat/classifier.py`의 `RuleBasedClassifier` / `normalize` — 평가 대상 그 자체
- `app/chat/faq.py`의 `embed` / `cosine` / `MockRetriever` / `QuestionClusterer`
- `app/chat/registry.py`의 임계치 — **하드코딩하지 않고 import** (`test_chat_faq.py` 선례)
- `app/chat/service.py`의 `ChatModerationService` — 반복질문 E2E 경로 평가에 사용

### CI 회귀 게이트 설계

결함을 고치지 않기로 했으므로 게이트는 **품질 강제가 아니라 회귀 방지**다. 측정 후 실측치보다
약간 낮게 잡는다.

```
assert moderation.recall("악성") >= MIN_ABUSE_RECALL        # 실측 − 여유
assert moderation.precision("악성") >= MIN_ABUSE_PRECISION
assert set(false_positives) <= KNOWN_FALSE_POSITIVES        # 새 오탐 없음
assert set(false_negatives) <= KNOWN_FALSE_NEGATIVES        # 새 미탐 없음
assert faq.silence_accuracy == 1.0                          # 환각 0건 — 정책이라 강제
assert moderation.latency_p95_ms < 300                      # 설계 목표
```

`<=` 부분집합으로 두는 게 핵심이다 — 나중에 분류기를 개선하면 집합이 줄어들어 그대로 통과하고,
악화되면 새 항목이 생겨 실패한다. `KNOWN_*` 상수에는 각 항목이 왜 알려진 실패인지 주석을 단다.

### 리포트 출력

`app/chat/artifacts/eval_report.md`에 기록하고 **gitignore한다**(생성물). `AI/.gitignore`에
기존 두 주석과 같은 형식으로 한 줄 추가한다.

사람이 읽는 서술(오탐/미탐 정리)은 **계획서 결과 섹션에 커밋**한다 — 리포에 `reports/` 선례가
없고, 생성 파일만 남기면 Jira 결과물 "오탐/미탐 사례 정리"가 리포에 남지 않는다.

## 검증 방법

```bash
cd AI
pip install -r requirements-dev.txt
ruff check . && black --check . && pytest -q
python -m app.chat.pipeline.evaluate            # 콘솔 표 + artifacts/eval_report.md
python -m app.chat.pipeline.evaluate --set A    # 호환셋만
```

- Set A 210건 생성 결과가 원본과 동일한지 확인(총 210, 정상 126 / 악성 84).
- 콘솔 표에 Set A/B 지표가 나란히, 문서 인용 수치(`kor_unsmile` 58.3%, `kcelectra` 98.8%)와
  같은 표에 출력되는지 확인. **인용 수치는 재측정값이 아님을 표에 명시**한다.
- 오탐/미탐 사례가 문장 + 근거 라벨과 함께 나열되는지 확인.
- 임계치 스윕이 현재 0.30 주변 곡선을 보여주는지 확인.
- `pytest -q` — 기존 110개 + 신규 테스트 전부 통과(스킵 없이 CI에서 실행).

## 측정 결과 (2026-07-26 실측)

`ruff` / `black` / `pytest -q` 통과 — 140 passed, 2 skipped (기존 110 + 신규 30).
평가 대상: `rule_based` 분류기 / `mock_bigram` 임베더 / `mock` retriever (전부 현재 기본값).

### 1. 비매너 판정 — Set A 호환셋 (210건, 기존 벤치마크와 동일 샘플)

혼동행렬 TP 14 / FP 0 / FN 70 / TN 126.

| 분류기 | accuracy | 악성 recall | 출처 |
| --- | --- | --- | --- |
| **rule_based (현재 기본값)** | **66.7%** | **16.7%** | 이번 실측 |
| kor_unsmile (기존 baseline) | 83.3% | 58.3% | 문서 인용 |
| kcelectra_base_hate (1순위 후보) | 99.5% | 98.8% | 문서 인용 |

악성 precision 100.0% · recall 16.7% · F1 28.6% / 정상 recall 100.0% / 지연 p95 0.01ms.
우회 변형별 recall은 원문 17.1%(6/35) · 웃음패딩 19.0%(4/21) · 초성체 14.3%(2/14) ·
띄어쓰기 14.3%(2/14) — **변형 종류와 무관하게 고르게 낮다.**

**핵심 발견**: 규칙 기반의 악성 recall이 기존 baseline의 **약 1/3.5**다. 원인은 우회 처리
실패가 아니라 **사전 어휘 자체의 협소함**이다 — 벤치마크의 악성 문장 대부분("실력은 없네",
"양심 있냐", "한심하다", "정떨어진다")이 사전에 없다. 변형별 recall이 고르게 낮은 게 그 증거다
(우회가 문제면 원문 recall만 높아야 한다).

| 침묵 정확도 (지식베이스 밖 8건) | **100.0%** — **환각 0건** |
| B-1 질문 판별 | 26/26 전부 통과 |
| 클러스터링 (임계치 0.30) | precision 87.5% · recall 95.5% |

**RAG 경로는 흠 없이 동작한다.** "근거 있는 경우에만 응답"(CHAT-02/03) 정책이 실제로 지켜지고,
근거 문서도 100% 정확하다. 비매너 판정과 대비가 뚜렷하다.

**임계치 스윕에서 나온 발견** — 현재 `cluster_similarity=0.30`은 최적이 아니다:

| 임계치 | precision | recall |
| --- | --- | --- |
| 0.30 (현재) | 87.5% | 95.5% |
| **0.35** | **91.3%** | **95.5%** | ← recall 손실 없이 precision만 개선 |
| 0.40 | 90.9% | 90.9% |
| 0.50~0.60 | 100.0% | 81.8% |
| 0.80 (LAB-8 제안값) | 100.0% | 27.3% |

0.35가 recall을 잃지 않고 precision을 3.8%p 올린다. 다만 **수정은 별도 티켓**(이번 스코프는
측정까지). 오분류 쌍은 잘못 묶임 3건(`교환이나 반품 되나요?` ↔ `주차 되나요?` 0.4136 —
"되나요" 어미 중첩), 못 묶음 1건(`주차 되나요?` ↔ `주차 가능한가요?` 0.1550).
LAB-8 제안값 0.8은 recall 27.3%로 **사실상 작동하지 않음**이 다시 확인됐다.

### 4. 결론 — 티켓 질문에 대한 답

Jira가 물은 "실제 구현에서 개선 여부"에 대한 답은 **아니다**. 현재 기본값인 규칙 기반 분류기는
모델 선정 단계의 어떤 후보보다도 악성 recall이 낮다(16.7% vs 58.3% vs 98.8%). 이건 구현 결함이
아니라 **의도된 트레이드오프의 대가**다 — CI에서 의존성 없이 전체 파이프라인을 검증하려고
규칙 기반을 기본값으로 택했고, 실모델은 레지스트리 키 하나로 교체되게 해 뒀다.

실서비스 전환 시 `ACTIVE_CLASSIFIER = "kcelectra_base_hate"`가 필요하다는 근거가 정량적으로
확보됐다. 반대로 **반복질문 RAG 경로는 목업 상태로도 정책을 지키며 정확히 동작**한다.
