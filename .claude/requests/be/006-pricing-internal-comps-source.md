## 처리 결과 (2026-08-06 BE 회신)

**§1-A 회신 요약**
- 브랜드는 **이미 FK로 구조화**돼 있다(`brand_id`, 자유입력 아님, 21개 고정 목록 전달받음).
  → §4의 "브랜드 선택형 전환" 요청은 **필요 없어짐**(이미 충족).
- 모델명/품번 전용 컬럼은 **없음** — `title` 자유 텍스트에서 파싱 필요.
- 판매 상태는 **`sale_status`**(`DRAFT`/`ON_SALE`/`AUCTION_SCHEDULED`/`AUCTION_IN_PROGRESS`/
  `SOLD`)와 **`sale_type`**(`DIRECT_SALE`/`AUCTION`)이 **별개 enum**. 상시판매만 걸러내려면
  `sale_type = DIRECT_SALE` 조건이 필수 — `SOLD`만 보면 경매 낙찰가까지 섞인다.
- `condition_grade`는 Redis가 아니라 **product 테이블 영구 컬럼**. AI 쪽이 참고한
  "Redis TTL 1시간" 설명은 검수 세부 findings와 혼동한 것이었다(BE가 명확히 구분해서 답변).
- 카테고리(126개, 3-depth) / 브랜드(21개) 전체 목록 수령.
- `POST /pricing/estimates` 호출 자체가 BE에 아직 없어 §1-A 7·8은 "해당 없음".
- AI ↔ BE DB 네트워크·자격증명은 이미 연결돼 있으나, **BE와 같은 관리자 계정**이라 읽기
  전용이 아니다.

**§1-B 회신 요약**
- 상시판매 72건 존재하나 `brand_id`/`condition_grade`가 전부 NULL, 상품명이 테스트 픽스처
  (`zzsearch...`, "리바이스 501 빈티지" 반복 등) — **실질적으로 0건.**

**§2 회신** — BE도 **뷰 + 읽기 전용 계정** 방식 지지(뷰가 스키마 변경 완충 역할을 하고,
헷지가 배치 작업이라 SQL이 자연스러우며, 컨트롤러/인증 유지보수 부담을 늘리지 않기 위함).

**§3/§4 처리** — 뷰 생성·읽기 전용 계정 발급은 인프라 변경이라 BE가 별도 계획
(`docs/plans/BE/`)으로 사용자 승인 후 진행하기로 함. **BE가 §1-B 결과(실질 데이터 0건)를
근거로, 이 방향을 그대로 밀어붙일지 먼저 확인해 달라고 요청함.**

→ AI 쪽 결론: 데이터가 없는 지금 인프라(뷰·계정)를 먼저 만드는 것은 순서가 아니다.
**DB 없이 완성 가능한 부분(매칭·헷지 순수 함수, `InMemoryObservationStore`, 시뮬레이션)을
먼저 진행**하고, 뷰·계정 요청은 FE 더미 데이터 생성 또는 실사용자 등록 건수가 쌓인 뒤
재요청한다. 반영: `.claude/plans/ai/CH016-internal-comps-hedge.md` §2·§3.1·§4·§7.

## 배경/이유

지금 가격 책정의 시세 근거(comps)는 **외부 LLM 웹검색 1회**로만 얻는다. 실측 결과 평균
1.7건·7.7초·매 요청 과금이고 정확도는 측정된 적이 없다.

방향을 바꿔 **우리 플랫폼 상시판매 상품의 등록 호가를 1차 근거로 쓰고, 외부 검색은 그 시세가
적정선인지 검증하는 보조 장치로** 쓰려 한다. 그런데 이 설계는 BE가 가진 데이터의 실제 모양에
전적으로 의존한다 — 아래 §1을 먼저 확인해야 설계가 성립하는지 알 수 있다.

**AI 쪽에서 BE 코드를 수정하지 않는다.** 이 문서는 확인 질문과 요청만 담는다.

## 1. 먼저 받아야 하는 것 (설계 전제 검증)

설계가 아래를 당연하게 가정하고 있다. **하나라도 사실이 아니면 해당 기능을 범위에서 뺀다.**

**요청 형식**: 서술 설명("브랜드 컬럼 있습니다")보다 **그대로 붙여넣을 수 있는 산출물**(DDL,
엔티티 클래스, enum 정의, 값 목록)이 훨씬 유용하다. AI 쪽은 받은 컬럼 계약을
`app/pricing/store.py`에 그대로 고정할 예정이다.

### 1-A. 코드만 읽으면 답할 수 있는 것

1. **상시판매 상품 엔티티의 컬럼 목록** — 이름·타입·nullable. DDL이나 엔티티 클래스를 그대로
   붙여 주면 된다. 특히 아래 둘의 존재 여부가 중요하다.
   - **브랜드가 구조화 필드인가** — 상품명 텍스트뿐이면 동일 상품 판정을 텍스트 정규화로만
     해야 해서 정확도가 크게 떨어진다.
   - **모델명/품번 필드가 있는가** (예: "501", "04511-3773") — 없으면 매칭 정밀도가
     브랜드+카테고리 수준으로 내려간다.
2. ⚠️ **판매 상태 enum의 값 문자열을 그대로** (`ON_SALE`인지 `SELLING`인지) + 각 값의 의미.
   추측해서 쓰면 필터가 **에러 없이 0건**을 반환한다 — 가장 발견하기 어려운 실패다. 호가는
   *안 팔린 물건도 포함*하므로 판매완료 여부가 편향을 잡는 핵심 신호다.
3. ⚠️ **품질검수 등급(condition_grade)의 저장 위치** — 상품 테이블 컬럼인가, 별도 검수
   테이블인가(그렇다면 조인 키). AI 쪽 기록(`app/pricing/schemas.py`)에는 *"검수 결과는
   Redis에 TTL 1시간으로만 남고, 상품 등록 흐름에서 BE가 들고 있다"* 고 되어 있다. 영구
   저장되지 않으면 **등급별 시세 가중·등급별 가격 밴드가 전부 불가능**해진다.
4. **상품 등록일시(또는 가격 확정 시점)** 컬럼 — 오래된 호가의 가중을 낮추는 데 쓴다.
5. **카테고리 체계 매핑** — AI 쪽 `GarmentCategory`는 6종(니트/셔츠/자켓/코트/팬츠/스커트)인데
   BE는 `categoryId = f(성별, subcategory)` 조합이다. 매핑 표(또는 BE 카테고리 전체 목록)가
   있어야 내부 조회에 카테고리 필터를 걸 수 있다.
6. **브랜드 마스터 테이블이 있는가** — 있으면 전체 목록. AI 쪽 별칭 테이블의 시드로 그대로
   쓰고, §4(선택형 전환)의 실현 가능성도 여기서 갈린다.
7. **BE가 `POST /pricing/estimates`에 실제로 채워 보내는 값** — `brand`/`category`가 항상
   오는가, 비는 경우가 있는가. 지금 스키마상 optional인데, 실제로 안 오면 **동일 상품 키의
   입력이 없어져** 정규화를 설계할 수 없다.
8. **job result 파싱이 엄격한가** — `PricingResult`에 필드가 추가되면 BE 파싱이 깨지는가
   (unknown 필드 거부 여부). §3-4의 계약 변경 리스크가 이 한 줄로 결정된다.

### 1-B. DB를 실제로 조회해야 아는 것

데이터가 아직 없으면 **"0건"이라고만 답해 주면 된다** — 그 경우 1-A(엔티티 정의)와 등록 폼의
실제 입력 필드로 대체하고, FE 더미를 BE 스키마에 맞춰 만든다.

9. **마스킹된 실제 행 5~10건** (브랜드 / 상품명 / 모델명 / 가격 / 판매 상태 / 등록일시 / 등급).
   **스키마보다 이게 더 유용하다** — 브랜드 표기가 한글·영문·혼용인지, 모델번호가 상품명에
   섞여 있는지, 가격 단위가 원인지, null이 얼마나 흔한지를 봐야 정규화 규칙이 제대로 나온다.
10. **건수 통계** — 전체 상시판매 건수 / 브랜드별 상위 10개와 각 건수 / **같은 브랜드+모델
    조합이 2건 이상인 조합 수**. 마지막 항목으로 "동일 상품 비교가 실제로 성립하는지"가
    즉시 판정되고, FE가 만들 더미의 필요량도 여기서 계산된다.
11. **AI 컨테이너에서 BE DB에 닿는가** — compose 네트워크에서 부를 호스트명·포트·스키마명과
    자격증명 주입 경로. AI 쪽 설정에 `db_*` 항목은 있으나 지금까지 어느 코드도 쓰지 않았다.

## 2. 협의가 필요한 것 — 접근 방식

AI 쪽에서는 잠정적으로 **AI 게이트웨이(FastAPI)가 BE DB를 읽기 전용으로 직접 조회**하는
방향으로 정했다(조회만 하고 쓰지 않으므로). 다만 **BE 동의를 받은 결정이 아니다.**

`CH012`에서 *"결과의 소유권은 BE에 있다"* 로 정리한 전례가 있으므로, BE가 **조회 API로
제공하는 편이 낫다고 판단하면 그쪽을 따르겠다.** 어느 쪽이 좋을지 의견을 주면 좋겠다.

- 직접 조회의 장점: BE 작업이 뷰·계정 제공으로 끝난다
- 조회 API의 장점: 소유권 경계가 명확하고 스키마 변경에 안전하다
- AI 쪽 제약: 무엇을 택하든 **조회 전용**이다. 쓰기는 하지 않는다

## 3. 요청 사항 (§1·§2가 정리된 뒤)

1. **상시판매 가격 조회용 뷰**
   테이블 직접 조회 대신 뷰를 주면 AI가 조인 로직을 몰라도 되고, BE 내부 스키마 변경에
   완충이 생긴다. 필요한 컬럼: 브랜드 / 상품명 / 모델명·품번 / 카테고리 / 가격 / 판매 상태 /
   등록일시 / 검수 등급.
2. **읽기 전용 DB 계정** (직접 조회 방식으로 갈 경우)
   코드가 SELECT만 쓰는 것과 계정이 SELECT만 할 수 있는 것은 다르다. 권한 수준에서 막아 두면
   AI 쪽 실수로 데이터가 바뀔 여지가 없다.
3. **컬럼 계약 문서화**
   컬럼 이름·타입·상태 enum 값을 문서로 고정해 주면, 변경 시 AI 쪽이 조용히 깨지는 일을
   막을 수 있다. AI 쪽은 SQL을 한 파일(`app/pricing/store.py`)에만 두어 결합을 격리한다.
4. **`PricingResult` 응답 계약 변경 예고**
   내부 시세와 외부 시세의 교차검증 결과, 그리고 이상 판정으로 산정에서 제외한 매물 목록을
   응답에 추가할 예정이다. 필드가 늘어나는 방향이라 기존 파싱은 깨지지 않을 것으로 보지만,
   구체 필드가 확정되면 별도로 공유한다.
